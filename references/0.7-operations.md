# 0.7 Completing the operation set — from management use case to API

A *"Manage products"* row in the use case table is **valid and empty**. It satisfies every [2.1](2.1-actors-and-use-cases.md) rule — correct goal level, verb + object, actor, and supporting `FR` — yet omits what every downstream document needs: **how many operations exist, who performs each, what data crosses, and what failure returns.**

That is why this file exists. [0.5](0.5-derivation.md) determines *which components exist* and [0.6](0.6-mechanism.md) checks *whether a picture represents the real mechanism*. This file handles the third layer, which no notation can enforce: **how much remains missing inside a named element.**

Read it before writing any section that produces operations or endpoints: [2.3](2.3-use-case-specs.md) · [3.2](3.2-sequence-diagrams.md) · [3.3](3.3-class-diagrams.md) · [4.1.2](4.1-design.md#412-database-design) · [4.1.3](4.1-design.md#413-detailed-class-design) · [4.4](4.4-api-contract.md) · [6.1](6.1-test-plan.md).

## The cost of a merged row

A merged management use case does not fail where it is written. It fails across six downstream documents, and every failure **looks complete**:

| Document | Result of merging | Discovered when |
|---|---|---|
| [2.3](2.3-use-case-specs.md) activity flow | One flow, usually *create* | — |
| [3.1](3.1-analysis-classes.md) class table | One `<<control>>` with vague responsibility *"manage products"* | — |
| [3.2](3.2-sequence-diagrams.md) sequence | One diagram, usually *create*; update and delete have none | Frontend asks "what do I call to delete?" |
| [4.1.3](4.1-design.md#413-detailed-class-design) design class | An unimplementable `manageProduct()` method | Implementation |
| [4.4](4.4-api-contract.md) API | 1 endpoint instead of 5–7; no delete error codes | Sprint 3, after frontend built the list screen |
| [6.1](6.1-test-plan.md) tests | Cases for *create*; delete-while-referenced is untested | Production |

This chain has an unpleasant property: **no intermediate layer detects it**. A one-operation sequence diagram is valid. A single endpoint is a valid section. Only counting backward from the operation matrix exposes the four omissions.

The general rule applies [SKILL.md](../SKILL.md) rule 3 one level deeper: **anything named "manage," "process," "configure," or "monitor" must list what it contains.** If the list is unknown, mark `**TBD**`; the row is not complete.

## The operation matrix

Every use case with at least two operations **must** contain this table inside its [2.3](2.3-use-case-specs.md) specification, **before** `Activity flow`, because the table determines how many flows must be written:

| ID | Operation | Actor | Trigger | Preconditions | Input | Result · postconditions | Rules | Exceptions | Screen | `I<n>` |
|---|---|---|---|---|---|---|---|---|---|---|
| T1 | List | Inventory clerk | Open catalog screen | Authenticated with `product:read` | filters, pagination, sorting | Current page + total count | — | 6a permission revoked | SCR-P01 | I1 |
| T2 | View details | Inventory clerk | Select a row | T1 | `product_id` | Full record + variants | — | 6b not found | SCR-P02 | I2 |
| T3 | Create | Catalog manager | Click *Add* | `product:write` permission | 9 required fields (field table) | Product in `draft` state with an ID | BR3, BR7 | 4a duplicate SKU · 4b invalid format | SCR-P03 | I3 |
| T4 | Update | Catalog manager | Click *Edit* in T2 | Product exists and is not `archived` | `product_id` + changed fields | Updated record + history row | BR3, BR9 | 5a modified concurrently · 5b product locked | SCR-P03 | I4 |
| T5 | Change state | Catalog manager | Click *Publish* | Images and price complete — BR11 | `product_id`, target state | New state + `product.published` event | BR11, [3.5](3.5-state-machines.md) | 5c publication conditions unmet | SCR-P02 | I5 |
| T6 | Soft delete | Catalog manager | Click *Delete* | No open order references it | `product_id` | `deleted_at` set; item disappears from T1 | BR12 | 7a still referenced | SCR-P02 | I6 |

Six rules govern this table, each preventing a different failure:

- **`Exceptions` is the costliest and most frequently blank column.** Every cell must cite a real numbered exception flow in `Activity flow`, later mapped to a real [4.4](4.4-api-contract.md) error code. A *write* operation with no exceptions has not been considered in failure.
- **`Input` states granularity, not every field name.** Field details belong in the use case's `Data fields` table. Here, show enough to reveal that T3 and T4 receive **different** inputs (`T4` has `product_id`; `T3` does not), which produces separate endpoints.
- **Different `Actor` values between rows signal separate use cases**, not a detail. See the [split test](#the-split-test-when-an-operation-stands-alone).
- **`Result · postconditions` must be observable** and include side effects: history row, emitted event, reduced inventory. This is where *"update writes an audit log"* is decided once instead of assumed three ways.
- **Leave `I<n>` blank while writing 2.1 and backfill it when [4.3.5](4.3-detailed-design.md#interface-inventory-the-contract-index) assigns IDs.** A blank after the API contract is complete identifies an unreachable operation.
- **Operation IDs are `T<n>` within a use case**; the full citation is `UC-A03.T4`. Downstream documents cite the ID rather than *"update"* because several use cases may contain an operation with the same name.

A use case with **one** operation does not need this matrix; its activity flow already provides the single row.

## The thirteen-operation inventory

Do not invent the matrix above; **sweep** it with the inventory below, using the same mechanism as the [0.5 K2](0.5-derivation.md#k2-nouns-the-filter-and-category-inventory) entity-category inventory. An unmentioned operation leaves no words to extract, so a checklist must ask about every row.

For every business object managed by the use case, process all thirteen rows and write `yes` or `no, because …`:

| # | Operation | Question | Often missed because |
|---|---|---|---|
| 1 | List | Who needs to see several records at once? | It seems obvious, so nobody decides pagination or sorting |
| 2 | Search and filter | Which fields support filtering and search? | It is merged into (1), then becomes a different endpoint next sprint |
| 3 | View details | What appears in details but not the list? | It resembles (1) but has a different payload and possibly stricter permission |
| 4 | Create | Which fields are required at creation? | — (the only operation nobody forgets) |
| 5 | Update | Which fields may and may not change? | Nobody writes the list of fields that **cannot** change |
| 6 | Change state | Is there a lifecycle, and who may trigger each transition? | It is hidden in (5) as "update status," losing the [3.5](3.5-state-machines.md) state machine |
| 7 | Delete | Soft or hard; what happens while referenced? | Everyone writes *"delete"* and nobody writes *"when deletion is forbidden"* |
| 8 | Restore | Can a soft-deleted item return, and who may restore it? | It follows directly from (7), but nobody derives it |
| 9 | Duplicate | Does anyone create a new record from an old one? | Real users do it daily; documentation rarely includes it |
| 10 | Bulk | Can several records be processed at once? | Partial success requires a different API shape — [4.4](4.4-api-contract.md) |
| 11 | Import / Export | Do CSV/Excel files enter or leave? | It always appears after handoff |
| 12 | Review / Approve | Must someone agree before the change takes effect? | A second actor is hidden inside one use case |
| 13 | View change history | Must the system answer who changed what and when? | A late decision requires reconstructing history from logs, if possible |

Rows 9, 11, 12, and 13 are the most valuable because each **changes architecture** when discovered late: duplication changes uniqueness constraints, file import changes the error model, approval adds a role and state, and history adds a table.

- **`No, because …` is valid and must be written.** *"No delete — accounting data is retained forever, BR14"* is valuable; a blank cannot be distinguished from an unasked question ([0.5](0.5-derivation.md#derivation-tables-keep-rejected-candidates)).
- **This inventory runs before anyone answers**, so in mode B it becomes an [0.4](0.4-interview.md) interview-round question rather than a place to guess. A half-filled table is faster to answer than *"what do you need to manage?"*
- **Mode A reads it from routes**: list every route touching the resource, queue consumer, and scheduled job, then compare with all thirteen rows. A route without a documented row means missing documentation; a row without a route is an unbuilt feature or invention.

## The split test: when an operation stands alone

This is a real design question, not *"always split"* or *"always merge"*: **the same operation set may form one use case or four, depending on whether operations differ in externally visible ways.**

Run six questions for every operation pair. **One `different` answer is enough** to require a separate representation:

| # | Do the operations differ in | `different` ⇒ separate |
|---|---|---|
| 1 | **Primary actor** | A separate use case in [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) — use cases are defined around actors |
| 2 | **Preconditions or permissions** | A separate flow and activity-diagram branch |
| 3 | **Who calls whom** — call sequence and external systems | **A separate sequence diagram** in [3.2](3.2-sequence-diagrams.md) |
| 4 | **Data crossing the boundary** — request or response payload | **A separate endpoint** in [4.4](4.4-api-contract.md) and separate `I<n>` |
| 5 | **Postconditions** — resulting state and emitted events | A separate matrix row and [6.1](6.1-test-plan.md) test case |
| 6 | **Exception set** | A separate [4.4](4.4-api-contract.md) error-code group |

Interpret results at three levels, and **at least the lowest level always applies** — there is no "write nothing" outcome:

| Differences | Representation level | Specifically |
|---|---|---|
| Only (4), (5), (6) — same actor and flow, different data | **Within one use case** | One operation-matrix row · one sequence `alt` · one endpoint · one error-code group |
| Also (2) or (3) | **Separate subsection in the same use case** | One numbered flow · **one separate sequence diagram** · one `### UC-A03.T6 — Delete product` block |
| Also (1) | **Separate use case** | A new [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) row plus class table, sequence, class diagram, screen, and tests |

Three examples show that the test produces genuinely different conclusions:

| Case | Differences | Conclusion |
|---|---|---|
| Product *list* versus *details* | (4) payload | One use case, two endpoints, one sequence diagram with two calls |
| Product *create* versus *update* | (4) payload, (5) postconditions, (6) duplicate SKU only on create and stale version only on update | One use case, two endpoints, separate branches; separate flows because preconditions differ |
| *Update price* versus *Approve price list* | (1) actor, (2) permission, (5) event | **Two use cases.** Merging hides a role and an approval step |

**The most common mistake is not a wrong split but no split at all**, leaving missing parts to surface at the API layer. The second is splitting in reverse: four use cases `Create / Update / Delete / View product`. These are four operations of one business goal, not four goals; the split quadruples the use case table while still failing to assign rules to operations ([2.1](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases), *CRUD is not a use case set*). **The operation matrix prevents both failures**: one use case per goal with every operation listed.

## The seven-stage chain for every operation

Every operation-matrix row passes through exactly seven stages, and **can be counted at each stage**. This expands the [SKILL.md](../SKILL.md) traceability chain at operation rather than use case level:

| # | Stage | Document | One operation becomes | Verify by |
|---|---|---|---|---|
| 1 | Operation | [2.3](2.3-use-case-specs.md) | One `T<n>` operation-matrix row | All 13 inventory rows answered `yes`/`no, because` |
| 2 | Flow | [2.3](2.3-use-case-specs.md) | One main flow or numbered branch | Every `T<n>` appears in at least one flow |
| 3 | Responsibility | [3.1](3.1-analysis-classes.md) | One responsibility on the use case `<<control>>` | `Responsibility` enumerates `T1..Tn`, not *"manage X"* |
| 4 | Interaction | [3.2](3.2-sequence-diagrams.md) | A separate diagram or an `alt` carrying `T<n>` | Every `T<n>` is visible; none exists only in a caption |
| 5 | Structure | [3.3](3.3-class-diagrams.md) → [4.1.3](4.1-design.md#413-detailed-class-design) | A full method signature + `Exceptions` column | Public control methods ≥ documented `T<n>` count |
| 6 | Data + contract | [4.1.2](4.1-design.md#412-database-design) · [4.4](4.4-api-contract.md) | A CRUD cell + endpoint + error codes | CRUD matrix ([0.5 K4](0.5-derivation.md#k4-the-crud-matrix)) has no row missing `C`; every endpoint has `I<n>` |
| 7 | Verification | [6.1](6.1-test-plan.md) | At least 1 success case + 1 per exception | Every `Exceptions` cell maps to a `TC-…` |

The **operation traceability matrix**, placed in [4.4](4.4-api-contract.md) and repeated in [6.1](6.1-test-plan.md), is the only place all seven stages are visible together:

| Operation | 3.2 diagram | 4.1.3 method | Table written | Endpoint | Error codes | Test cases |
|---|---|---|---|---|---|---|
| UC-A03.T3 Create | 3.2 UC-A03 *Create* | `ProductService.create` | `product` C | `POST /products` | `sku_duplicated`, `validation_failed` | TC-PRD-01, 02, 03 |
| UC-A03.T6 Delete | 3.2 UC-A03 *Delete* | `ProductService.softDelete` | `product` U | `DELETE /products/{id}` | `product_referenced` | TC-PRD-11, 12 |

A blank in any column is a specific question, not generic unfinished work: blank `Endpoint` means the operation is unreachable; blank `Error codes` leaves failure handling to the client; blank `Test cases` means nobody knows whether it works.

## Exceptions become error codes

This chain runs in one direction and **must not break** — every break forces the client to guess:

```
Exception flow 2.3 (7a)  →  Method exception 4.1.3 (ProductReferenced)
                           →  Error code 4.4 (409 product_referenced)
                           →  Screen message 4.5
                           →  Test case 6.1 (TC-PRD-11)
```

| Location | Write | Failure if omitted |
|---|---|---|
| [2.3](2.3-use-case-specs.md) exception flow | ID + triggering condition + system response | Nobody knows the case exists |
| [4.1.3](4.1-design.md#413-detailed-class-design) `Exceptions` column | One exception name per case | Every failure becomes generic `Exception` that upper layers cannot distinguish |
| [4.4](4.4-api-contract.md) error table | HTTP + `code` + retryability + client action | Client parses `message` and breaks when wording changes |
| [4.5](4.5-ui-design.md) screen specification | Actual message at the correct location | One *"Something went wrong"* toast for seven cases |
| [6.1](6.1-test-plan.md) | One case per error code | Failure branch never runs before a customer reaches it |

**Two failures requiring different client actions receive two error codes**, even with the same HTTP status ([4.4](4.4-api-contract.md#exceptions-and-error-design)). Conversely, failures differing only in wording use **one** code with different `details`. This is the only test; do not merge codes simply because there seem to be too many.

## Reading and searching are different operations

Four read operations — list, search/filter, details, export — are often merged as *"view products,"* despite differing in exactly the expensive places:

| | List | Search / filter | Details | Export |
|---|---|---|---|---|
| Payload | Reduced field set | List fields + match score | Full + relationships | Full + flattened |
| Pagination | Required — state type and limit | Required | No | Batch |
| Sorting | Sortable fields and default | Relevance or field | — | Fixed |
| Permission | May expose more records than details | Same as list | May be stricter than list | Usually strictest |
| Required index | [4.1.2](4.1-design.md#412-database-design) | Different index, possibly full text | Primary key | — |
| Large-data failure | Later pages get slower | Table scan | — | Timeout, memory exhaustion |

Three facts **must be decided in the operation matrix** for every read operation; otherwise clients discover them on real data: **pagination type** (offset or cursor and hard limit), **returned field set** (reduced or full and exact membership), and **default ordering** (without one, pagination is nondeterministic and one record may appear on two pages).

## Self-check

| # | Check | Failure prevented |
|---|---|---|
| 1 | Every use case with ≥ 2 operations has an operation matrix before `Activity flow` | A use case row looks complete while empty inside |
| 2 | All **13 inventory rows** processed, each `yes` or `no, because …` | The list stops at create/update/delete and misses duplicate, import, approval, and history |
| 3 | Every `T<n>` appears in at least one numbered [2.3](2.3-use-case-specs.md) flow | A named operation with no way to run |
| 4 | Every `T<n>` differing in (3) *who calls whom* has a **separate [3.2](3.2-sequence-diagrams.md) sequence diagram** | The *create* diagram stands in for four operations |
| 5 | Every `T<n>` differing in (4) *boundary data* has a **separate [4.4](4.4-api-contract.md) endpoint** | One `POST /product/action` endpoint takes an `action` string |
| 6 | Every `Exceptions` cell traces to a [4.4](4.4-api-contract.md) error code and [6.1](6.1-test-plan.md) case | A failure branch exists only in the specification |
| 7 | Every read operation defines pagination, fields, and default order | Nondeterministic pagination discovered on real data |
| 8 | Every write operation decides soft/hard deletion, history, and event emission | Three people assume three behaviors, none contradicted by documentation |
| 9 | **Count**: matrix rows = resource endpoints + operations declared `no endpoint` | API contract misses endpoints without any document showing red |
| 10 | Operation traceability matrix has no unexplained blanks | One broken stage while seven documents look complete |
