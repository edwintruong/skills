# 0.5 Identifying components — derivation techniques

Almost every section in this document set produces a **list of things**: actors, use cases, classes, processes, stores, states, tables, screens, interfaces, or test cases. A remembered list and a derived list look identical on the page, while the missing row remains invisible in both. This reference explains how to produce those lists so omissions become visible and every retained row proves that it belongs.

Read it before writing any section whose output is a component list. [0.6](0.6-mechanism.md) is its companion: this file decides **what exists**; that file decides **whether the representation of how it works is accurate**.

## The root rule: evidence travels with the element

**Every row in an identification table must trace to its origin.** Exactly four evidence types are valid:

| Type | Written as | Use when |
|---|---|---|
| An upstream item in the document chain | `UC-01 b3` · `FR2` · `BR-CAMP-01` · `1.1.2 N7` · `D2` · `S1` | Always, when the upstream document exists |
| An interview, **named by topic** | `round 3 — reservation expiry` ([0.4](0.4-interview.md)) | Mode B |
| A location in code | `app/api/orders.py:41` | Mode A, while drafting |
| Your own assumption | `**ASSUMPTION** — <assumption> (confirm: <person>)` | Mode B, when nobody can answer yet |

### Evidence and citation are different things

**Evidence** prevents the author from accepting an unproven row. A **citation** lets the reader inspect the source. They overlap for three evidence types but diverge for interviews: readers do not have the recording, so `Q57` is a dangling reference.

- **Question IDs live in `.software-docs.json`**, inside the `interview` object, not in document prose. The `Source` cell contains the topic.
- **An ID never becomes a sentence subject.** Write *“Reservations expire after 60 minutes (round 3 — reservation expiry)”*, not *“`Q63` established the reservation expiry.”*
- **An empty `Source` cell is a defect.** Fill it or write `**TBD** — <missing evidence> (owner: <person>)`.
- **The `Open questions` table uses local numbering `1..n`.** Those numbers are not global IDs and must not be cited across documents.

A fifth source exists in practice: **memory of similar systems**. It produces mostly correct rows, making incorrect rows difficult to detect and missing rows impossible to remember.

Use existing traceability columns: `Source` in [1.1.4](1.1-problem-survey.md#114-functional-requirements) and [2.1](2.1-actors-and-use-cases.md), `Derived from` in [3.1](3.1-analysis-classes.md), `Use case` in [4.5.2](4.5-ui-design.md), and `Derived from analysis class` in [4.1.3](4.1-design.md).

## Derivation tables: keep rejected candidates

Every technique below uses the same working table. It is **not a published document section**; transfer accepted items into the section's existing template.

| Candidate | Evidence | Classification | Keep / reject | Why |
|---|---|---|---|---|
| Delivery address | UC-01 b3, field table | Attribute | Reject | Belongs to `Order` until customers have an address book |
| Reservation | UC-01 b5 | Entity | Keep | Survives across requests and has its own expiry |
| Temporary cart calculation | UC-01 b1 | Transient | Reject | Exists for one request and is never read again |

**Record rejected candidates somewhere.** An undocumented rejection returns next session as a new idea; readers deserve an answer to “why is X absent?”; and a derivation pass that rejects nothing probably did not run.

Record rejections in the main table when possible, in `Open questions` when confirmation is pending, or in unpublished working notes otherwise. Never add a new document section solely for rejected candidates; the required section order remains fixed ([0.1](0.1-visual-style.md#section-order)).

## Bidirectional checks, always

A list closes only after checking both directions: every source produces at least one element, **and** every element traces to at least one source. The forward direction catches omissions; the reverse direction catches unrequested scope.

| Pair | Forward check catches | Reverse check catches | Where |
|---|---|---|---|
| `FR<n>` ↔ use case | Requirement nobody performs | Use case nobody requested | [2.1](2.1-actors-and-use-cases.md#finding-the-complete-set-not-stopping-at-obvious-cases) |
| Function-tree leaf ↔ use case | Omitted function | Use case outside the tree | [2.1](2.1-actors-and-use-cases.md) |
| Use case ↔ DFD process | Use case touching no data | Process nobody invokes | [3.4](3.4-data-flow.md) |
| `<<entity>>` ↔ store | Remembered object with no storage | Store with no class | [3.4](3.4-data-flow.md) |
| `<<entity>>` ↔ table | Class mapping to no table | Table nobody requested | [4.2](4.2-data-model.md) |
| Use case ↔ screen | Use case with no place to execute | Screen nobody needs | [4.5](4.5-ui-design.md) |
| Cross-boundary message ↔ `I<n>` | Call without a contract | Contract nobody invokes | [4.3](4.3-detailed-design.md) |
| Exception flow ↔ test case | Failure branch nobody tests | Test with no requirement | [6.1](6.1-test-plan.md) |

**Counting is a check, not a feeling.** The subsection counts in [3.1](3.1-analysis-classes.md), [3.2](3.2-sequence-diagrams.md), and [3.3](3.3-class-diagrams.md) must match one another and the use case table's row count.

### K1 · Event partitioning

Function lists systematically omit work that **nobody starts by selecting a control**. Begin with events and list the response afterward.

| Type | Question | Common omission |
|---|---|---|
| **External event** | What strikes the system from outside? | Partner webhook · reconciliation file · email reply · cancellation in another channel |
| **Temporal event** | What runs on a schedule, deadline, or period? | Reservation expiry · period close · reminder · expired-data cleanup |
| **State event** | Which internal state triggers other work? | Inventory below threshold · queue over threshold · negative balance |

Write each as `event → system response → information required → result left behind`. One response becomes **one** use case in [2.1](2.1-actors-and-use-cases.md) and **one** top-level process in [3.4](3.4-data-flow.md).

- An event happens outside the system's control; it is not an internal step.
- Temporal events have no actor. Cron belongs in the use case's `Trigger` field.
- In Mode B, K1 becomes an interview group. EventStorming is the workshop form of the same technique.

### K2 · Nouns, the filter, and category inventory

Scan activity flows, [2.3](2.3-use-case-specs.md) field tables, and `BR<n>` rules. Underline noun phrases, then ask:

| Question | If “no” |
|---|---|
| Must the system **remember** it across requests? | Transient—reject |
| Does it have its **own attributes**? | Attribute—reject |
| Does it have **identity**, so two identical instances remain distinct? | Value—reject |
| Is it one concept rather than a synonym? | Merge synonyms and choose one glossary term |
| Is it **inside the box**, not a role outside it? | Actor—move to [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) |

Then sweep Larman's categories: transactions, transaction lines, products or services, roles, places, containers, contained items, memorable events, reference catalogs, ledgers, financial instruments, schedules, rules, and policies.

- Transaction lines are missed most often: `OrderItem`, `PaymentAllocation`, and `StockMovement`.
- A memorable event is an entity whenever someone will ask “when?” or “who did it?”
- Reference catalogs often begin as hard-coded values and become administration requirements later.
- Verbs found during the scan populate the [3.1](3.1-analysis-classes.md) `Responsibilities` column.

### K3 · Responsibility and collaboration (CRC)

Use CRC to decide whether a `<<control>>` should split. Give each class a card with **name · responsibilities · collaborators**.

1. Read the use case flow and assign every step to exactly one card.
2. When work needs another card's data, make that card a collaborator instead of copying its responsibility.
3. Split a card when it has more than seven collaborators or its responsibility requires *and*.

Write the result as verb phrases, not method lists.

### K4 · The CRUD matrix

Rows are `<<entity>>` classes; columns are use cases; cells contain `C`, `R`, `U`, or `D`.

| Entity | UC-01 Place order | UC-02 Approve order | UC-05 Receive stock | UC-07 Report |
|---|---|---|---|---|
| `Order` | C | RU | — | R |
| `Product` | R | — | RU | R |
| `Voucher` | RU | — | — | R |
| `StockMovement` | C | — | C | R |

| Shape | Meaning | Action |
|---|---|---|
| Row without `C` | Unknown data origin | Add an entry, migration, or synchronization use case |
| `R`-only row | Nobody writes it | Declare reference data or add administration use cases |
| Row without `D` or retention | Retained forever by omission | Add lifecycle and retention to [4.2](4.2-data-model.md) |
| Empty column | Use case touches no data | It may be a step incorrectly promoted to a use case |
| Empty row | Nobody uses the entity | Remove surplus analysis or find the missing use case |

The matrix is also a rough authorization map: when two roles touch one entity differently, [1.1.7](1.1-problem-survey.md#117-technical-and-security-constraints) needs a rule.

### K5 · The two multiplicity questions

Ask about each association end independently and numerically:

> How many `OrderItem` instances may one `Order` have at minimum and maximum?
> How many `Order` instances may one `OrderItem` belong to at minimum and maximum?

- Ask minimum and maximum separately.
- When the maximum is `*`, ask whether it can exceed a few dozen; the answer affects indexes and pagination.
- A `0..1` end raises a lifecycle question: when is it empty and who fills it?
- Decide composition by asking whether the child retains meaning after the parent is deleted.

### K6 · Decision tables and hit policy

Use a decision table whenever two or more conditions jointly determine an outcome.

| # | Age ≥ 20 | Income ≥ 8m | DTI < 60% | Result |
|---|---|---|---|---|
| 1 | N | – | – | Reject `under_age` |
| 2 | Y | N | – | Reject `low_income` |
| 3 | Y | Y | N | Manual review |
| 4 | Y | Y | Y | Approve |

- For `n` binary conditions, account for all `2ⁿ` combinations.
- Record impossible combinations and explain why.
- State the DMN hit policy: `U` unique, `F` first, `P` priority, or `C` collect.
- Express boundaries with `<` and `≤`, not vague prose.
- Every row produces at least one test case, plus cases on both sides of every boundary.

### K7 · Finding states

Collect state candidates from status columns or enums, adjectives and completed verbs in flows, every use case postcondition, and every numbered exception flow. Build a **state × event grid** and fill both valid and invalid cells. A blank cell asks what happens when that event arrives in that state.

An entity merits a state machine when it has at least three states or a transition with a side effect that must not run twice.

### K8 · Deriving interfaces from cross-boundary messages

For each [3.2](3.2-sequence-diagrams.md) sequence diagram, retain messages crossing a team or process boundary.

1. Turn each retained message into an `I<n>` row in [4.3.5](4.3-detailed-design.md#interface-inventory-the-contract-index).
2. Group rows by **resource**, not screen.
3. Turn every `I<n>` into an endpoint in [4.4](4.4-api-contract.md), and require every endpoint to have an invoking `I<n>`.
4. Derive payloads from use case field tables, not database tables.

**An arrow whose payload cannot be written reveals missing data.**

### K9 · From classes to tables

Default to one `<<entity>>` per table and derive the rest from multiplicity:

| Multiplicity | Mapping | Accompanying decision |
|---|---|---|
| `1` — `0..1` | Foreign key on optional side, or merge | Merge when always read together; split when lifecycles differ |
| `1` — `0..*` / `1..*` | Foreign key on many side | Derive `ON DELETE` from composition vs. association |
| `0..*` — `0..*` | **Join table** | If it has attributes, it was an entity; return to [3.1](3.1-analysis-classes.md) |
| Closed value set | Enum or reference table | Use a table when administrators add values or values have attributes |

- Normalize to 3NF first; denormalize only after measurement.
- A repeating attribute becomes a table, not `item_1`, `item_2`.
- Time-effective data needs `effective_from` and `effective_to` from the start.
- A business key as primary key is a one-way door; record it in [4.1](4.1-design.md#one-way-doors).

### K10 · Reviewing vague language

| Signal | Hidden issue | Rewrite as |
|---|---|---|
| *fast · easy · friendly · stable · optimal · flexible* | No threshold | Number + load condition + measurement method |
| *process · manage · support · related to* | Empty verb | Observable verb: *create*, *reject*, *send*, *display* |
| *and · or · simultaneously* in one row | Two requirements | Two separately identified rows |
| *valid · complete · appropriate · accurate* | Missing rule | Cite `BR<n>` or use `<` / `≤` |
| *if needed · when possible* | Deferred decision | Owned and dated `**TBD**` |
| Generic *user* | Unknown actor | Exact role from [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) |
| Bare plural | Unknown quantity or ownership | Explicit quantifier and owner |
| *etc.* or *similar cases* | Open-ended list | Enumerate all items or state the generation rule |

One test applies to every row: **can you write a test case from it?**

### K11 · Operation inventory

For every managed business object, sweep thirteen operations and mark each `yes` or `no, because …`: list, search/filter, detail, create, update, change state, delete, restore, clone, bulk action, import/export, approve, and change history.

- An open question cannot find something nobody has mentioned; use the inventory.
- `no, because …` is valid and explicit; a blank cell looks like nobody asked.
- Close by counting: operation-matrix rows = resource endpoints + declared operations intentionally lacking an endpoint.

See [0.7](0.7-operations.md) for the complete method and split test.

## Mode A: extracting components from code

Code reveals *what exists*, not *why*. Record `path:line` while drafting.

| Component | Read from | Pitfall |
|---|---|---|
| Actor | Authentication middleware, permissions, callers | Code roles are permissions, not necessarily business roles |
| Use case | Handlers grouped by goal, not route | Four CRUD routes may serve one use case; one route may serve two |
| Scheduled use case | Cron, scheduler, queue consumer | This group has no route and is often absent |
| `<<boundary>>` | Routes, UI components, external clients | An outbound client is a boundary even without a screen |
| `<<control>>` | Service/use-case layer, transaction boundary | A filename proves nothing; follow the call chain |
| `<<entity>>` · table | ORM model and **migration** | Migration is authoritative; the model may have drifted |
| State | Enum, `status`, string comparisons | A literal in an `if` is an implicit state |
| Business rule | Condition, validator, threshold | An `if` is a **hypothesis** until confirmed |
| `NFR<n>` · constraint | Timeout, retry, index, SLO, load limit | A library default is not a commitment |
| Arrow mechanism | Actual call site | Awaiting publication does not create a synchronous dependency on the consumer |

Three Mode A rules:

- **Record the source while writing**, not during review.
- **Intent cannot be read from code.** Ask whether each derived rule is intended behavior or a defect.
- **Things absent from code still appear.** A discussed but unimplemented use case becomes `**TBD**`.

## Mode B: every element has an answer behind it

Without code, interview answers provide evidence. Every list element points to an [0.4](0.4-interview.md) question **by topic**, or carries an `**ASSUMPTION**` naming the person who must confirm it. An unanswered candidate becomes **a question for the next round**, not a silent table row.

K1 events, K2's category list, and empty cells in the K4 CRUD matrix can run before anyone answers. A half-complete table produces better questions than an entirely open-ended interview.

## Self-check before publishing a list

| # | Check | Fails when |
|---|---|---|
| 1 | Every row has one of the four valid evidence types | A row comes from memory |
| 2 | Every required discovery pass ran and was recorded | The list stops at obvious items |
| 3 | At least one candidate was rejected with a reason | Derivation was recalled, not performed |
| 4 | Both directions were checked and both unmatched sets are empty | Omission or unrequested scope |
| 5 | Counts match the upstream document | An item silently disappears between documents |
| 6 | Unknown facts carry owned `**TBD**`; author-selected facts carry `**ASSUMPTION**` | A guess reads as a decision |
| 7 | No row belongs in a different table | Container as actor; attribute as entity; step as use case |
