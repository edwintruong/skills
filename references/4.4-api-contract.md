# 4.4 API contracts

An API contract exists so the producer and the consumer can build in parallel and meet in the middle without a meeting. Everything in it is written from the consumer's point of view: what do I send, what do I get back, what happens when it goes wrong.

Four flavours share one document shape: synchronous HTTP, asynchronous events, model inference, and batch/file handoffs. Read the section that matches.

## Document template

```markdown
# <Service or interface> — API contract

<metadata table, plus:>
| **Producer** | <team / service> |
| **Consumers** | <teams / services> |
| **Base URL** | `https://…` (per environment) |
| **Contract version** | v1.3 |

<plain-language summary paragraph>

## 4.4.1 Scope
## 4.4.2 Conventions
## 4.4.3 Authentication
## 4.4.4 Endpoint inventory by group
<one table listing EVERY service endpoint, grouped by resource>
<one operation matrix per group>

## 4.4.5 Product group (I3–I8)
<one H3 per endpoint in this group>

## 4.4.6 Order group (I9–I14)
<repeat for every group — one separately numbered H2 per group>

## 4.4.<n> Errors
<envelope + service-wide error code catalog>

## 4.4.<n> Rate limits and timeouts
## 4.4.<n> Use case ↔ API traceability
## Changelog
```

**A group is a separately numbered H2; endpoints are unnumbered H3 headings** ([0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers)), just as subsystems occupy H2 in [3.2](3.2-sequence-diagrams.md). Above roughly five groups, or when a group needs two levels beneath it, make the group a **separate file** (`4.4.5-product-api.md`) rather than demoting endpoints to H4 — H4 does not appear in the page contents. The `Errors` number therefore depends on the number of groups and uses `<n>`. For a service with one group, omit the group tier: `## 4.4.5 Endpoints`, followed directly by H3 endpoints.

`Conventions` covers what would otherwise be repeated in every endpoint: date format (ISO 8601, UTC), naming (`snake_case` vs `camelCase`), pagination style, money representation, ID format, null versus omitted-field semantics, idempotency headers. Ten lines here removes a hundred lines of repetition below, and it is where most cross-team disagreements actually live.

Where an OpenAPI or protobuf file exists, it is the machine-readable truth and this document links to it. The document still exists, because a schema file cannot explain *when* to call something, what the states mean, or what to do when it fails.

## API groups and endpoint inventory

An API document may contain thirty H3 sections in one column, while its first reader is not looking for one endpoint — they ask *"what can this service do with products?"* Section 4.4.4 answers that question. Its more valuable second purpose is that **a resource-grouped inventory exposes a missing endpoint as an empty row**, while a flat list cannot.

**Group by business resource, not screen or team.** Three screens reading one order form one `Orders` group, not three groups ([0.5 K8](0.5-derivation.md#k8-deriving-interfaces-from-cross-boundary-messages)); grouping by screen produces `/checkout-page-data` and endpoints that cannot be reused by a second screen.

| Group | Endpoint | Operation | Use case | `I<n>` | Auth · scope | Idempotency | Notes |
|---|---|---|---|---|---|---|---|
| Products | `GET /products` | T1 List | UC-A03 | I1 | `product:read` | — | Cursor pagination |
| Products | `GET /products/{id}` | T2 View details | UC-A03 | I2 | `product:read` | — | Includes variants |
| Products | `POST /products` | T3 Create | UC-A03 | I3 | `product:write` | `Idempotency-Key`, 24h | |
| Products | `PUT /products/{id}` | T4 Update | UC-A03 | I4 | `product:write` | `If-Match` required | Full replacement |
| Products | `POST /products/{id}/status` | T5 Change state | UC-A03 | I5 | `product:publish` | — | Transitions follow [3.5](3.5-state-machines.md) |
| Products | `DELETE /products/{id}` | T6 Soft delete | UC-A03 | I6 | `product:write` | — | Blocked while referenced |
| Products | `POST /products/{id}/restore` | T8 Restore | UC-A03 | I7 | `product:write` | — | |
| Products | `POST /products/import` | T11 Import file | UC-A05 | I8 | `product:import` | `Idempotency-Key` | Partial success |

- **This is a complete table, not a summary.** Every row has an H3 below, and every H3 has a row here; count in both directions before publishing.
- **`Operation` connects this table to [2.3](2.3-use-case-specs.md)** and makes the next section's count possible.
- **`I<n>` connects to [4.3.5](4.3-detailed-design.md#interface-inventory-the-contract-index)**: a row without `I<n>` is an endpoint called by no [3.2](3.2-sequence-diagrams.md) arrow — either the diagram is incomplete or the contract is unnecessary. Resolve both cases; do not leave the cell blank.
- **Keep all four interface types in one table when the service has them** — synchronous HTTP · events · model inference · batch files — with a `Type` column. Isolating events in a corner prevents anyone from reviewing them.

## Endpoint completeness: operation matrices

The inventory answers *"what exists?"* This matrix answers the more valuable question: **"what is missing?"** It is the only coverage pass in the set that exposes a contract missing three endpoints when no other document shows an error.

Create one table per group with the thirteen fixed rows from [0.7](0.7-operations.md#the-thirteen-operation-inventory), answering every row `yes` or `no, because …`:

| Operation | Endpoint | Yes / no |
|---|---|---|
| List | `GET /products` | yes |
| Search and filter | `GET /products?q=&status=` | yes — same endpoint, query parameters |
| View details | `GET /products/{id}` | yes |
| Create | `POST /products` | yes |
| Update | `PUT /products/{id}` | yes |
| Change state | `POST /products/{id}/status` | yes — separate because permission differs |
| Delete | `DELETE /products/{id}` | yes — soft delete |
| Restore | `POST /products/{id}/restore` | yes |
| Duplicate | — | **no** — no requirement yet, `**TBD**` (owner: PM) |
| Bulk | — | no — low operation volume, decision dated 2026-08-10 |
| Import / Export | `POST /products/import` | yes — export missing, `**TBD**` |
| Approve | — | no — this process has no approval step |
| View history | `GET /products/{id}/history` | yes |

- **`No, because …` is valid and must be explicit.** A blank cannot be distinguished from a question nobody asked ([0.5](0.5-derivation.md#derivation-tables-keep-rejected-candidates)).
- **Count in both directions**: `yes` rows = rows for that group in inventory 4.4.4 = `T<n>` operations with `I<n>` in the [operation matrix](2.3-use-case-specs.md). Any mismatch identifies an unreachable operation or unused endpoint.
- **State explicitly when one endpoint serves two operations** — *search* and *list* sharing `GET /products` is normal; *create* and *update* sharing one `POST` is not, because they have different payloads, postconditions, and error sets ([0.7](0.7-operations.md#the-split-test-when-an-operation-stands-alone)).
- **`POST /products/action` with an `action` string is a false endpoint**: it combines five contracts, obscuring fields, errors, and permissions. Split by operation.

## Endpoint sections

**The endpoint list is a consequence of drawn arrows**, not a list invented from database tables: every cross-boundary [3.2](3.2-sequence-diagrams.md) message becomes an `I<n>` in [4.3.5](4.3-detailed-design.md#interface-inventory-the-contract-index), then every `I<n>` becomes a section here. Every section here must have an `I<n>` calling it or the contract has no consumer ([0.5 K8](0.5-derivation.md#k8-deriving-interfaces-from-cross-boundary-messages)).

One H3 per endpoint, inside its group's H2. **All eight blocks are mandatory**; a block that genuinely does not apply is written as one line saying so (`No path parameters.`), never silently dropped — an absent block reads as "not thought about" and the consumer has to ask.

````markdown
### POST /orders

Converts a cart into a paid-pending order. Call it once the customer has confirmed
the address; it reserves stock, so do not call it to preview a total — use
`POST /carts/{id}/quote` for that.

| | |
|---|---|
| **Operation · use case** | UC-U01.T4 Checkout — [2.3](2.3-use-case-specs.md) |
| **Interface** | I9 — [4.3.5](4.3-detailed-design.md#interface-inventory-the-contract-index) · [3.2](3.2-sequence-diagrams.md) diagram UC-U01 |
| **Auth** | Bearer token, scope `orders:write` |
| **Idempotency** | Required — `Idempotency-Key` header, 24h window |
| **Timeout** | 5s; safe to retry on 5xx and network failure |

**Path and query parameters**

| Name | In | Type | Required | Constraint | Description | On invalid |
|---|---|---|---|---|---|---|
| `dry_run` | query | boolean | No | `true` \| `false` | Validates and prices without reserving stock. Default `false` | `400 invalid_parameter` |

**Request body**

| Field | Type | Required | Constraint | Description | On invalid |
|---|---|---|---|---|---|
| `cart_id` | string (uuid) | Yes | uuid v4; cart belongs to caller and is not converted | Cart to convert | `404 cart_not_found` · `403 cart_not_owned` · `409 cart_already_converted` |
| `shipping.address_id` | string (uuid) | Yes | One of the caller's saved addresses | One of the caller's saved addresses | `422 address_unknown` |
| `shipping.note` | string ≤ 200 | No | ≤ 200 characters, no line breaks | Free text shown to the courier. Omitted and `null` are equivalent | `400 validation_failed`, `details.field` |
| `voucher_codes` | string[] | No | 0–5 items; each matches `^[A-Z0-9]{4,16}$`; case-insensitive | Unknown or expired codes fail the whole request; an empty array is the same as omitting it | `422 voucher_invalid`, `details.code` |

```json
{
  "cart_id": "8f1c2f4e-…",
  "shipping": { "address_id": "b21a-…", "note": "Call before delivery" },
  "voucher_codes": ["SUMMER10"]
}
```

**Response `201 Created`**

| Field | Type | Always | Unit · format | Description |
|---|---|---|---|---|
| `id` | string (uuid) | Yes | uuid v4 | Order ID issued by this service. Stable for the lifetime of the order; the consumer may store it |
| `status` | enum | Yes | `pending_payment` · `paid` · `cancelled` | Order state immediately after creation. New values may be added — see Versioning |
| `total.amount` | integer | Yes | VND, integer | Amount the customer pays after all discounts and delivery fees |
| `total.currency` | string | Yes | ISO 4217 | Always `VND` today |
| `paid_at` | string (date-time) | No | RFC 3339, UTC, second precision | Present only when `status` is `paid`; absent otherwise, never `null` |

```json
{
  "id": "3b90a1c2-…",
  "status": "pending_payment",
  "total": { "amount": 450000, "currency": "VND" }
}
```

**Errors**

| HTTP | `code` | Cause | Consumer should |
|---|---|---|---|
| 401 | `unauthenticated` | Missing or expired token | Refresh and retry once |
| 403 | `cart_not_owned` | Cart belongs to another customer | Do not retry; this is a bug |
| 404 | `cart_not_found` | No such cart, or it expired | Rebuild the cart |
| 409 | `cart_already_converted` | An order exists for this cart | Fetch the existing order via `order_id` in `details`; **do not** retry |
| 409 | `insufficient_stock` | Stock dropped between quote and submit | Show the affected lines from `details.lines` and let the customer amend |
| 422 | `voucher_invalid` | A code is unknown, expired or not applicable | Show `details.code`; resubmit without it |
| 429 | `rate_limited` | Too many requests | Back off using `Retry-After` |
| 503 | `payment_unavailable` | Downstream provider down | Retry with backoff; the order was **not** created |

```json
{ "error": { "code": "insufficient_stock", "message": "2 lines are no longer available",
  "details": { "lines": [{ "sku": "AO-001-RED-M", "requested": 2, "available": 0 }] } } }
```
````

## Writing the field tables

The contract is an interface document: a consumer must never need to read the producer's source to call it correctly. That makes the `Description` column the load-bearing part of the whole document — it is prose, not a restatement of the type.

**One sentence per field**, and the sentence answers whichever of these the field raises. The checklist is from [0.2](0.2-writing-principles.md#completeness-of-an-interface-description):

| Check | The question the sentence must not leave open |
|---|---|
| Identity | What this actually is, beyond a restatement of its name |
| Units | Minor units or major? Percent of what? Seconds or milliseconds? |
| Boundaries | Is the range inclusive? Does "end" mean the last item or the one after? Max length |
| Absence | Is `null` allowed, is an omitted field different from a null one, and what does each mean |
| Ownership | Who sets it — caller, server, or either |
| Invariants | What stays true between calls, that a caller may rely on |
| Failure | What happens if it is wrong: which error code, and is it the whole request or just this field |

Three columns beyond `Description` carry information one sentence cannot, and all three are often omitted:

| Column | Answers | If blank |
|---|---|---|
| `Constraint` | What is accepted, expressed testably — range, length, regex, value set | Frontend and backend invent different validation rules, and users see errors only after submission |
| `Unit · format` | VND or cents, seconds or milliseconds, timezone, standard | Money differs by 100× and timestamps shift timezone; both surface only in reports |
| `On invalid` | Exact error code caused by the field and whether the whole request or only the field fails | Clients parse `message` and break when wording changes |

`On invalid` closes the **exception flow → method exception → error code** chain ([0.7](0.7-operations.md#exceptions-become-error-codes)): a constraint that rejects data without an accompanying error code is an unnamed failure branch.

Rules that keep the tables usable:

- **Enums are listed exhaustively**, inline, and it is stated whether new values may appear. A consumer writing a `switch` needs both facts.
- **Nested objects use dotted paths** (`shipping.address_id`) in the same table rather than a second table, until the nesting is genuinely deep or reused — then give it its own H3 in a shared *Schemas* section and link to it from every field that carries it. Never an H4: the page's contents list collects h2 and h3 only.
- **Arrays say what an empty array means**, and whether order is significant.
- **The response table has an `Always` column**, not `Required`. Consumers write parsers against it, and "sometimes present" is the single most common cause of a client crash. A field that is only present in some states says which states.
- **Never describe a field as "the ID"**. Say which entity it identifies, who issues it, and whether the consumer may store it.

If an endpoint cannot be described completely without explaining how the service works internally, that is a signal about the endpoint rather than the document — the abstraction is leaking and the boundary is in the wrong place. Note it in open questions instead of writing around it.

## Examples

Every endpoint carries at least three: a request, the interesting success response, and **at least one error body**. Error shapes are what consumers get wrong most often, and the one place they will look is here.

- **Examples must be internally consistent with their table** — same field names, plausible domain values, no `"string"` or `"123"` placeholders. Consumers copy these into fixtures, so a wrong example becomes a wrong test that passes.
- **Show the interesting response, not every 2xx.** A `204` needs no body example.
- **Use realistic data in the document's domain** — real-looking SKUs, Vietnamese addresses, actual currency amounts. An example with `"foo"` in it teaches nothing about the field's shape.
- When a response varies by state, show the two that differ most (here: `pending_payment` without `paid_at`, and `paid` with it) rather than one and a sentence.

## Exceptions and error design

Two failures of the same shape are one error; two failures the consumer must handle differently are two errors, even when the status code is the same. That is the whole design rule, and `409 cart_already_converted` versus `409 insufficient_stock` above is what it looks like — same code, opposite recovery.

**One envelope for the whole service**, shown once at the top of the Errors section:

```json
{ "error": { "code": "cart_already_converted", "message": "Cart has an order already", "details": {} } }
```

Then one table listing every code the service emits, with the column that prevents incidents:

| HTTP | `code` | Meaning | Retryable | Consumer should |
|---|---|---|---|---|
| 409 | `cart_already_converted` | An order exists for this cart | No | Fetch the existing order, do not retry |
| 429 | `rate_limited` | Too many requests | Yes, after `Retry-After` | Back off |
| 503 | `payment_unavailable` | Provider down | Yes, with backoff | Nothing was created; safe to retry |

Six rules that decide which exception is which:

1. **A business failure is never a `200`.** An order that could not be created returning `200 {"success": false}` forces every consumer to write two error paths, and half of them will forget the second. Reserve 2xx for "the thing you asked for happened".
2. **`400` is a malformed request; `422` is a well-formed request the domain refuses.** A missing required field is `400`; an expired voucher is `422`. Consumers route the first to a bug report and the second to the user.
3. **`404` versus `403` is an information-disclosure decision**, not a style choice. Returning `404` for a resource that exists but is not yours hides its existence; returning `403` confirms it. Pick one, state it in `Conventions`, and apply it everywhere.
4. **`409` means the state moved under you.** It always carries enough in `details` for the consumer to recover without a second call — the existing order ID, the lines that went out of stock.
5. **Every code is marked retryable or terminal.** That one distinction is what stops a retry storm during an outage, and it is the field most often missing.
6. **Partial success needs its own shape.** A batch endpoint where three of five items fail is not a `200` and not a `400`; decide between all-or-nothing and a per-item result array, say which, and never leave it to the consumer to discover.

Validation errors get one more thing: **which field failed**, machine-readably, in `details` — not only in `message`. A form that has to regex the human-readable string to highlight a field is a contract that was written for a log reader rather than a client.

## Service-wide error code catalog

Each endpoint's error table answers *"what can happen when I call this?"* This catalog answers *"which codes does this service emit?"* It serves different readers: endpoint integrators read the local table, while authors of shared error handling and user-facing translations read this catalog.

**Name error codes `<object>_<what_happened>`**, in `snake_case` and without numbers: `sku_duplicated`, `cart_already_converted`, `product_referenced`. Three naming rules make codes reusable without ambiguity:

- **An error code is an identifier, not a message.** It does not change when wording changes, is never translated, and is never reused for a different meaning.
- **Service-wide codes use general names** (`unauthenticated`, `rate_limited`, `validation_failed`); object-specific codes name the object. A bare `not_found` forces clients to guess *what* was not found.
- **A new code is a breaking change** when consumers must handle it differently — see Versioning.

| `code` | HTTP | Meaning | Internal exception | Emitted by | Retryable | Consumer action |
|---|---|---|---|---|---|---|
| `unauthenticated` | 401 | Token missing or expired | `AuthMissing` | all endpoints | Yes, after token refresh | Refresh and retry once |
| `forbidden` | 403 | Authenticated but unauthorized | `PermissionDenied` | all endpoints | No | Hide the action from the UI |
| `validation_failed` | 400 | Malformed request | `ValidationError` | all write endpoints | No | Read `details.fields` and highlight the corresponding fields |
| `sku_duplicated` | 409 | SKU already exists | `SkuDuplicated` | `POST /products` | No | Show the error at SKU and suggest an available code |
| `product_referenced` | 409 | Referenced by open orders | `ProductReferenced` | `DELETE /products/{id}` | No | List `details.orders` and suggest discontinuing instead of deleting |
| `stale_version` | 409 | Record changed by another user | `StaleVersion` | `PUT /products/{id}` | Yes, after reload | Reload, let the user compare, then resubmit |
| `rate_limited` | 429 | Too many requests | — | all endpoints | Yes, per `Retry-After` | Back off according to `Retry-After` |

- **`Internal exception` links back to [4.1.3](4.1-design.md#413-detailed-class-design)** and verifies continuity: every exception name in the method table must have exactly one row here. An exception without an error code leaks outward as `500`.
- **`Emitted by` must be specific.** *"Anywhere"* indicates an overly general code that clients must handle at every call site.
- **`500` has no business error code.** It is a server failure carrying `request_id` for logs and never exposes internal details. A `500` listed as a *normal* endpoint outcome is an undesigned branch.
- **User-facing messages do not belong here** — [4.5](4.5-ui-design.md) defines one sentence per code in user language. Response `message` is for developers reading logs, not direct UI display.

## Use case ↔ API traceability

One table at the end of the document detects three defects invisible elsewhere: unreachable operations · endpoints nobody needs · untested failure branches.

| Operation | [3.2](3.2-sequence-diagrams.md) diagram | [4.1.3](4.1-design.md#413-detailed-class-design) method | Table written | Endpoint | Error codes | Test cases |
|---|---|---|---|---|---|---|
| UC-A03.T3 Create | UC-A03 *Create* | `ProductService.create` | `product` C | `POST /products` | `sku_duplicated`, `validation_failed` | TC-PRD-01…03 |
| UC-A03.T6 Delete | UC-A03 *Delete* | `ProductService.softDelete` | `product` U | `DELETE /products/{id}` | `product_referenced` | TC-PRD-11, 12 |

Run the check in both directions: every [2.3](2.3-use-case-specs.md) `T<n>` has a row here (missing means no invocation path), and every endpoint in inventory 4.4.4 appears in at least one row (missing means no consumer). A blank `Error codes` cell leaves failure handling to client guesses; a blank `Test cases` cell means nobody knows whether the path works. The complete table and its seven expanded stages are in [0.7](0.7-operations.md#the-seven-stage-chain-for-every-operation).

## Events

Asynchronous contracts need everything the HTTP ones need, plus what a queue introduces:

```markdown
### `order.created`

| | |
|---|---|
| **Topic** | `shop.orders.v1` |
| **Key** | `order_id` |
| **Emitted when** | An order row is committed |
| **Delivery** | At-least-once — consumers **MUST** be idempotent |
| **Ordering** | Guaranteed per key only |
| **Retention** | 7 days |

<payload table + example>
```

State the emission trigger precisely ("after commit", not "when an order is created") — a consumer that reads back and finds nothing is almost always hitting a before-commit emission. Say what happens on repeated delivery, since at-least-once is the default reality and pretending otherwise pushes the problem downstream silently.

## Model inference contracts

An inference endpoint is an HTTP contract plus the properties that make ML different, and consumers plan for these badly when they are undocumented:

| Property | Why it belongs in the contract |
|---|---|
| Model name and version | Output changes with version; consumers need it in their logs |
| Input constraints | Max tokens, image dimensions, supported languages, required preprocessing |
| Output schema | Including score ranges and whether scores are comparable across calls |
| Latency | p50 and p95, not an average — tail latency drives the caller's timeout |
| Determinism | Whether the same input yields the same output, and what varies it |
| Confidence handling | What the consumer **SHOULD** do below a threshold — fall back, escalate, caveat |
| Failure modes | Timeouts, empty results, refusals, and the safe default for each |
| Cost | Per-call or per-token, when consumers control call volume |

Add a short `Quality expectations` note: what the model is good at, what it is known to be weak at, and what it **MUST NOT** be relied upon for. FE and BE engineers integrating a model rarely read the eval report, and this is the one place they will look.

## Batch and file handoffs

Common between BE and Data, and usually the least documented interface in a system:

| Property | Example |
|---|---|
| Location | `s3://bucket/exports/orders/dt=YYYY-MM-DD/` |
| Format | Parquet, snappy, one file per 100k rows |
| Schema | Link to the data dictionary; column order is not guaranteed |
| Schedule | Daily 02:00 UTC, complete by 03:00 UTC |
| Completeness marker | `_SUCCESS` file — consumers **MUST NOT** read a partition without it |
| Late data | Up to 3 days; partitions may be rewritten |
| Backfill | How to request one, and how consumers detect it |

The completeness marker and the late-data policy are what separate a working pipeline from one that silently produces wrong numbers on some days.

## Versioning and compatibility

State the compatibility promise once, near the top:

- Additive changes (new optional field, new endpoint, new enum value in a field documented as extensible) ship without a version bump. Consumers **MUST** ignore unknown fields.
- Breaking changes (removing or renaming a field, narrowing a type, changing semantics, adding a required field, **adding a new error code a consumer must handle**) require a new version, a migration window, and a `Deprecated` note with a removal date on the old one.
- Every changelog entry is tagged `added` / `changed` / `deprecated` / `removed`, with the date. Consumers read this table before every integration, and it is the only reliable answer to "did something change on your side?".

## Self-check before publishing

| # | Check | Fails when |
|---|---|---|
| 1 | Endpoints are grouped by **resource**, with one numbered H2 per group | A flat list of thirty sections where missing endpoints are invisible |
| 2 | **Count both directions**: every inventory row in 4.4.4 has an H3, and every H3 has a row | The contract disagrees with its own contents |
| 3 | Every group has a **13-row operation matrix**, each row `yes` or `no, because …` | Missing *restore*, *duplicate*, *import/export*, or *history* — operations that change architecture when found late |
| 4 | Every endpoint has an `I<n>` and operation ID `T<n>` | An endpoint invented from database tables instead of a drawn arrow |
| 5 | Every field has a type, testable constraint, unit/format, meaning, and error code | Frontend and backend invent different validation rules |
| 6 | Response tables use `Always`, not `Required`, and state exactly which states include conditional fields | A client crashes on a field that is "sometimes present" |
| 7 | Every endpoint has at least one request example, successful response, and **error body** | Integrators guess the shape they encounter most often |
| 8 | Every error code appears in the service-wide catalog with internal exception and retryability | Retry storms during incidents and inconsistent client behavior |
| 9 | Every exception in [4.1.3](4.1-design.md#413-detailed-class-design) maps to exactly one error code here | A failure branch leaks out as `500` |
| 10 | The use case ↔ API traceability table has no unexplained blanks | An unreachable operation or untested failure branch |
| 11 | Read endpoints define pagination, default order, and returned field set | Nondeterministic pagination shows a record on two pages |
| 12 | Write endpoints define idempotency and concurrency conditions (`If-Match`, version) | One retry creates two records, or concurrent edits overwrite silently |

## Common mistakes

| Mistake | Instead |
|---|---|
| One flat list of all endpoints | Group by resource, with one H2 and operation matrix per group |
| `POST /products/action` with an `action` string | One endpoint per operation, each with its own payload, permission, and error set |
| Create and update share an endpoint | Different payloads, postconditions, and exceptions ⇒ two endpoints |
| Error table contains only `400` and `500` | Outcomes requiring different client behavior get different codes, even with the same HTTP status |
| Bare `code: "error"` or `code: "not_found"` | `<object>_<what_happened>`, never reused for another meaning |
| `Description` repeats the data type | State *what it means*, plus unit, constraint, and error code |
| Events isolated where nobody reviews them | Put them in the same inventory as HTTP, with a `Type` column |
