# 0.6 Drawing the mechanism accurately — mechanism fidelity

[0.3](0.3-diagramming.md) chooses the tool and [0.1](0.1-visual-style.md#diagram-captions) the caption; this file decides whether the picture is **true**. Every box and every arrow is an assertion about how the system actually behaves, and the reader has no other source — they will build against the drawing, size a timeout from it, and promise a partner a delivery guarantee it never had.

A wrong sentence in prose gets challenged. A wrong arrow gets implemented, because a diagram has nowhere to write *"perhaps"* and therefore reads as certain at every altitude.

Read this before drawing anything that shows behavior: activity diagrams ([2.3](2.3-use-case-specs.md)), sequences ([3.2](3.2-sequence-diagrams.md)), data flows ([3.4](3.4-data-flow.md)), state machines ([3.5](3.5-state-machines.md)), containers ([4.1.1](4.1-design.md)), or screen transitions ([4.5.3](4.5-ui-design.md)).

## The five mechanism questions

Before drawing a behavioral arrow, answer five questions. If any answer is unavailable, the **mechanism is unknown** — put `**TBD**` in the caption and do not draw a guess; a guessed arrow is the hardest defect to detect in the entire documentation set.

| # | Question | If answered incorrectly, the reader | Show with |
|---|---|---|---|
| 1 | **Who initiates?** Is the receiver called, or does it fetch? | Builds a webhook while the other side waits to be polled | Arrow direction, plus a `poll 30s` label when fetching |
| 2 | **Does the caller wait?** If not, is it fire-and-forget, callback/webhook, or polling? | Sets a timeout on something that never replies | `->>` waits · `--)` does not wait · a second arrow for the response path |
| 3 | **What actually crosses?** All data, or only an identifier? | Misses one lookup and discovers it in week six | Short payload labels: `{order_id}` differs fundamentally from `{order, items[]}` |
| 4 | **Where and when does it become permanent?** Is commit before or after event publication? | Reads back and finds nothing — the classic publish-before-commit bug | `Note over`: *"publish after commit"*, or a store-write arrow first |
| 5 | **What happens on failure?** Timeout, retry, duplicate delivery, reordering, partial success | Creates a retry storm or two orders from one click | `alt` branches, `Note` for timeout/retry, and `Idempotency-Key` on the arrow |

The first three questions determine the arrow's **shape**; the last two determine **what must be written beside it**. A diagram that answers only the first three describes structure, not mechanism.

## What each notation asserts

Drawing an edge asserts a sentence. If that sentence cannot be spoken plainly, do not draw the edge — or draw it and write the sentence immediately in the caption.

| Notation | An edge asserts | It **does not** assert | Common misrepresentation |
|---|---|---|---|
| Sequence `->>` | A real call occurs in that direction and the caller **waits** | Protocol, latency, or call count | A poll or queue publish |
| Sequence `--)` | The sender continues immediately; any result returns by another path | That the receiver has received it | A synchronous call drawn for convenience |
| Sequence `alt` / `loop` | The branch or loop **exists in the flow**, with a guard matching [2.3](2.3-use-case-specs.md) | That the loop has an upper bound | An N-way fan-out drawn as one arrow |
| DFD flow | **Data** moves between two elements | Order, condition, or timing ([3.4](3.4-data-flow.md)) | An activity diagram disguised as a DFD |
| DFD store `[()]` | Data **rests** between interactions and has writers and readers | That it is one physical database | A transformation drawn as a store |
| ERD edge | A real foreign key exists, with multiplicity at both ends | That every use case uses the relationship | One-ended multiplicity leading to the wrong table ([3.3](3.3-class-diagrams.md)) |
| State transition | An **event** changes a state-column value under a guard | That side effects run exactly once ([3.5](3.5-state-machines.md)) | A processing step drawn as a state |
| Container arrow | A runtime dependency uses a named protocol | That it is synchronous | A job reading a shared database drawn as an API call |
| Screen-transition edge | A **user action** leads to another screen | That the destination screen can fetch all required data ([4.5](4.5-ui-design.md)) | A mode of one screen drawn as a separate screen |
| Class association | One side holds a reference to the other | That calls occur between them ([3.3](3.3-class-diagrams.md)) | An association never used in [3.2](3.2-sequence-diagrams.md) |

## Read-back

Checking a picture by looking at it again is ineffective: the eye sees what the hand just drew. The executable check is to **read it back as sentences**, then compare every sentence with evidence ([0.5](0.5-derivation.md#the-root-rule-evidence-travels-with-the-element)):

1. Number every edge.
2. Rewrite each edge as **one complete subject–verb–object sentence**, explicitly stating whether the caller waits.
3. Record evidence for each sentence: `path:line` in mode A, or `Q<n>` / use case step in mode B.
4. If no evidence can be written, either the diagram is wrong or the system is undecided — distinguish those cases instead of leaving them ambiguous.

For example, the same three-arrow picture reads back into two different sets of statements:

```text
Diagram says         : "FE calls BE and waits; BE calls AI and waits; BE returns the result."
Code says            : FE calls BE and waits (api/chat.py:88)
                       BE writes a queue item and immediately returns 202 (api/chat.py:104)
                       A worker calls AI and stores the result (workers/score.py:31)
                       FE polls every 2s until a result exists (web/useScore.ts:44)
```

The first picture does not merely omit detail — it is **semantically wrong**. It promises a result within the same call, so frontend adds a synchronous spinner, QA writes synchronous cases, and backend timeout sizing starts from a value that does not exist.

Mode A: any mismatch is **a finding** and must be classified — correct the document when it is wrong; report the code when it is wrong, while the code remains the current truth. Mode B: a mismatch means two people imagine different systems, so it becomes a question in the next interview round rather than a detail to choose silently.

## Ten signs of an inaccurate mechanism

| # | Diagram symptom | Likely real mechanism | Correction |
|---|---|---|---|
| 1 | An arrow from our system to an external system has no cadence | We **poll** periodically; the other side does not push | Label `poll 30s`, or reverse direction for a webhook |
| 2 | A consumer is drawn as a call from the producer | A queue sits between them, introducing delay, replay, and possible reordering | Draw a queue `[[]]` and state `at-least-once` |
| 3 | Every read reaches the store | A cache serves some reads and may be stale | Draw the cache as a box; state TTL and invalidator |
| 4 | A bidirectional arrow | Two different mechanisms are merged into one line | Draw two arrows, each with a label |
| 5 | One arrow represents repeated calls | N+1: one call per item | Use `loop` with an upper bound, or state that calls are batched |
| 6 | An event appears beside a write with no before/after statement | Publish before commit — consumers read back and find nothing | Add `Note`: *"publish after commit"* |
| 7 | A scheduled job is drawn as an actor outside the box | The job is **inside**; *time* is the external trigger | Use the use case's `Trigger` field ([2.1](2.1-actors-and-use-cases.md#what-is-often-mistaken-for-an-actor)) |
| 8 | Containers and use cases share one picture | Two C4 levels are mixed | Split into two diagrams, one level each |
| 9 | One box both transforms and stores | Process and store are separate elements | Split them; stores do not talk directly to stores ([3.4](3.4-data-flow.md)) |
| 10 | Two services share a database but are drawn calling each other | No call exists; they are coupled through the schema | Draw both pointing to the store and state who may write |

Symptoms 1, 2, and 3 share one cause: **the picture shows the system the author wants, not the system that exists**. One read-back question catches all three: *"who calls this function, and on which line?"*

## One diagram, one altitude

Every diagram operates at one altitude, stated in the caption's first sentence. Mixing levels is a mechanism error, not an aesthetic one: readers can no longer tell whether a box is a business capability, a process, or an operating-system process.

| Altitude | A box is | An arrow is | Used in |
|---|---|---|---|
| Business | Capability or work step | Handoff between people | [1.1.3](1.1-problem-survey.md#113-business-process-diagram), [2.3](2.3-use-case-specs.md) |
| Analysis | `<<boundary>>`/`<<control>>`/`<<entity>>` class | Delegated responsibility | [3.1](3.1-analysis-classes.md)–[3.3](3.3-class-diagrams.md) |
| Data | Process or store | Moving data | [3.4](3.4-data-flow.md) |
| Deployment | Running container | Protocol, timeout, and retry behavior | [4.1.1](4.1-design.md), [4.3](4.3-detailed-design.md) |

Drawing the same use case at several altitudes is normal and useful — **the same step numbers at different altitudes** let readers compare the diagrams and spot divergence ([4.3](4.3-detailed-design.md#deriving-interaction-design-from-use-case-specifications)). One *diagram* at two altitudes is not acceptable.

## What a picture cannot carry

Six facts have no adequate notation, so put them in the caption or a `Note`, with at most three or four notes per diagram before the notes become the diagram:

| Fact | Required statement | If omitted |
|---|---|---|
| Delivery guarantee | *"at-least-once; consumer must be idempotent"* | Teams assume different guarantees and one charges twice |
| Ordering guarantee | *"ordered only within `order_id`"* | Readers assume global ordering |
| Commit point | *"publish the event after commit"* | Consumers read back and find no data |
| Time window | *"400 ms timeout, 1 retry"* — derived from the [4.3](4.3-detailed-design.md#performance-budget) budget | Timeouts are chosen independently and create retry storms |
| Clock and timezone | *"deadlines use Vietnam time; data is stored in UTC"* | Near-deadline cases shift by a day |
| Deliberate omission | *"the diagram shows only the happy path; authentication and logging are omitted"* | Readers assume they were forgotten and add them independently |

## Mode A: every arrow has an address

A diagram reconstructed from code is trustworthy only when every edge has a supporting code location. For each edge, find the **call site**, identify **what it crosses** (HTTP client · queue publish · in-process call · database query), and only then choose the arrow shape.

The two most common misreadings both produce pictures that *look correct*:

- **`await` does not mean synchronous with the ultimate receiver.** `await queue.publish(...)` waits only for the queue write; the consumer runs later, perhaps seconds later and perhaps twice. Drawing `->>` to the consumer promises a mechanism that does not exist.
- **A function call is not a network hop.** Two modules in one process are not two containers; drawing them as deployment-level lifelines invents a boundary, timeout, and failure mode.

Three more facts must be read from code rather than guessed: the **commit point** (where the transaction opens and closes relative to event publication), **retries and timeouts** (library defaults must still be documented as defaults), and the **loop upper bound** (if none exists, the diagram must say so, because an unbounded diagram loop is an unbounded production loop).

## Self-check before publishing a diagram

| # | Check | Failure prevented |
|---|---|---|
| 1 | All five mechanism questions are answered — in the picture, caption, or as `**TBD**` | A guess drawn as fact |
| 2 | Read-back completed: every edge becomes a sentence and every sentence has evidence | The picture was viewed again but never verified |
| 3 | Synchronous and asynchronous behavior use two distinct notations | Readers cannot distinguish *wait* from *do not wait* |
| 4 | No edge combines two mechanisms; no bidirectional arrows | Two agreements merged into one |
| 5 | Queues, caches, and polls each have their own box or label | Delay, replay, and stale data disappear from the design |
| 6 | Commit point and delivery guarantee appear on every event diagram | Consumers read back and find nothing |
| 7 | One diagram uses one altitude, stated in the caption | Two C4 levels in one picture |
| 8 | The caption states deliberate omissions | Readers assume omissions were forgotten and add them independently |
| 9 | Mode A: every edge has `path:line`; code mismatches are reported as findings | A diagram reconstructed from architectural memory |
