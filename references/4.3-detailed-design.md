# 4.3 Detailed design (SDD)

The software design document is the one artifact that has to work for two very different readers at once: a stakeholder deciding whether to fund and accept the work, and four engineering teams who need to build in parallel without blocking each other. It fails in a predictable way — written for engineers it loses the sponsor, written for the sponsor it stops being buildable.

The structure below solves that by **layering rather than diluting**: sections 4.3.1–4.3.2 are readable by anyone and contain no jargon, everything from 4.3.3 on is fully technical, and nothing in the technical half is watered down to keep the first half readable. Say so explicitly at the top of the document ("Sections 4.3.1 and 4.3.2 are written for all readers; the rest assumes engineering context") so nobody feels they are failing to understand something they were meant to.

Write one SDD per significant feature or subsystem, not one per repository. If the design does not cross a team boundary, a feature spec plus an API contract is enough — do not produce this document out of habit.

**Where the feature spec ends and this document begins.** The feature spec describes what outside agents observe when they interact with the system — screens, inputs, outputs, rules, acceptance criteria — and deliberately does not say how any of it is implemented. This document says how that observable behaviour is realised: which components exist, what each owns, the interfaces between them, the algorithms and data structures behind the behaviour. When a section of the SDD could be moved into the feature spec without loss, it was written at the wrong level; when the feature spec starts naming services and tables, it has drifted into this document's territory.

Both documents get an approvals block under the metadata table, since both bind more than one party:

```markdown
| Approval | Who | Date |
|---|---|---|
| Business owner | | |
| BE / FE / AI / Data | | |
```

An empty row is information, not an oversight: it means that side has not agreed, and anyone building against the document is building on an assumption. Get the SDD agreed before implementation starts — not as ceremony, but because the interface inventory below is worthless as a contract if one of the parties has not read it.

## Document template

```markdown
# <Feature or subsystem> — Software design

<metadata table, plus:>
| **Teams** | BE: … · FE: … · AI: … · Data: … |
| **Reviewers** | |
| **Related** | BRD, feature spec, C4, ERD |

> Sections 4.3.1–4.3.2 are written for all readers. 4.3.3 onwards assumes engineering context.

## 4.3.1 Overview
### What we are building
### What changes for users
### Key decisions
### What we are deliberately not doing

## 4.3.2 Solution at a glance
One diagram plus one paragraph. The whole design in a page.

## 4.3.3 Architecture
What exists today, what this adds or changes. Decisions first, then the picture.

## 4.3.4 Data design
New and changed entities, ownership, migration. State machines for anything
with a lifecycle, drawn once here and referenced everywhere else.

## 4.3.5 Interface inventory
Every boundary this design creates or changes, numbered `I<n>`.

## 4.3.6 Interaction design — <Sales subsystem>
One flow per use case in scope, each message citing its `I<n>` and its step number.

## 4.3.7 Interaction design — <Inventory subsystem>

## 4.3.<n> Component design
One subsection per team: BE, FE, AI, Data.

## 4.3.<n> Cross-cutting design
Auth, errors and retries, idempotency, observability, configuration.

## 4.3.<n> Non-functional design
Performance budget, capacity, availability, degradation.

## 4.3.<n> Failure design
What breaks, what happens, who notices.

## 4.3.<n> Rollout and migration
## 4.3.<n> Alternatives considered
## 4.3.<n> Requirements traceability
## Open questions
## Changelog
```

Numbering continues the document number and stops at three levels ([0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers)): sections use `4.3.<n>`, while subsections are named, unnumbered H3 headings. One SDD per subsystem is the usual split. When one document covers several, **interaction design is the section divided by subsystem** — one numbered H2 per subsystem, using the same axis and order as [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) and [3.2](3.2-sequence-diagrams.md). Every other section remains whole: there is one interface inventory and one failure table regardless of the number of subsystems in scope. Splitting either table gives two teams two answers about one boundary. Because the numbering after component design depends on the number of subsystem sections, those later headings use `<n>` placeholders.

**Three positions in the order above express dependencies, not convention** ([0.1](0.1-visual-style.md#section-order)):

| Before | After | Reason |
|---|---|---|
| Architecture | Data design | The containers that exist determine where data can live and who owns it |
| Data design | Interface inventory | A boundary is where data changes ownership; interfaces cannot be inventoried until ownership is settled |
| Interface inventory | Interaction design | Sequence diagrams **cite** `I<n>` items; drawing first lets every arrow invent its own name and forces the contract table to reconcile them later |

Component design follows all three because every team builds its part **against** numbered contracts and documented flows. Reversing the order lets each team define its own contract before integration — exactly what the interface inventory exists to prevent.

## Deriving interaction design from use case specifications

Interaction design is the section most often written from memory, and the symptom is always the same: diagrams of the happy path and a system with no defined behaviour when anything goes wrong. Open [2.3](2.3-use-case-specs.md) beside it and take one thing from each part of every use case in scope:

| In the use case specification | In interaction design |
|---|---|
| Precondition | A check at the start of the flow and a branch for the unsatisfied case |
| Each main-flow step | One message carrying the same step number (`b3`) |
| Each numbered alternative or exception flow | An `alt` fragment, or a separate diagram when it changes *who calls whom* |
| Postcondition | What must be true when the flow ends — usually a state in the state machine |
| Cited business rule | `BR<n>` written directly on the message that applies it |

At the analysis level, lifelines are classes ([3.2](3.2-sequence-diagrams.md)); here they are **deployed containers** with protocols, timeouts, and retry behavior. The use case and step numbers stay the same while the altitude changes, so the diagrams can be read side by side and any mismatch becomes obvious.

## The stakeholder layer

Sections 4.3.1 and 4.3.2 are the part most engineers write badly, usually by compressing the technical design rather than answering different questions. Four rules make the difference:

**Write in the domain's vocabulary, not the system's.** "A loan application is scored automatically and only borderline cases reach a credit officer" — not "the scoring service is invoked synchronously and returns a decision payload".

**`What changes for users` is concrete and specific.** Who does something differently on Monday morning than they did on Friday? Which screens change, which manual step disappears, what gets faster and by how much. If nothing observable changes, say that too — plenty of good design work is invisible, and pretending otherwise invites the wrong questions.

**`Key decisions` states impact, not reasoning.** Three to six rows, no more:

| Decision | Why | What it means for us |
|---|---|---|
| Scoring runs synchronously during submission | Applicants expect an immediate answer | The scoring service becomes part of the submission path; if it is down, submissions stop. The failure design section covers the fallback. |

The third column is what a sponsor actually needs — the consequence they are accepting. Reasoning that needs a page belongs in an ADR, linked from here.

**`What we are deliberately not doing`** is short and blunt. Scope refused in writing at design time is scope you do not re-argue at delivery time.

Section 4.3.2 gets exactly one diagram — usually a simplified container view showing only what this design touches, with everything else greyed out. Resist adding a second; the constraint is what forces the diagram to be readable.

## Interface inventory: the contract index

This is the highest-value table in the document, and the reason the SDD is worth writing at all. Every boundary the design creates or changes, in one place, with a status:

| # | Interface | Type | Producer | Consumer | Contract | Status |
|---|---|---|---|---|---|---|
| I1 | `POST /applications/{id}/score` | REST sync | AI | BE | [scoring.api.md](…) | Agreed |
| I2 | `application.scored` | Event | BE | Data, FE | [events.api.md](…) | Draft |
| I3 | `applications_daily` partition | Batch | BE | Data | [exports.md](…) | **TBD** |
| I4 | Scoring feature table | Table | Data | AI | [erd-features.md](…) | Agreed |

Two habits make it work. First, review this table before implementation starts and check every row is at least `Agreed` — a row still in `Draft` is a team that will be blocked, visible weeks before it happens. Second, when a design review runs long, come back to this table: most cross-team disagreement turns out to be about a row here, and arguing about the row is faster than arguing in the abstract.

Number the interfaces `I1`, `I2` and cite those numbers in the sequence diagrams and component sections, so a reader can move between the picture and the contract without guessing.

**This table is derived, not recalled from memory**: filter all [3.2](3.2-sequence-diagrams.md) messages that cross a team or process boundary, remove calls within the same container, then group by **resource**, not screen — three screens that read the same order use one interface. The four-step process and the method for deriving payloads from use case field tables instead of database tables are in [0.5 K8](0.5-derivation.md#k8-deriving-interfaces-from-cross-boundary-messages).

**Count it as well as reviewing it**: a management use case has one `I<n>` for **every operation** in the [2.3](2.3-use-case-specs.md) operation matrix, except operations explicitly declared to have no interface. A row such as `I3 Manage products` combines five contracts into one. It passes review because it looks complete, then five teams discover five different omissions during implementation ([0.7](0.7-operations.md#the-seven-stage-chain-for-every-operation)).

## Per-team component design

One subsection per team, each following the same shape. The consistency matters — engineers read only their own subsection plus the interfaces they touch, so the shape should be predictable.

```markdown
### Backend — orders-service

**Responsibility** — one or two sentences.

**Does not** — what this component explicitly leaves to others.

**Internal structure**
| Module | Responsibility | Notes |

**Key logic**
The non-obvious algorithms, calculations or state transitions. Business rules are cited (`BR-EL-02`), not restated.

**Assumes** — what this component takes as given about the rest of the system.

**Replacing this** — cheap / expensive / permanent, and one line on what it would cost.

**Depends on** — I1, I4; the `applications` table.

**Provides** — I2, I3.
```

The **`Does not`** line is the one people skip and the one that prevents the most rework. Duplicated logic across BE and FE, or between BE and a data pipeline, almost always traces back to two teams each assuming the other was not handling something. Writing the negative space costs a sentence.

**`Assumes` and `Replacing this`** are how the detail budget from [0.2](0.2-writing-principles.md#how-much-detail-spend-it-on-what-cannot-be-undone) reaches component level. Most components answer `Replacing this` with *cheap* and one line, and that is the correct amount of writing for them. The ones that answer *permanent* get everything: expand `Assumes` into a list, and give the component its own subsection rather than a table row. An SDD where every component is documented to the same depth has failed to tell the reader which parts they cannot get wrong.

Team-specific additions worth requiring:

**Frontend** — state management approach for the data involved, what is cached and for how long, what is optimistic, and how the states from the wireframe document map onto the interfaces above. An FE section without an explicit answer for "what does the screen show while I1 is slow" is incomplete.

**AI / ML** — model choice with a one-line rationale, input construction (what data is assembled and from where), output post-processing, the confidence threshold and what happens below it, the deterministic fallback when the model is unavailable, and how the model is versioned and rolled back. Also: what is decided by the model versus by rules, because that boundary is the thing other teams most need to understand and most often assume wrongly.

**Data** — which tables are produced and consumed, freshness guarantees, lineage from source to serving table, how backfills work, and whether any consumer reads a table this design does not own. Add retention and PII handling here rather than leaving it to the ERD, since design time is when it is cheap to change.

## Performance budget

An end-to-end latency target is meaningless to four teams until it is split. This table turns one number into four contracts:

| Hop | Owner | Budget (p95) | Measured at | Notes |
|---|---|---|---|---|
| Browser render + request | FE | 150ms | RUM | |
| API handling | BE | 80ms | Server span | Excludes downstream |
| Feature lookup | Data | 40ms | Server span | Cached, 5min TTL |
| Model inference | AI | 250ms | Server span | Batch size 1 |
| Network + overhead | — | 80ms | | |
| **End to end** | | **600ms** | | Target from R4 |

Each team now owns a number they can test against, and a regression is attributable rather than a group discussion. Add a `Timeout` and `On exceeded` column when the budget also drives client behaviour — a caller's timeout should be derived from this table, not chosen independently, which is how retry storms start.

The same treatment applies to throughput (expected and peak rate per interface) and to data freshness (how stale a consumer may find a table). State the assumption behind the numbers — expected volume, concurrency, growth over the next year — because a budget with no stated load assumption cannot be re-derived when volume changes.

## Failure design

Designed explicitly, at design time, rather than discovered in production:

| # | Failure | Blast radius | Detection | Behaviour | Owner |
|---|---|---|---|---|---|
| F1 | Model service unavailable | New submissions cannot be scored | Alert on I1 error rate > 5% | Fall back to rule-only decision; flag for review; user sees no error | AI + BE |
| F2 | Feature table stale > 24h | Scores use old data, silently | Freshness check in pipeline | Block scoring, route to manual review | Data |

Work through every row of the interface inventory and ask what happens when it is unavailable, slow, or returning wrong-but-plausible values. That third case is the one teams skip and the one that hurts most, because nothing alerts and the damage accumulates.

Every failure needs a decided user-visible behaviour. "Returns an error" is a decision; leaving it unstated means each team invents a different one.

## Traceability

Close the loop back to the requirements:

| Requirement | Design element | Interfaces | Verified by |
|---|---|---|---|
| R4 (decision within 1s) | Non-functional design, performance budget | I1, I4 | TC-SC-003 |
| BR-EL-02 (income floor) | Component design, BE key logic | — | TC-EL-011 |

A requirement with no design element is either unaddressed or handled somewhere nobody wrote down; a design element with no requirement is scope that arrived without being asked for. Both are worth surfacing during review, and this table is the only place either becomes visible.

## What does not belong here

The SDD gets bloated when it absorbs neighbouring documents. Keep it a hub:

| Content | Belongs in |
|---|---|
| Full request and response schemas | API contract |
| Every column and constraint | ERD and data dictionary |
| Screen layouts and states | Wireframes |
| Business rule logic | Business rules |
| The argument behind a decision | ADR |
| Setup and deployment steps | Engineering guide |

The SDD says *what the pieces are, how they interact, and who owns what*. Everything it references is a link. When a section starts restating another document, replace it with a link and one sentence explaining why the reader might follow it — a design document that duplicates its sources is a design document that will be wrong within a month.
