## Interface and implementation

Stanford's CS 190 draws a hard line between two kinds of documentation: **interface** documentation is what someone needs in order to *use* a thing, and **implementation** documentation is how it works internally. The rule is that implementation detail must never leak into interface documentation — a user who has to understand the internals in order to call something correctly is looking at a failed abstraction. Interface documentation is also allowed to use entirely different, simpler vocabulary than the implementation does, if the simpler terms describe the thing more clearly.

Stanford's university IT practice draws the same line at document scale: the functional specification describes what outside agents *observe* when interacting with the system and deliberately does not define how any of it will be implemented, while the technical design describes how that behaviour is realised in code — interface signatures with their data types and exceptions, class models, the specific algorithms used, and physical data models.

Both are the same rule. Every document in this set falls on one side of it, and knowing which side keeps content from drifting into the wrong file:

| Interface documents — what a consumer observes | Implementation documents — how it works |
|---|---|
| API contract | Component design (SDD, component design section) |
| Interface inventory (SDD 4.3.5) | Key logic and algorithms |
| ERD and data dictionary | Migration and pipeline internals |
| Wireframes and screen states | Frontend state management design |
| Feature spec, business rules | Technical design, ADR |
| User guide | Runbook, engineering guide |

Practical consequences worth enforcing while writing:

- An API contract that explains *why* the service is slow, or which library it uses, has leaked. Move it to the design document.
- A design document that restates every field of a payload has leaked in the other direction. Link the contract.
- A user guide that mentions services, queues or tables has leaked badly — users observe screens and outcomes, nothing else.
- When a consumer keeps asking "but what does it do internally?", the interface documentation is incomplete, not the reader inattentive. Fix the interface document rather than sending them the design.

## Completeness of an interface description

The corollary of the rule above is demanding: an interface description must contain *everything* any user might need to know, because you have just forbidden them from reading the implementation to find out. CS 190's list of what is routinely missing maps directly onto the fields and endpoints in our contracts. Check each one:

| Check | Question to answer explicitly |
|---|---|
| Identity | Exactly what is this thing — not a restatement of its name |
| Units | Minor units or major? Percent of what? Seconds or milliseconds? |
| Boundaries | Does "end" mean the last item or the one after it? Is a range inclusive? |
| Absence | Is null allowed, is an omitted field different from a null one, and what does each mean? |
| Ownership | Who creates it, who may modify it, who is responsible for cleaning it up |
| Invariants | What is always true of this thing, that a caller may rely on |
| Failure | What happens when it is not available, and what the caller should do |

These are cheap to write at design time and expensive to discover later, because each one is a defect that only appears at an integration boundary — precisely where two teams each assumed the other's interpretation.

## Document each thing exactly once

Duplicated documentation does not get maintained, so the copies diverge and readers cannot tell which is current. Reference instead of repeating, and keep each fact as close as possible to the thing it describes: field semantics live in the data dictionary, endpoint behaviour in the API contract, decision rationale in the ADR.

This is why the SDD is a hub of links rather than a self-contained narrative, and why a document that restates its sources should be shortened rather than expanded. When you catch yourself copying a table from another document, replace it with a link and one sentence saying why the reader might follow it.

Higher-level statements survive longer than lower-level ones, so when a fact could reasonably be written at either level, write the higher one. "Scores are cached for the duration of an application session" outlives "scores are cached for 300 seconds in Redis".

## How much detail: spend it on what cannot be undone

"Be detailed" and "be concise" are only in tension if detail is spread evenly. It should not be. Two questions decide how much any component or decision gets, and they are independent of how large it is:

**1. Will the code still be able to tell you this later?** Structure, field names, call order and module layout are all recoverable by reading the source — documenting them in depth buys a copy that will drift. Reasoning, rejected alternatives, baked-in assumptions and the conditions that would force a change are recoverable from nowhere: the moment the author leaves, that knowledge is gone. **Write down what the code cannot say.**

**2. What does being wrong cost?** A decision that can be reversed in an afternoon needs a line. A decision that cannot be reversed without migrating every row, rewriting every client, or restarting the project needs everything: what it assumes, what depends on it, what it would take to change, and what was rejected.

| Reversibility | Examples | Detail it earns |
|---|---|---|
| **Effectively permanent** — replacing it means migrating all data or rewriting the system | Tenancy model, primary-key and ID strategy, database engine where its semantics are relied on, the identity/permission model, event-log semantics, what a "user" is | Full treatment: assumptions, dependants, alternatives rejected with the reason, the cost and trigger of ever changing it |
| **Expensive** — weeks, and other teams feel it | Public API shape, message bus, framework, sync-versus-async choice at a boundary, storage format of anything already written | An ADR plus a complete interface contract |
| **Cheap** — days, contained inside one component | Library choice, internal module layout, caching, log format, most refactors | One line in the component table. No ADR — the code is the documentation |

The practical consequence is that a good design document is **uneven on purpose**. Three paragraphs on the tenancy model and one line on the HTTP client is not an inconsistency to fix; it is the budget being spent where it is unrecoverable. A document that gives every component equal weight has told the reader nothing about which parts to worry about — and a reviewer's attention is the scarcest thing the document is competing for.

Two failure modes this rule is aimed at, in opposite directions. Padding a cheap component with implementation detail produces a document nobody finishes and that is wrong within a sprint. Compressing a permanent decision to one line because "we should be concise" removes the only information that will still matter in two years. Cutting length is only free when what you cut is recoverable elsewhere.

[4.1](4.1-design.md#one-way-doors) carries the operational version of this: the table of components that cannot be swapped, and what each of their entries must contain.

## Design notes: things with no natural home

Some knowledge belongs to no single component: a wire protocol, how the system handles a node that appears dead but is not, a timing assumption shared by three services, an invariant maintained jointly by BE and Data. CS 190's answer is a `designNotes` file with tagged sections, referenced from wherever the knowledge is needed — in code, a one-line comment pointing at the tag rather than a copy of the explanation.

Adopt it directly. Keep `docs/design-notes.md` with short named sections, and reference the tag from code comments, ADRs and the SDD:

```markdown
## Zombie workers
A worker whose lease has expired may still be processing a job...

## Clock assumptions
Three services compare timestamps generated on different hosts...
```

```go
// See "Zombie workers" in docs/design-notes.md.
```

This is the file that catches the cross-cutting knowledge that otherwise lives only in the head of whoever built it, and it is worth creating before anyone feels the need for it. Each section is short; anything that grows past a page is really an ADR or a section of the SDD.

## When to write

Write the documentation for an interface **before** building behind it, not after. CS 190 makes the argument bluntly: you probably will not go back, and if you do, you will be in a hurry, emotionally checked out, and will have forgotten the subtleties — so what you produce will be a superficial restatement of what the artifact already shows.

Writing first has a second benefit that matters more for a team than for an individual: the API contract, the interface inventory and the wireframe states are exactly the artifacts that unblock the other three teams. Written first, they are a contract. Written last, they are a transcript.

The same discipline applies to changes. Stanford's IT practice requires technical documentation to be updated whenever a change request or enhancement is approved during a project, precisely so that support teams have accurate design information at go-live. Treat a documentation update as part of the change rather than a follow-up task: the pull request that changes the behaviour changes the document, and reviewers check both.

## Documentation as a design smell detector

The most valuable thing about writing documentation first is what it reveals. CS 190 names several red flags; each has a direct equivalent in this document set:

| Red flag while writing | What it usually means |
|---|---|
| The interface description has to be very long to be complete | The interface is too complex; simplify the interface, not the document |
| You cannot write the description without describing internals | The abstraction is leaking; the boundary is in the wrong place |
| You cannot find a clear, unambiguous name for a field or endpoint | The concept is not yet understood, or two concepts are conflated |
| Two components' `Does not` sections overlap or contradict | Ownership is genuinely undecided; settle it before implementation |
| A wireframe needs a paragraph to explain what a control does | The screen, not the document, is the problem |

When you hit one of these, say so in the document's open questions rather than writing around it. A document that quietly absorbs a design problem hides it from exactly the review that could have caught it.

## Approval gates

Stanford's IT practice gates each phase on an approval: the functional specification must be approved by both the business and the IT sponsor before technical design starts, and the technical design must be approved before development begins. The heavy version of this is more process than most teams want — but the underlying point is sound, and cheap to keep: a document that is a contract needs someone on each side to have said yes, on the record.

Keep the light version. Add an approvals block to any document that binds two or more parties — feature spec, SDD, API contract, test plan, UAT:

```markdown
| Approval | Who | Date |
|---|---|---|
| Business | | |
| Engineering (BE) | | |
| Engineering (AI) | | |
```

An empty row is informative: it means that side has not agreed yet, and anyone building against the document is building on an assumption. Where the team uses an issue tracker, link requirement numbers to their tracker issues so the document and the work queue stay connected in both directions.
