# 5.1 Codebase guide

Documentation for the person who has to work in the codebase: a new joiner on day one, and someone from another team making a cross-cutting change. Operational documents — runbook, ADRs, release notes — are in [5.2](5.2-operations.md).

These files live in the repository, not in a wiki. Documentation that is not in the same pull request as the change it describes goes stale within a quarter, and code review is the only reliable moment at which someone notices.

## What lives where

| File | Reader | Update when |
|---|---|---|
| `README.md` | Anyone landing in the repo | Purpose, entry points or setup change |
| `docs/dev/setup.md` | New joiner | The toolchain changes |
| `docs/dev/conventions.md` | Every contributor | The team agrees a new rule |
| `docs/dev/configuration.md` | Anyone deploying or debugging | A variable is added or its meaning changes |
| `docs/dev/deploy.md` | Whoever ships | Pipeline or environment changes |
| `docs/ops/runbook-<service>.md` | On-call | A new failure mode is learned |
| `docs/design-notes.md` | Anyone hitting cross-cutting behaviour | A shared assumption or mechanism is established |
| `docs/decisions/NNNN-<slug>.md` | Future maintainers | Never — ADRs are immutable |

Keep these in the repository, not in a wiki. Documentation that is not in the same pull request as the change it describes goes stale within a quarter, and code review is the only reliable moment at which someone notices.

## Repository README

The README's only job is to get a reader oriented in under a minute and then point them onwards. Keep it short — everything detailed belongs in `docs/`.

```markdown
# <service-name>

One or two sentences: what this service does and who consumes it.

| | |
|---|---|
| **Owner** | team + channel |
| **Language / framework** | |
| **Runs on** | |
| **API contract** | link |
| **Dashboards / alerts** | link |
| **Runbook** | link |

## Quick start
Three to five commands from clone to running locally.

## Where things are
| Path | Contains |
|---|---|

## Documentation
Links to setup, conventions, configuration, deployment, architecture.
```

The "Where things are" table beats a directory tree dump: it explains intent (`internal/orders` — order lifecycle and state transitions) rather than restating what `ls` already shows.

## Onboarding and local setup

Written so a new joiner can follow it without asking anyone. Test this by having the next new joiner follow it literally and fix whatever they got stuck on — that is the only reliable way this document stays correct.

Cover, in order: prerequisites with exact versions; access needed and who grants it; clone and install; how to get local data (seed script, anonymised dump, fixtures — never a production copy); how to run the service, its dependencies and its tests; how to verify it is working, with a specific command and its expected output; and the three problems newcomers most often hit, with fixes.

Pin versions explicitly. "Node 20.11" is followable; "a recent Node" produces a support conversation.

## Code structure and conventions

Document only what a linter cannot enforce. Formatting rules belong in tooling, not prose — if the team argues about a rule, encode it in the formatter and delete the paragraph.

What genuinely needs writing down:

- **Layering.** Which direction dependencies are allowed to flow, and what each layer may not do (handlers do not touch the database directly; domain code does not import the web framework).
- **Naming patterns** that carry meaning: what a `*Service`, `*Repository`, `use*` hook or `*_job` module is expected to be.
- **Error handling.** Where errors are wrapped, where they are logged, what reaches the caller. Duplicate logging is the usual symptom of this being undocumented.
- **How to add a common thing** — a new endpoint, a new event consumer, a new migration, a new React page — as a short numbered walkthrough naming the files touched. This single section removes most "how do I…" questions.
- **Testing expectations.** What must have a test, what is deliberately untested, where fixtures live.
- **Boundaries between BE / FE / AI / Data code**: which packages are shared, how generated clients are produced from the API contract, and who regenerates them.

Anti-patterns worth naming explicitly, with one line on why, are more useful than a list of rules — they explain the reasoning and let people generalise.

## Configuration and environments

One table, every variable, no exceptions:

| Variable | Required | Default | Environments | Description |
|---|---|---|---|---|
| `DATABASE_URL` | Yes | — | all | Postgres connection string |
| `RANKING_MODEL_VERSION` | No | `latest` | staging, prod | Pin to reproduce results |

State for each: whether it is a secret and where secrets are stored; whether changing it needs a restart; and what happens when it is missing — failing loudly at startup is a design decision worth documenting, because silent defaults cause outages that look like code bugs.

Then a short environment table: name, purpose, URL, data (real / anonymised / synthetic), who can deploy. The data column matters — it is what stops someone testing against real customer records.

## Build, test and deploy

Describe the path a commit takes to production, in the order it happens: what CI runs and what blocks a merge; how a version is produced and tagged; what a deploy does, including migrations; how a feature flag or gradual rollout is controlled; how to roll back and what the rollback does *not* undo (a run migration, an emitted event, a sent email).

That last point deserves its own line in the document. Rollback is usually assumed to be complete, and it usually is not.

For services with a model or a data pipeline, add: how a model version is promoted and rolled back, and how a pipeline is backfilled or re-run after a fix — including whether re-running is safe, which is the first question anyone asks under pressure.
