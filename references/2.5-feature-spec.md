# Feature specs

A feature spec is the one document a stakeholder and an engineer read together. It has to hold a business rationale and an implementation contract on the same page without either half becoming noise for the other reader. The structure below does that by ordering sections from least to most technical — a PM stops reading after `Requirements`, an engineer starts skimming there.

## Document template

```markdown
# <Feature name>

<metadata table — required: Status and Last updated; optionally add Target release, Stakeholders, and Engineering owners only when known>

<plain-language summary paragraph>

## Problem
Who has the problem, how it shows up today, and what it costs. Evidence where it exists — a number, a ticket volume, a quote from support.

## Goals and non-goals
| | |
|---|---|
| **Goals** | |
| **Non-goals** | |

## Success metrics
| Metric | Current | Target | Measured by |
|---|---|---|---|

## User stories
| # | As a… | I want… | So that… |
|---|---|---|---|

## Requirements
| # | Requirement | Priority | Notes |
|---|---|---|---|

## Behaviour
Rules, edge cases, and state transitions. Diagram if there is a state machine.

## UX
Link to the wireframe document. Do not redraw screens here.

## Technical approach
| Layer | Changes | Contract |
|---|---|---|
| Backend | | |
| Frontend | | |
| AI / ML | | |
| Data | | |

## Dependencies and risks
| # | Item | Type | Impact | Mitigation / owner |
|---|---|---|---|---|

## Rollout
Flag, phases, migration, rollback trigger.

## Acceptance criteria
## Open questions
## Changelog
```

`Non-goals` does more work than its size suggests. It is where scope creep is refused once, in writing, instead of repeatedly in standups.

## Writing requirements

Number every requirement (`R1`, `R2`) — reviews, tickets and test cases all reference these numbers, and unnumbered requirements become unciteable.

One requirement states one testable thing. Prefer the concrete over the aspirational: "The confirmation email **MUST** be sent within 60 seconds of payment capture" is buildable and checkable; "The system should be fast and reliable" is neither.

Priority uses MoSCoW (`Must` / `Should` / `Could` / `Won't`) and the `Won't` rows stay in the table rather than being deleted — a visible "not this release" prevents the question being reopened.

Where a requirement depends on a rule the business owns (tax, pricing, eligibility), state the rule fully in the `Behaviour` section rather than in the requirement row. Requirements should read as short claims; the rules behind them need room.

## Splitting work across BE / FE / AI / Data

The `Technical approach` table is where a feature becomes parallelisable, so it needs to name the boundary artifacts rather than describe intentions. Each row's `Contract` cell links to the document that lets the other side start work: an API contract, an ERD change, a wireframe, a model contract.

Useful discipline: after filling the table, ask what each team is blocked on and whether the thing that unblocks them exists yet. If FE is blocked on an endpoint that has no contract document, the spec is not ready — that is the most common cause of a feature slipping, and it is visible here before any code is written.

For AI-involving features, additionally record what is being asked of the model, what the fallback is when it fails or is unavailable, how output quality will be evaluated before launch, and who reviews that evaluation. These questions are cheap now and expensive after integration.

For data-involving features, record which tables or events are added or changed, whether analytics events are needed for the success metrics above (a metric with no event is not measurable), and whether any historical backfill is required.

## Acceptance criteria

Written so that a person who did not build the feature can verify it. Given/When/Then works well because it forces a starting state:

```markdown
- **AC1** — Given a cart with an expired coupon, when the user submits the address step, then a field-level error appears on the coupon and the step does not advance.
- **AC2** — Given payment succeeds, when the confirmation screen renders, then the order ID is shown and an `order.created` event has been emitted.
```

Cover the failure paths, not just the happy one, and make each criterion trace back to a requirement number. Criteria that cannot be checked without reading the code are not acceptance criteria.

## Sizing the spec

Match the document to the decision it carries:

| Change | Spec |
|---|---|
| Copy change, config toggle | No spec; a ticket is enough |
| Single-team, no interface change | Problem, requirements, acceptance criteria — one page |
| Multi-team or new interface | Full template |
| Multi-quarter initiative | Full template per deliverable, plus a short parent document linking them |

A spec longer than about four pages has usually stopped being a contract and started being a design discussion. Split it, and move the argument into a decision record linked from `Technical approach`.
