# 6.1 Test plan and cases

Test documents close the loop the other documents open: requirements state what should happen, test cases prove it does. The link between them is what makes the whole set trustworthy, so traceability is treated here as a first-class requirement rather than an afterthought.

Business acceptance and defect reporting are in [6.2](6.2-uat-and-defects.md).

**Risk priorities come before test levels, and both come before the criteria** ([0.1](0.1-visual-style.md#section-order)): the risk table determines how deeply each level covers each area, and the exit criteria set thresholds *on* that depth. In the reverse order, the levels table becomes a generic list copied from the previous release and the risk table becomes a page nobody acts on.

Exit criteria need numbers, not adjectives: *"no open Severity 1 or 2 defects; ≥ 95% of Must-priority cases passed; p95 latency of `POST /orders` below 400ms at 50 rps"*. "Quality is acceptable" cannot be argued about productively at 6pm on a release day, which is exactly when it will be argued about.

Risk-based prioritisation is what keeps the plan honest. Testing everything equally means testing the payment path with the same care as the settings page; say plainly which areas get deep coverage and which get a smoke test.

## Writing test cases

Group cases by feature area, one table per area. Keep them in the repository next to the code, or in the test management tool if the team uses one — but never in both, because two copies diverge and nobody knows which is authoritative.

| # | Requirement | Title | Preconditions | Steps | Expected result | Priority | Type |
|---|---|---|---|---|---|---|---|
| TC-CO-014 | R7, BR-EL-02 | Reject below income floor | Applicant with income 7,000,000 VND | 1. Submit application<br>2. Open decision screen | Status `rejected`, reason `low_income` shown; no loan account created | Must | Negative |

Rules that keep cases usable:

- **One expected result per case.** A case checking three things fails ambiguously.
- **Expected results are observable** — a screen state, an API response, a row, an emitted event. "Works correctly" is not a result.
- **Preconditions are complete.** A case that only passes because of leftover state from the previous case is a case that fails for the next person.
- **Stable IDs.** `TC-<area>-<n>`, never renumbered. Bug reports and traceability matrices cite them.
- **Cover the negative and boundary cases deliberately.** For every rule with a threshold, write cases at the boundary and on both sides of it. Most defects found late are boundary defects.
- Mark which cases are automated and where they live, so manual regression runs skip them.

Four sources generate test cases **mechanically** and should be processed before inventing any cases: every decision-table row produces one case, plus two boundary cases on either side of each threshold ([0.5 K6](0.5-derivation.md#k6-decision-tables-and-hit-policy)); every cell in the state × event grid — valid and invalid alike — produces one case ([0.5 K7](0.5-derivation.md#k7-finding-states) and [3.5](3.5-state-machines.md#testing-a-state-machine)); every numbered alternative and exception flow in [2.3](2.3-use-case-specs.md) produces one case; and **every operation-matrix row plus each of its error codes** produces one success case and one case for every exception ([0.7](0.7-operations.md)). These four sets cover precisely what brainstorming misses, and they can be counted.

The fourth source catches exactly what the first three miss: **operations nobody demonstrates**. Deleting a referenced item, restoring a deleted item, handling a file import that fails midway, and resolving concurrent edits by two users do not appear in the main flow, but each has a row in the operation matrix.

Derive cases from acceptance criteria where they exist — an `AC` in a feature spec should map to at least one case, and an `AC` with no case means either the criterion is untestable or the coverage has a hole. Both are worth knowing before release.

## Traceability

A single table, maintained per release, is enough for most teams and answers the two questions that matter: *is everything we promised actually tested*, and *if this rule changes, what do we re-run*.

| Business req | Feature req | Acceptance criterion | Test cases | Status |
|---|---|---|---|---|
| BR3 | R7 | AC2 | TC-CO-014, TC-CO-015 | Passed |
| BR4 | R9 | AC5 | — | **Gap** |
| NFR1 | — | p95 < 400ms @ 50 rps | TC-PERF-002 | Passed |

Three items are cited at a finer grain than the requirement, and all three are common coverage gaps: a use case **flow** (`UC-02 5a`, not just `UC-02`), because teams often write cases only for the main flow; an **operation** (`UC-A03.T6`, not just `UC-A03`), because a use case marked *tested* often means only its create path was tested; and an `NFR<n>`, whose row carries the threshold and verification method chosen in 2.1, so the test plan inherits them instead of inventing a second value.

Error codes are traced as individual rows as well: every `code` in [4.4](4.4-api-contract.md#service-wide-error-code-catalog) has at least one case, because a failure branch that has never run before a customer reaches it will fail in a way nobody has seen.

Rows with no test cases are the whole point of the table — surface them rather than quietly omitting them. Generate it from the source documents if the team's tooling allows; maintain it by hand only when the release is small enough that it will actually be kept current.

## Test data

Undocumented test data is the most common reason a test suite works for one person and not another.

| Dataset | Purpose | Source | Refresh | Contains PII |
|---|---|---|---|---|

State how each dataset is created (seed script, fixture file, anonymised export), how it is reset between runs, and which accounts or records the cases depend on by name. Anonymisation is stated explicitly — never test against a raw production copy, and say so in the document so nobody assumes it is allowed.

## Testing across BE / FE / AI / Data

Each side fails differently, so a plan that only describes end-to-end tests leaves real gaps:

**Backend** — contract tests generated from or validated against the API contract document, so drift between the document and the implementation is caught mechanically rather than by a consumer in production. Include error paths and idempotency.

**Frontend** — the states table from the wireframe document doubles as a test checklist: loading, empty, error, partial, permission, validation, long content. Add the browser and device matrix, and accessibility checks if they are in scope.

**AI / ML** — behaviour is statistical, so pass/fail cases only work for the plumbing (the endpoint responds, the schema is right, the timeout is honoured, the fallback fires). Quality is assessed against a fixed evaluation set with a threshold agreed in advance: which metric, what score, on what data. Also test the ugly cases explicitly — empty output, refusal, low confidence, adversarial or out-of-domain input, and behaviour when the model service is down. Record which model version the results apply to; results without a version cannot be compared later.

**Data** — test schema conformance, row counts against expectations, null and uniqueness constraints, and the completeness marker before a partition is read. Add reconciliation cases that compare a derived table against its source for a known window, since silent divergence is the characteristic data failure and it is invisible to every other kind of test.
