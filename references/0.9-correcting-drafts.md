# 0.9 Correcting drafts — the read, edit, observe loop

AI-generated documentation does not fail randomly. Its errors follow **shapes**: wherever a number is required, a plausible number appears; wherever a field name is required, a conventionally named field appears; wherever an arrow is required, an arrow connects two real boxes. Nothing is blank, so nothing **looks** wrong. That is the central difficulty of correction: fluent reading reveals little, so defects must be sought by type.

This file defines the working loop for that task. It does not replace [0.5](0.5-derivation.md) (does each component have evidence?), [0.6](0.6-mechanism.md) (does the picture represent the real mechanism?), or [0.8](0.8-use-case-constraints.md) (is a use case testable?). It explains **how to run those checks against a completed draft** and which tools reduce a two-minute correction to ten seconds.

## Start a correction pass

```bash
python3 scripts/serve_docs.py <docs_folder> --title "<set name>"     # :8777
```

**Do not use `npx serve` or open `site.html` through `file://` for correction.** Both serve static HTML: edits have no path back to `.md`, so either you copy them manually into an editor or correct a copy while the real file remains unchanged. The page served by `serve_docs.py` is **the same page** plus three server-only capabilities: `Ctrl/Cmd+S` writes directly to the real `.md`, disk changes flow into the open page, and the page maintains a baseline for comparison.

Click `Edit` (or press `Ctrl/Cmd+E`) to open two synchronized panes: Markdown on the left and the rendered page on the right.

## Three tasks the tool handles

| Task | Action | Why it matters |
|---|---|---|
| **Find what to edit** | Click **any block in the rendered page** — paragraph, table row, heading, or diagram — and the editor jumps to and selects the corresponding Markdown block | The questionable claim may be on line 340 of a 500-line file; locating it takes more effort than retyping it. The reverse direction also works: placing the caret in Markdown highlights the corresponding rendered block |
| **Edit a diagram** | Click **✎** on a diagram (or click the diagram while in Edit mode) to open Mermaid source on one side, a live redraw on the other, and syntax errors below. `Apply` replaces exactly the body between the fences | A Mermaid fence is the only document part that **cannot be proofread as text** — readers cannot reliably reconstruct a picture from twenty lines of `-->`. Insert buttons for nodes, decisions, labelled edges, lanes, include/extend, and init blocks preserve the [0.1](0.1-visual-style.md) and [0.3](0.3-diagramming.md) conventions |
| **See how far the review has progressed** | A colored bar marks every block that differs from the **baseline** — Git HEAD for a committed file, or startup content otherwise. The editor bar counts changed blocks and opens a clickable list | After an hour, the remaining question is *"which text is still the AI's original?"* On the rendered page, corrected text and unread text otherwise look identical |

Two baseline details determine what the bars mean: the baseline is **the AI-produced draft**, so it **does not move when you save** — the bars deliberately remain. To move the baseline after finishing one pass and beginning another, run `git commit` and reload the page; the new HEAD becomes the new baseline.

## Review order: by type, not from start to finish

Sequential reading is the weakest review method because fluent prose is precisely what AI produces best. Review by **element type**, one type per pass, in descending risk order:

| # | Review | How to catch defects | Consequence of invention |
|---|---|---|---|
| 1 | **Do identifiers exist?** — table, column, endpoint, error code, and enum names | Compare against real code or schema; in mode A, every statement must have `path:line` | Frontend builds against a nonexistent endpoint |
| 2 | **Numbers** — NFR thresholds, frequency, capacity, and duration | Any number that cannot be traced to a `Source` was invented | A performance contract nobody can measure |
| 3 | **Empty or suspiciously identical `Source` cells** | One source repeated across an entire table means the derivation passes were not run ([0.5](0.5-derivation.md)) | A whole family of use cases is missing without anyone noticing |
| 4 | **Diagram arrows** | Read every edge back as a sentence and demand evidence ([0.6](0.6-mechanism.md)) | An incorrect mechanism is drawn as settled |
| 5 | **Counts** — sections equal use case rows; operation rows equal endpoints | Rules 3 and 11 in [SKILL.md](../SKILL.md) | Half the system lacks specifications while the set looks complete |
| 6 | **Conditions and exceptions** | [0.8 R4–R5](0.8-use-case-constraints.md#r4-conditions-preconditions-business-rules-and-assumptions-are-different) | Only the happy path is implemented |
| 7 | **Wording** — vague language and empty verbs | [0.5 K10](0.5-derivation.md#k10-reviewing-vague-language), [0.8 R2](0.8-use-case-constraints.md#r2-name-verb--object-and-nothing-else) | Cheapest to fix, so review it last |

Passes 1–3 must be run **beside the code or a domain expert**, not alone. Passes 4–7 can be run independently on the page.

## Correct without breaking traceability

There are three ways to handle an untrusted statement, and choosing the wrong one is worse than leaving it unchanged:

| Situation | Do | Do not |
|---|---|---|
| You know the correct value | Correct it directly | — |
| You know it is wrong but not what is correct | `**TBD** — <what is missing> (owner: <who>)` | **Delete it.** Deletion turns a known error into an invisible gap nobody asks about |
| It sounds plausible but nobody has confirmed it | `**ASSUMPTION** — <what is assumed> (confirm: <who>)` | Leave it unmarked — unmarked text means *someone stated it* ([SKILL.md](../SKILL.md), rule 5) |

This is rule 5 in reverse: while writing, unmarked text means a source exists; while correcting, **removing a marker requires a reason**. Deleting a false statement without leaving a trace is how an unanswered question disappears from the project.

## How one correction propagates

The documentation set is connected by **identifiers**, so changing one identifier means changing several files. After fixing the source, search immediately:

```bash
grep -rn "UC-03\|Place order" <docs_folder>           # changed use case ID or name
grep -rn "recipient_phone" <docs_folder>               # changed field name
grep -rn "NFR2" <docs_folder>                          # changed threshold
```

| Changed item | Must propagate to |
|---|---|
| **Use case** name or ID | [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) · diagrams in 2.2 · specification block in 2.3 · [3.1](3.1-analysis-classes.md) · [3.2](3.2-sequence-diagrams.md) · [3.3](3.3-class-diagrams.md) · [4.5](4.5-ui-design.md) · [6.1](6.1-test-plan.md) |
| **Actor** name | [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) · actor column in 2.1.2 · actor field in each use case · activity-diagram lane · [3.2](3.2-sequence-diagrams.md) lifeline · [3.4](3.4-data-flow.md) external entity |
| **Field** name | Field tables in 2.3 · [4.2](4.2-data-model.md) · [4.4](4.4-api-contract.md) · test cases |
| An **operation** `T<n>` | The seven stages in [0.7](0.7-operations.md#the-seven-stage-chain-for-every-operation) |
| An **exception** | Flow in 2.3 · error code in [4.4](4.4-api-contract.md) · test case in [6.1](6.1-test-plan.md) |
| **System boundary** | Not one row: update [1.1.1](1.1-problem-survey.md#111-problem-and-system-boundary), the actor table, external entities in 3.4, and containers in [4.1.1](4.1-design.md) together; see [2.1](2.1-actors-and-use-cases.md#changing-the-boundary-means-changing-the-whole-table-not-adding-a-row) |

The open page automatically reloads files changed on disk, so changes made in another editor appear immediately. A document with unsaved browser edits is never overwritten; the page reports the conflict instead.

## Diagrams: the one thing that cannot be proofread as text

The ✎ pane solves the mechanics of *typing* a diagram. It does not determine **whether the diagram is true** — a polished picture can still describe the wrong mechanism. Run one check after every diagram edit: **read every edge back as a complete sentence, then demand evidence for that sentence** ([0.6](0.6-mechanism.md#read-back)). *"The order service calls the payment gateway and **waits** for the result"* — does it really wait, or is the response a webhook? If the answer is unknown, put `**TBD**` in the caption instead of drawing a more attractive arrow.

Three errors survive every review because they **look like architectural knowledge**: a poll drawn as a push, a queue drawn as a direct call, and an event drawn before the commit that makes it visible.

## Review-session self-check

| # | Check | Failure prevented |
|---|---|---|
| 1 | Correct through `serve_docs.py`, not static HTML | A copy is corrected while the real `.md` remains as the AI wrote it |
| 2 | Run all seven type-based passes instead of one sequential read | Fluent prose is mistaken for correct prose |
| 3 | Every unconfirmed statement has `**TBD**` or `**ASSUMPTION**` with an owner | An unanswered question disappears with Delete |
| 4 | Search the entire set for every changed identifier | Two documents use different names for one concept without either showing an error |
| 5 | Read back every edge in each corrected diagram | An incorrect mechanism is drawn as settled |
| 6 | At session end, `git commit` moves the baseline | The next pass cannot distinguish AI text from reviewer text |
| 7 | Counts in rules 3 and 11 still match after correction | Deleting an extra row misaligns a table in another document |
| 8 | Run `build_site.py` and resolve **every `!` line** — dead `.md` links, fragments matching no heading, H4, or pages over the contents budget | Content moved elsewhere leaves a link pointing nowhere |
| 9 | **Inspect the rendered page**, not just heading counts: is the sidebar evenly divided, and does the page contents list the parts readers need? | A bold label looks finished in Markdown but remains invisible in navigation |
