# 2.4 Non-functional requirements

**Phase 2 · Specification.** The final file in phase 2 defines how fast, scalable, reliable, and secure the system must be — every target has a number and a measurement method.

Phase 2 contains five files — [2.1 actors and use cases](2.1-actors-and-use-cases.md) · [2.2 diagrams](2.2-use-case-diagrams.md) · [2.3 specifications](2.3-use-case-specs.md) · **2.4 NFRs** · [2.5 feature specifications](2.5-feature-spec.md).

**This is the authoritative statement of NFRs for the documentation set.** [1.1.7](1.1-problem-survey.md#117-technical-and-security-constraints) records constraints the project *was given*; the table here records what the project *commits to*; [4.1](4.1-design.md) and [4.3](4.3-detailed-design.md) explain how the design satisfies each commitment; [6.1](6.1-test-plan.md) explains how each is verified. All three cite `NFR<n>` instead of copying its text.

Organised by the nine characteristics of ISO/IEC 25010:2023, because a home-made list always misses the same three — recovery, operability, portability: functional suitability · performance efficiency · compatibility · interaction capability · reliability · security · maintainability · flexibility · safety.

| # | Quality characteristic | Requirement | Measurable threshold | Verification method | Priority | Applies to | Source |
|---|---|---|---|---|---|---|---|
| NFR1 | Performance | The order-list page **MUST** respond within the threshold below at design load | p95 < 400 ms at 50 rps with 100k orders in the database | Test — pre-release load scenario | Must | UC-03 | Constraint 1.1.7 |
| NFR2 | Reliability | A recorded order **MUST NOT** be lost when the payment service fails | 0 orders lost across 1,000 simulated failures | Test — payment-gateway chaos test | Must | UC-01 | N3 |
| NFR3 | Security | A recipient's phone number **MUST NOT** appear in application logs | 0 phone-number pattern matches in 24 hours of staging logs | Inspection — automated log scan | Must | Entire system | Data policy |

- **A non-functional requirement without a number is not a requirement.** Every row carries a threshold **and the condition it holds under** — a latency with no load figure behind it is met trivially by testing with one user.
- **`Verification method` uses the four ISO/IEC/IEEE 29148 methods**: *Test* (run and measure) · *Demonstration* (operate and observe) · *Inspection* (read code, configuration, or logs) · *Analysis* (calculate or model). A row with no identifiable method is a row nobody will check.
- **Say what it applies to.** A blanket NFR is usually three different numbers pretending to be one; checkout and the reporting export do not deserve the same latency budget.
- **This is the authoritative statement.** [1.1.7](1.1-problem-survey.md#117-technical-and-security-constraints) records constraints the project was *given*; [4.1](4.1-design.md) and [4.3](4.3-detailed-design.md) explain how the design meets each one; [6.1](6.1-test-plan.md) explains how each is tested. All cite `NFR<n>` rather than restating it.
