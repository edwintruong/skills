# 5.2 Operations, decisions and releases

Three document types that share a reader: whoever has to keep the system running and understand why it is the way it is. The codebase-facing documents are in [5.1](5.1-codebase-guide.md).

The cross-cutting `docs/design-notes.md` file belongs to this group too — see [0.2 Writing principles](0.2-writing-principles.md#design-notes-things-with-no-natural-home).

## Runbook

Written for someone tired, under pressure, and possibly unfamiliar with the service. Structure everything as symptom → action.

```markdown
# <service> — Runbook

| | |
|---|---|
| **Owner / escalation** | team, channel, on-call rota |
| **Dashboards** | links |
| **Dependencies** | what this breaks if it is down, and what breaks it |

## Health checks
Command or URL, and what a healthy response looks like.

## Alerts
| Alert | Means | First action | Escalate if |
|---|---|---|---|

## Common failures
One H3 per failure: symptom, how to confirm, how to fix, how to verify recovery.

## Routine operations
Restart, scale, clear a queue, replay events, rotate a credential.

## What not to do
Actions that look helpful and cause damage.
```

Include the exact commands, not descriptions of them. "Drain the queue" is not actionable at 2am; the command is.

The `What not to do` section is written from real incidents, and it is the highest-value part of the document — every entry represents an outage the team is no longer going to repeat.

## Architecture decision records

An ADR captures one decision, at the moment it is made, and is never edited afterwards. Superseding an ADR means writing a new one and marking the old one `Superseded by NNNN`. The immutability is the point: the value is knowing what was believed at the time, not what turned out to be true.

```markdown
# NNNN — <Decision in a short noun phrase>

| | |
|---|---|
| **Status** | Proposed / Accepted / Superseded by NNNN |
| **Date** | YYYY-MM-DD |
| **Deciders** | |

## Context
The forces at play: constraints, requirements, what we knew and did not know.

## Decision
What we are doing, stated in one or two sentences, in the active voice.

## Alternatives considered
| Option | Why not |
|---|---|

## Consequences
What becomes easier, what becomes harder, what we are now committed to, what we will need to revisit.
```

Write an ADR when a choice is expensive to reverse, constrains other teams, or would otherwise be re-litigated every few months — a datastore, an auth model, a sync-vs-async boundary, a model-serving approach. Library choices rarely need one. Keep them under a page; an ADR nobody reads is worse than an ADR that omits some nuance.

## Release notes

One entry per release, newest first, in a single `CHANGELOG.md`. Group changes by `Added` / `Changed` / `Fixed` / `Deprecated` / `Removed` / `Security`, and write each line for the person who consumes the change rather than the person who made it — the audience is other teams and support, not the author.

Flag anything that requires action from a consumer: a breaking API change, a required config addition, a migration that must run first. Those lines belong at the top of the entry, marked plainly, because they are the only lines a reader must not miss.

For user-visible releases, keep a separate, plainer set of notes with the user guide. The engineering changelog and the customer release notes serve different readers and merging them serves neither.
