# 0.4 Requirements interview

Mode B has no codebase to read, so the source of truth is a person. This reference explains how to elicit it: run the interview as **rounds over a design tree**, writing every answer into a numbered document before the next round begins. It replaces *"ask what the customer wants"* — which produces a feature list — with a sweep that has an end condition.

The engine is adapted from Matt Pocock's `grilling` and `domain-modeling` skills. What is added here is that **the design tree is already known**: it is the section list of phases 1 → 4, so the frontier can be computed instead of discovered, and every answer has a cell waiting for it.

## The engine

| Term | Meaning |
|---|---|
| **Design tree** | Every decision, branching into the decisions that hang off it |
| **Frontier** | Decisions whose prerequisites are already settled — what you can ask *now* without guessing at an answer you have not heard |
| **Round** | The whole frontier, asked in one message, numbered, each with your recommended answer |
| **Done** | Frontier empty: every branch visited, nothing silently assumed |

Ask the frontier, then **wait**. A question whose answer depends on another question still open belongs to a *later* round — asking it now buys a guess. Each round's answers push the frontier outward; recompute and ask again. Question numbers run `Q1…Qn` across the whole interview so an answer stays citable.

```markdown
**Q7 · Cart reservation expiry** — How long should inventory remain reserved before release?
(a) 15 minutes · (b) 60 minutes · (c) until end of day
→ **Recommend (a)** — enough for one checkout attempt without locking inventory overnight.
```

Four laws:

| Law | Why |
|---|---|
| **Facts are yours, decisions are theirs** | Never ask what you can look up — repo, schema, standard, public data, this skill's own references. Dispatch the lookup and do not block the rest of the round on it; only the questions downstream of that fact wait |
| **One question, one decision** | Two decisions in one question get one answer, and you will not know which one it was |
| **Every question carries your recommended answer** | Confirm-or-correct is several times faster than compose. A recommendation you got wrong gets corrected; a bare question gets skipped |
| **Write before the next round** | An answer living only in the conversation is lost at the next `/clear`. Fill the rows it unblocked, *then* recompute the frontier |

The `Q<n>` identifier is **evidence** for every row produced by that answer — but it is **writer-facing evidence** and belongs in the `interview` block of `.software-docs.json`, not document prose. In the document, the `Source` cell names the question by **topic**: *"round 3 — reservation expiry"*, not `Q7`. Readers do not have the interview transcript, so `Q7` is a dangling reference they cannot verify or distinguish from an invented code ([0.5](0.5-derivation.md#evidence-and-citation-are-different-things)).

⚠ **Do not make a code the subject of a sentence.** *"`Q63` settles reservation expiry"* breaks when codes are removed, and every such sentence requires manual rewriting. Codes confined to `Source` cells and parentheses can be removed in one command. Name each question as a **readable topic** from the start (`Q7 · Cart reservation expiry`), not a label meaningful only during the conversation. The reverse direction is more valuable: three derivation techniques run **before** anyone answers — event partitioning, the entity-category inventory, and empty CRUD-matrix cells ([0.5](0.5-derivation.md#eleven-techniques)) — and a half-filled table is always faster to answer than an open question.

## How one round works

A round is a delivery unit, not merely a question unit: **ask → wait → write → show → ask the next round**. Respondents see the documents grow after every answer, understand what their answer became, and can correct it immediately — instead of answering thirty questions and later receiving documents nobody remembers agreeing to.

| # | Step | Ends with |
|---|---|---|
| 1 | Research everything discoverable — repository, standards, public data, and this skill's references | Existing facts that will not be asked again |
| 2 | Prefill using the three techniques that work before anyone answers ([0.5](0.5-derivation.md#eleven-techniques)) | A half-filled table |
| 3 | Ask **the entire frontier in one message**, numbered `Q<n>`, with one recommendation per question | One message, not a sequence |
| 4 | **Wait.** Write nothing belonging to this round before answers arrive | — |
| 5 | Write the unlocked sections immediately into the **real files** | Changed documents on disk, not a chat summary |
| 6 | Report exactly three things: changed files, `ASSUMPTION`/`TBD` lines, and the next round's topic | Respondents know where they are |
| 7 | Save state and recompute the frontier | The next round can begin in another session |

Three prohibitions prevent three distinct loop failures:

| Prohibition | Reason |
|---|---|
| **Write beyond the frontier** | Writing 4.5 while round 8 remains open is fiction: screens derive from flows that nobody has settled |
| **Ask the next round before writing this one** | Answers that live only in chat disappear at the next `/clear`, forcing the interview to restart |
| **Combine rounds "for speed"** | Combine only when all prerequisites are closed (the round table states *Prerequisite*); otherwise deep-branch questions are answered by guesses that become requirements |

**Partial answers are normal.** If eight questions receive five answers, write those five and place the remaining three as owned `**TBD**` items **in the documents**, then ask again at the start of the next round. Do not silently omit them or block the whole round. A round closes only when every question has an answer *or* a named owner on its `TBD`.

## The rounds are already known

Mode B's design tree is the document set. Rounds are not sprints — several can go in one message when all their prerequisites are settled, and one round can take several messages.

| Round | Settles | Writes into | Prerequisite |
|---|---|---|---|
| 0 | Folder, language, diagram mode, documentation mode, system shape | `.software-docs.json` | — |
| 1 | Context, problem statement, goals with baseline + target, in/out of scope, **boundary: what is the box and what is inside it** | [1.1](1.1-problem-survey.md) 1.1.1 | 0 |
| 2 | User groups, goals, current approach, pain points, scale/frequency | 1.1.2 `N<n>` → [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) actors | 1 |
| 3 | As-is process: who does what, order, **manual steps**, SLA per step | 1.1.3 | 2 |
| 4 | Functions + MoSCoW priority, function tree, **subsystem names**, input/output per leaf | 1.1.4 `FR<n>`, 1.1.5, 1.1.6 | 3 |
| 5 | Constraints, security, personal data, retention, compliance, measurable thresholds | 1.1.7 `C<n>` → NFRs in 2.4 | 4 |
| 6 | Business rules and vocabulary | [1.2](1.2-business-rules.md) `BR<n>` + glossary | continuous; waits for no round |
| 7 | **Close the use case list** — six passes in 2.1 become six question groups; assign every case a subsystem | 2.1.1 + 2.1.2 | 4 |
| 8 | Each use case: preconditions, main flow, alternatives, exceptions, postconditions | 2.3 onward | 7 |
| 9 | One-way doors: buy or build, synchronous or asynchronous, data ownership | [4.1.1](4.1-design.md) *Architecture decisions* + ADR | 5, 7 |
| 10 | Entities, keys, lifecycle, retention · external systems, who calls whom | [4.2](4.2-data-model.md), [4.4](4.4-api-contract.md) | 8 |
| 11 | Screens, visibility, and primary action per screen | [4.5](4.5-ui-design.md) 4.5.2, six screen passes | 8 |
| 12 | **Wireframe review**: layout, field order, error placement, empty states | 4.5 seven-block screen specs + wireframes | 11 |
| 13 | Milestones, dependencies, and risks with early indicators | 1.1.8 | 4 |

**Round 1 settles the boundary, and three later documents reread that exact statement** — the [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) actor table, [3.4](3.4-data-flow.md) external entities, and the [4.1.1](4.1-design.md) container inventory. Ask two questions, not one: *"what does this product include that your team builds and releases?"* then *"which externally owned systems exchange data with it?"* The combined question *"what does the system interact with?"* mixes internal services with actual partners and sends that mixture directly into the actor table.

**Round 4 settles subsystem names, and the entire set reuses them exactly.** Ask for the subsystem axis once, then copy it into 2.1, 3.1–3.3, 4.3, and 4.5 ([0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers)); documents divided independently can no longer be read side by side.

**Round 7 is the most expensive and must not be shortened.** Everything from phase 3 onward is written per use case, so one omission here removes a class table, sequence diagram, class diagram, screen, and test-case set.

**Phase 3 has no interview round of its own**, deliberately: [3.1](3.1-analysis-classes.md)–[3.4](3.4-data-flow.md) are **derived** from round 8 without further questions. Needing a question during phase 3 means round 8 missed an exception flow — return to round 8 for that use case rather than patching a diagram with an assumption.

**Round 12 is the only round run against a drawing.** A wireframe lets respondents see what they did not verbalize: a missing field, wrong action order, or overlooked state. Keep it low fidelity for that reason — a finished-looking design shifts feedback toward colors.

## Resuming an interview in a later session

A mode B documentation set spans several sessions, and the assistant has no memory between them. State lives beside the setup answers in `<docs_folder>/.software-docs.json`:

```json
{ "docs_folder": "docs", "language": "en", "diagram_mode": "mermaid",
  "mode": "greenfield", "systems": ["admin", "user"], "author": "Alex Nguyen",
  "interview": {
    "round": 7,
    "asked_through": "Q34",
    "open": ["Q31 cart reservation expiry", "Q34 who approves refunds"],
    "answered": { "Q31": "round 3 — reservation expiry", "Q28": "round 3 — who may cancel orders" },
    "written": ["1.1", "1.2", "2.1", "2.2"],
    "next": "8 — 2.3 specify each use case, beginning with UC-U01"
  } }
```

Write this block **in the same document edit** as step 7, not at session end. A new session reads it before asking anything and begins *"round 7 still has Q31 and Q34 open"* instead of repeating round 1 — repeating answered questions is the fastest way to lose the respondent.

`answered` maps codes to topics, allowing a topic-based `Source` cell to trace back to the exact question. JSON is the **index** and the document is the **record**: the same open questions must appear in that document's `## Open questions`. If they disagree, the document wins; update JSON.

## When there is only an idea

There is no repository or known as-is process, and the user describes the product through imagined screens. Use the same engine with three adjustments:

**1 · Round 1 opens with a restatement to correct, not an open question.** From the user's description, create one page containing: product in one sentence · 3–6 user groups · 5–10 main flows · out of scope · system boundary. Mark every line `**ASSUMPTION**`. Ask *"what is wrong?"* plus only what the restatement cannot infer. Correcting an existing page is far faster than composing from an open question — this applies the *one recommendation per question* rule to the whole round.

**2 · Keep round 3 but change the question.** No system does not mean no existing work: people may use spreadsheets, chat, notebooks, or another system. That is the as-is process and the only place to discover manual steps and exceptions. If nobody has ever performed the work, write *"No as-is process exists"* rather than inventing one to fill the section.

**3 · Interface fields are evidence, not decoration.** People describe ideas through forms: *"this screen needs order ID, creation date, status, and customer name."* Each field is an undeclared **entity attribute** that arrives well before round 10. Record it immediately instead of leaving it only in wireframe notes:

| They mention | Record in | Ask immediately |
|---|---|---|
| A screen field | A row in the [4.2](4.2-data-model.md) data dictionary with source `Q<n>` | Which entity owns it? Who fills it? Is it required? Can it change after creation? |
| A button / action | A `T<n>` in the use case operation matrix ([0.7](0.7-operations.md)) | Who may click it? What does failure show? |
| A list-table column | A field plus filter/sort criterion in 4.5 | Can users filter by it? What is the default sort? |
| A state ("pending approval") | An enum value plus an edge in [3.5](3.5-state-machines.md) | Which states can reach it? Who changes it? |

The reverse is a trap: **do not draw screens to fill unanswered gaps.** A wireframe always looks complete, so guessed screens pass review and their entity tables inherit assumptions nobody can distinguish later. Mark every field nobody stated with `**ASSUMPTION**` in the table, even when it seems obvious.

## Question shapes that pay

| Ask | Instead of | Why |
|---|---|---|
| "When is that **not** true?" | "How does the process run?" | Main flows are guessable; exceptions are not, and exceptions create most rules |
| "How many, for how long, how often per day?" | "Is it a lot?" | Numbers fit tables; adjectives do not |
| "What happened the last time this failed?" | "Are there risks?" | Imagined risks are generic; real incidents have dates, impact, and early signals |
| "Who is accountable when this step is wrong?" | "Who performs this step?" | Reveals ownership, permission, and audit trail together |
| "If the system produces X, what do you do with the result?" | "Which feature do you want?" | Moves from a proposed solution to the underlying need |
| "What runs automatically without a button click?" | "What do users do?" | Scheduled and deadline-driven use cases never appear in workshops |
| "Do these two terms mean the same thing?" | *(ignore it)* | Vocabulary drift is the hardest defect to trace; fix it where it appears |

## Translating what they said

They speak in solutions and habits; the documents need needs, rules and use cases.

| They say | Actually | Record in |
|---|---|---|
| "Give me an Export to Excel button" | Proposed solution | Underlying need becomes `N<n>`; original statement goes in *Current approach* |
| "It must never…" | Business rule | `BR<n>` with conditions and boundaries expressed using `<` or `≤` |
| "Usually…" | Hidden exception | Ask *"when not?"*, then record an alternative flow in 2.3 |
| "This must be fast" | Unmeasurable NFR | `NFR<n>` with threshold, load, and measurement method |
| "Make it like the old system" | Constraint, not requirement | `C<n>` with source |
| "That case is very rare" | Still a use case | A 2.1.2 row, or explicit `Out of scope`, never silence |
| "We'll decide later" | Deferred decision | Owned and dated `**TBD**` |

## When they do not know

Two markers, never a silent choice. Both stay English like every reference ID, so they are greppable in a Vietnamese document.

| Marker | Use when | Form |
|---|---|---|
| `**TBD**` | Nobody has decided | `**TBD** — <what is missing> (owner: <who>, due: <date>)` |
| `**ASSUMPTION**` | You choose temporarily to continue | `**ASSUMPTION** — <what is assumed and why> (confirm: <who>)` |

`**ASSUMPTION**` is the only thing a mode B document may contain that nobody stated aloud. Everything unmarked means a human stated it. Both markers also become rows in that document's `## Open questions`, forming the next session's opening frontier.

## Who can answer what

| Question about | Can answer | Cannot answer reliably |
|---|---|---|
| Goals, scope, priority, budget | Sponsor, business owner | End user |
| Current approach, pain points, exceptions | Person doing the work | Manager — they describe how it *should* run |
| Infrastructure, operations, integration constraints | IT, operations | Business team |
| Personal data, retention, compliance | Legal, security | Anyone willing to guess but not own the answer |

Record who answered in the `Source` column of `N<n>`, `FR<n>`, and `BR<n>` — that column exists for exactly this purpose. An answer with nobody's name survives every review because nobody can identify whose preference it was.

The most expensive interviewing mistake is interviewing one person. A manager describes the process as designed; the exception paths, where the work actually is, never surface.

## Recording as you go

| Item | Destination | When |
|---|---|---|
| Answer | Correct cell and row in the numbered document | Immediately after the round, before the next |
| Newly settled term | [1.2](1.2-business-rules.md#domain-glossary) glossary, including *Not to be confused with* | When settled |
| Hard-to-reverse decision | ADR in [5.2](5.2-operations.md#architecture-decision-records) | When all three conditions below hold |
| Undecided item | `**TBD**` + that document's `## Open questions` | End of round |

An ADR is written only when all three hold: the decision is **costly to reverse**, a future reader would be **puzzled without the reasoning**, and there were **genuine trade-offs**. Anything else is a table row. See [4.1 One-way doors](4.1-design.md#one-way-doors) for which decisions qualify.

Challenge terms as they are spoken. Two words for one thing, or one word for two things, is fixed in the same sentence it appears — not in a cleanup pass, because there is never a cleanup pass.

## Self-check before leaving a round

| # | Check | Pass condition |
|---|---|---|
| 1 | Frontier empty | No round question remains unresolved — answered or converted to an owned `TBD` |
| 2 | Written down | Every answer is in its document cell, not only in conversation |
| 3 | No redundant questions | Nothing asked could have been researched directly |
| 4 | No premature questions | No question depends on another open answer |
| 5 | Sourced | Every new `N`/`FR`/`BR` names its respondent in `Source` |
| 6 | Quantified | Words such as *"many,"* *"fast,"* and *"often"* do not replace required numbers |
| 7 | Vocabulary | Every new term is in the glossary with likely confusions |
| 8 | Assumptions visible | Everything you chose is marked `**ASSUMPTION**` |
| 9 | Something delivered | The round changed at least one `.md` file on disk and named that file to the user |
| 10 | Resumable | The `.software-docs.json` `interview` block matches document `## Open questions` sections |

## Common mistakes

| Mistake | Consequence | Replace with |
|---|---|---|
| Ask one question per message | Interview takes ten times longer and respondents leave midway | Ask the entire numbered frontier in one message |
| Ask the whole tree at once | Deep-branch questions receive guesses that become requirements | Ask only the frontier |
| Ask what exists in the repository or public material | Spend respondent attention on research you can do better | Research facts; ask only decisions |
| Provide no recommendation | Receive short, vague, or missing answers | One recommendation and one-line rationale per question |
| Store interview minutes in a separate file | Nobody reads it, and it diverges from documentation within a week | Write directly into numbered documents |
| Choose silently | Later readers cannot distinguish decisions from guesses | `**ASSUMPTION**` naming the confirmer |
| Ask every round before writing | Respondents cannot see what answers became; defects surface only in the expensive final draft | Write after every round and report filenames |
| Draw screens for an unsettled flow | Finished-looking wireframes pass review and contaminate the entity model | Run rounds 11–12 only after round 8 |
| Stop at *"that is enough"* | Unvisited branches return in sprint 3 as "new work" | Exhaust the frontier, then confirm shared understanding |
