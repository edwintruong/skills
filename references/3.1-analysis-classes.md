# 3.1 Identifying analysis classes

**Phase 3 · Analysis.** Phase 2 described *what* the system does in business language. Phase 3 describes *how its pieces are arranged to do it* — still without choosing a framework, database engine, or deployment shape.

**Phase 3 is four documents, written in this order.** They are a dependency chain, not a menu: you cannot draw a sequence without knowing the participants, and you cannot freeze a class diagram honestly until the sequence has shown which associations are actually used.

| Document | Answers | Form | Unit |
|---|---|---|---|
| **3.1 Identifying analysis classes** (this file) | Which objects a use case needs and what each is responsible for | Table | Each use case |
| [3.2 Sequence diagrams for each use case](3.2-sequence-diagrams.md) | In what order they call one another and who waits for whom | Diagram | Each use case |
| [3.3 Class diagrams for each use case](3.3-class-diagrams.md) | How they relate and with what multiplicity | Diagram | Each use case |
| [3.4 Data-flow diagrams](3.4-data-flow.md) | Where data comes from, where it goes, and where it persists | Levelled diagrams | Entire system |

These are four documents, not four sections in one document: each grows with the number of use cases multiplied by one diagram, and a missing file is immediately visible in the sidebar — that visibility is the reason for the split. [3.5](3.5-state-machines.md) provides shared notation for entities with lifecycles; it is not another phase document.

**The section axis, numbering, and order** shared by all four documents are defined in [0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers): sections are H2 headings numbered `3.1.<n>`, use cases are unnumbered H3 headings, and the subsystem axis closed in [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) is reused without change.

**Three rules without exceptions** apply to 3.1, 3.2, and 3.3 — precisely the three ways phase 3 documentation usually fails:

1. **Every use case in the [2.1](2.1-actors-and-use-cases.md) table has exactly one subsection in 3.1, one in 3.2, and one in 3.3.** This can be counted: all three documents must have the same number of subsections, equal to the row count in that table. A missing subsection is a silently dropped use case, not one that is "not needed yet."
2. **A consolidated view cannot replace per-use-case views.** Draw the consolidated diagram *afterward*, at the end of the document, as an overview. Because it combines every class, it can no longer answer the one question this phase exists to answer: *which classes does this use case use, and which does it not use?*
3. **A simple use case still gets its own subsection.** A short flow produces a short table and diagram; three lifelines and four messages are valid. Merging two use cases because "they are similar" asserts that they are one use case, and if that is true, the table in 2.1 is what must change.

| Standard | Taken from it |
|---|---|
| Jacobson, *OOSE* (1992) → RUP **Use-Case Analysis** | The stereotypes `<<boundary>>` · `<<control>>` · `<<entity>>`, use-case realization, and who may call whom |
| ISO/IEC/IEEE 29148:2018 | Bidirectional traceability: every use case realised, every element tracing back to one |

**Two diagrams are deliberately not in this phase.** The **activity diagram** already lives inside each use case specification ([2.3](2.3-use-case-specs.md)) — the only one belonging here is a standalone one spanning several use cases. The **ERD** is a design artifact with one home, [4.2](4.2-data-model.md); what this phase owes it is its *input* — the `<<entity>>` classes below with their multiplicity from [3.3](3.3-class-diagrams.md), and the data stores of [3.4](3.4-data-flow.md). Two ERDs one phase apart is the most reliable way to end up with two answers about one table.

**Mode A** reads all four documents off the code: route handlers and UI components are `<<boundary>>`, the service layer is `<<control>>`, ORM models are `<<entity>>`. A control class inferred from a file name is a guess until the call chain confirms it.

Numbering stops at H2; each use case is an unnumbered H3 carrying its ID and name ([0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers)). The subsystem therefore occupies the H2 tier and each subsystem receives its own number. For a small system (≤ 8 use cases and one primary actor), omit the subsystem tier: `## 3.1.2 Analysis classes by use case`, followed by `### UC-01 — …`. Omitting the subsystem tier is optional; **omitting the use case tier is not**. Put the use case ID before the name because readers search for it. Keep **class names in English** and in `code`; write the `Responsibility` column in the document language.

## Ba stereotype

Three stereotypes, every class exactly one of them. The split survives because it separates the three things that change for different reasons: the interface changes with the UI or protocol, the control with the business flow, the entity with the domain.

| Type | What it is | Where to find it | Example |
|---|---|---|---|
| `<<boundary>>` | Where the system meets an actor — screen, endpoint, or external-system port | Every actor × use case pair in the [2.1](2.1-actors-and-use-cases.md) table | `OrderCheckoutScreen`, `PaymentGateway` |
| `<<control>>` | Coordinates one use case's flow | Every use case produces one control | `PlaceOrderController` |
| `<<entity>>` | Information the system must remember between interactions | Business nouns in flows and data-field tables | `Order`, `Voucher`, `Customer` |

- **One use case, one control, until evidence proves there are two.** Two controls in one use case mean it contains two independent flows — the use case table is wrong, not this class table.
- **Count boundaries by actor × use case pair.** A customer places an order through a screen while a payment gateway calls back through a webhook: two actors, two boundaries, one use case. Missing the external system's boundary is the most common way an integration disappears from the design.
- **A noun is not necessarily an entity.** Filter three groups: synonyms (*order* / *purchase order*), concepts that are only attributes of another object (*delivery address* belongs to `Order` until the customer has an address book), and concepts that live for only one interaction (*temporary cart*). The complete five-question filter and the **category inventory** find concepts the text never mentions — transaction lines, memorable events, and lookup catalogs ([0.5 K2](0.5-derivation.md#k2-nouns-the-filter-and-category-inventory)). Use [K3](0.5-derivation.md#k3-responsibility-and-collaboration-crc) to decide whether a control is one or two; after the class tables are complete, [K4](0.5-derivation.md#k4-the-crud-matrix) checks coverage by exposing entities nobody creates and use cases that touch no data.

**Who may call whom** — the rule that makes this model checkable rather than decorative:

| From ↓ · To → | Actor | `<<boundary>>` | `<<control>>` | `<<entity>>` |
|---|---|---|---|---|
| Actor | — | ✓ | ✗ | ✗ |
| `<<boundary>>` | ✓ | ✗ | ✓ | ✗ |
| `<<control>>` | ✗ | ✓ | ✓ | ✓ |
| `<<entity>>` | ✗ | ✗ | responds, does not initiate | ✓ |

**A boundary that reads or writes an entity directly** is business logic that moved into the screen; it will be duplicated the day a second interface appears and the duplicate will drift. **An entity that calls a boundary** is a domain object that knows about screens and cannot be tested or reused without the UI. A control with more than roughly seven collaborators is doing the work instead of coordinating it — split it, usually along a group of steps already visible in the flow.

## Self-check before publishing

| # | Check | Fails when |
|---|---|---|
| 1 | **Count**: number of subsections = number of rows in the [2.1](2.1-actors-and-use-cases.md) use case table | A use case silently dropped from phase 3 — the most common defect here |
| 2 | Every subsection carries a use case ID and follows the same subsystem axis as 2.1 | Two documents that cannot be read side by side |
| 3 | Every class has exactly one stereotype | A class doing two jobs, which is where the layering starts leaking |
| 4 | Exactly one `<<control>>` per use case, or a written reason | A use case that is really two |
| 5 | Every boundary traces to an actor × use case pair | An external-system integration missing from the design |
| 6 | `Derived from` points to a specific flow step in 2.1 | The class list was invented rather than derived |
| 7 | No framework, no column type, no repository, no DTO | Design decisions taken a phase early |

## Common mistakes

| Mistake | Instead |
|---|---|
| List classes only for a few "main" use cases | Include as many subsections as there are use case rows; count before publishing |
| One shared class table for the whole subsystem | Create per-use-case tables first, then add a consolidated table at the end |
| One "god" control per subsystem | One control per use case |
| Turn every noun in the specification into an entity | Filter synonyms, attributes, and concepts that live for only one interaction |
| Design names at analysis level (`…Repository`, `…DTO`, `…ServiceImpl`) | Domain names a business reader recognises |
| Omit an external-system boundary because "it has no screen" | A boundary is where the system meets an actor; a webhook is also such a boundary |
