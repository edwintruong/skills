# 0.8 Use case constraints — level, name, sentences, conditions, exceptions

The previous three files answer different questions: [0.5](0.5-derivation.md) asks *which elements exist*, [0.6](0.6-mechanism.md) asks *whether the mechanism shown is accurate*, and [0.7](0.7-operations.md) asks *how much remains missing inside a named element*. This file covers the remaining layer, where an otherwise complete document can still fail: **is a written row truly a use case, and is its wording verifiable?**

This is the hardest layer to notice because it **leaves no blank cells**. A use case at the wrong level can contain every section. An unverifiable precondition still occupies the correct cell. A postcondition written as an action often reads more smoothly than one written as a state. All three defects surface only in [6.1](6.1-test-plan.md), when a tester reads a line and cannot tell what to observe to determine whether it is true or false.

Read this file before writing any use case block in [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) or [2.3](2.3-use-case-specs.md), and before reviewing someone else's use case. It also provides the criteria for deriving a use case list from a feature, BRD, or PRD.

## Six constraint families

| # | Constraint | Question answered | Without it |
|---|---|---|---|
| R1 | Goal level | Is this row a use case, a step, or a program? | The use case table is both bloated and incomplete, and nobody knows which level they are reading |
| R2 | Name | Does the name reveal what the actor achieves? | Screen and database-table names enter the goal list |
| R3 | Flow sentence | Who performs which single action, and is it observable? | A step with no subject leaves [3.2](3.2-sequence-diagrams.md) unable to choose a lifeline |
| R4 | Conditions | When is it checked, who checks it, and where does failure go? | A business rule sits in the precondition cell and is never implemented |
| R5 | Alternatives · exceptions | How can it fail, and in which state does each failure end? | [4.4](4.4-api-contract.md) has no error codes and [6.1](6.1-test-plan.md) contains only success cases |
| R6 | Numbers | How many, how fast, and how important? | An adjective enters the contract unchanged |

These six families apply to **one use case block**. Set-level coverage—whether the use case set is complete and every `FR` has a use case—belongs to [2.1](2.1-actors-and-use-cases.md#finding-the-complete-set-not-stopping-at-obvious-cases); operation coverage within a use case belongs to [0.7](0.7-operations.md). These checks are independent: a document with complete use case and operation coverage but unverifiable wording still cannot be built.

## R1 · Goal level: one actor, one goal, one session

Cockburn divides goals into three levels, and **only the middle level is a use case**:

| Level | Signal | Example | Treatment |
|---|---|---|---|
| **Summary** — multiple sessions, multiple people | Describes a program, lifecycle, or departmental process | *"Manage the order lifecycle"*, *"Operate the warehouse"* | **Split downward**: make each subgoal a row; retain the old name as a **subsystem** in the `Subsystem` column |
| **User goal** — one actor, one session | The actor can leave satisfied when it finishes | *"Place an order"*, *"Approve a held order"*, *"Manage products"* | Correct level—one row in [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) |
| **Subfunction** — one step toward a goal | The actor finishes but has **not** achieved anything significant | *"Verify OTP"*, *"Check inventory"*, *"Calculate shipping fee"* | **Merge upward** into a flow step; promote to `<<include>>` only when reused by ≥ 2 different use cases |

**The coffee-break test** (Cockburn): when the use case finishes, can the actor leave for coffee without feeling unfinished? No ⇒ subfunction. Must return tomorrow to finish ⇒ summary level.

**The three-ones test**: exactly **one** primary actor, exactly **one** business goal, completed in **one** continuous session. Correct each failure as follows:

| Failure | Symptom on the page | Correction |
|---|---|---|
| Two primary actors | The `Primary actor` cell has two names, or the main flow changes owner halfway through | **Two use cases**—the actor defines the use case ([0.7](0.7-operations.md#the-split-test-when-an-operation-stands-alone), question 1). *Customer places an order* and *employee places an order on behalf of a customer* are not the same use case |
| Two goals | The word *"and"* connects two different kinds of nouns in the name | Split them; if the second always follows the first, they are two use cases connected by a precondition |
| Two sessions | The flow includes *"wait for approval"*, *"the next day"*, or *"when the partner responds"* | Cut at the wait: the remainder is a separate use case triggered by an **event**, often the use case missed by discovery pass 3 in [2.1](2.1-actors-and-use-cases.md#finding-the-complete-set-not-stopping-at-obvious-cases) |

**A wait is a use case boundary, not a step.** This is R1's most expensive and most frequently ignored constraint: placing *"the employee approves within 24 hours"* in the middle of a main flow turns a use case into a process. Every downstream artifact—sequence diagram, endpoint, and test case—is then written as if someone waits in front of the screen for 24 hours.

**`<<include>>` is not a container for subfunctions.** Extract behavior only when **≥ 2 different use cases** reuse it; a step used in exactly one place remains in that flow. See [2.2](2.2-use-case-diagrams.md) for the full rule and arrow direction.

## R2 · Name: verb + object, and nothing else

A use case name is an **action verb + object**, 2–6 words, containing no actor name, screen name, or endpoint name.

| Incorrect | Why | Rewrite |
|---|---|---|
| *Order* · *Promotion* | Bare nouns—say nothing about what anyone does | *Place an order* · *Create a promotion* |
| *Customer places an order* | The actor already has its own column; including it in the name creates two places that can diverge | *Place an order* |
| *Cart screen* · *Order-list page* | Screen names belong in [4.5](4.5-ui-design.md), and screens change before goals do | *Place an order* · *Track an order* |
| *POST /orders* · *Synchronize the `products` table* | Mechanisms, not goals; Mode A often makes this mistake when deriving use cases from routes | *Place an order* · *Update the catalog from an external source* |
| *Process order* · *Perform payment* | Empty verbs—see below | *Approve a held order* · *Pay for an order* |

**Empty verbs and real verbs.** An empty verb is not inherently wrong; it **does not reveal the operations inside**, so it always creates a debt:

| Empty | Replace with | If retained |
|---|---|---|
| Manage, process, configure, monitor | Create · Update · Approve · Reconcile · Change state · Export | May be retained, but **owes an operation matrix** in [0.7](0.7-operations.md)—this is rule 11 in [SKILL.md](../SKILL.md) |
| Perform, execute, do | A real business verb | Do not retain—there is no useful meaning |
| Check, verify (standing alone) | Usually a subfunction | Merge into the use case that invokes it (R1) |

The distinction between the first two rows is R2's key point: **_"manage products"_ is a valid row that owes a table; _"process order"_ is an undecided row.** Resolve the first through [0.7](0.7-operations.md); ask the user to clarify the second.

## R3 · Flow sentences: explicit subject, one action per step

Seven constraints apply to every step in main, alternative, and exception flows:

| # | Constraint | Incorrect | Correct |
|---|---|---|---|
| 1 | **Explicit subject**, using an actor name from [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) or *System* | *"Checks inventory."* | *"The system checks inventory for each cart line."* |
| 2 | **Active voice, present tense** | *"The order will be created."* | *"The system creates the order in `pending_payment` state."* |
| 3 | **One action per step**—*and* joining different action types means two steps | *"The customer enters the code and selects Apply and the system checks it."* | Three steps; selecting the button must stand alone because an exception attaches to that exact step |
| 4 | **Alternate actor ↔ system** | Five consecutive steps contain only *"Customer…"* | Every time an actor sends something across the boundary, the system has a response step—even when the response is only a display update |
| 5 | **No branching inside a step**—no *if / when / otherwise* | *"3. If stock is available, create the order; otherwise report out of stock."* | The main flow follows the default branch; the other becomes `3a` in an alternative or exception flow |
| 6 | **No loops inside a step** | *"Repeat until the customer enters a valid value."* | *"Steps 3–5 repeat at most 3 times"*—state the **upper bound**, because it is both a rule and a test case |
| 7 | **No implementation details**—no table, endpoint, or component names | *"The system `INSERT`s into `orders` and calls `POST /pay`."* | *"The system records the order and sends the request to the payment system."* |

Constraints 5 and 6 share a non-aesthetic reason: **a branch embedded in a sentence has no number**, yet the number (`3a`, `6b`) links the flow to the activity diagram, the error code in [4.4](4.4-api-contract.md), and the test case in [6.1](6.1-test-plan.md). An unnumbered branch cannot be counted and silently disappears from all three places.

**Write interface labels in bold, exactly as shown on screen**: *"The customer selects **Place order**."* This is a controlled exception to constraint 7—the actor can **observe** a label but not a component. Labels must match [4.5](4.5-ui-design.md); a one-word difference means the documents describe different controls.

**Ambiguous wording passes the [0.5 K10](0.5-derivation.md#k10-reviewing-vague-language) filter** before a step is considered complete:

| Ambiguous | Replace with |
|---|---|
| valid, appropriate, compliant | specific criteria or a cited `BR<n>` |
| fast, timely, almost immediate | a threshold in `NFR<n>` |
| occasionally, as needed, if possible | an explicitly named condition |
| user | a role name from [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) |
| notify the customer | which channel, what content, and who owns delivery |

## R4 · Conditions: preconditions, business rules, and assumptions are different

These three concepts look alike in writing but belong in different places. Distinguish them with three questions—**who checks, when, and what happens on failure**:

| | Precondition | Business rule `BR<n>` | Assumption |
|---|---|---|---|
| Who checks | System | System | **Nobody** |
| When | **Before** the use case starts | **While** the use case runs | Never checked |
| On failure | The use case cannot start | A numbered exception flow | The system behaves incorrectly without reporting it |
| Where | `Preconditions` cell in the use case block | [1.2](1.2-business-rules.md), cited in the `Rules` column | `Assumptions` cell and a candidate for `**ASSUMPTION**` |

In one order-placement use case: *"The customer is signed in"* is a precondition (checked first; failure prevents entry). *"COD is permitted only for orders below VND 5 million"* is a `BR` (checked during the flow; failure branches). *"The payment gateway meets a 99.5% SLA"* is an assumption (nobody checks it at runtime; failure surfaces in an NFR).

**A precondition must be checkable by a query or a true/false test.** *"The system is ready"*, *"The customer wants to buy"*, and *"The data is complete"* are not checkable—the first is empty, the second is motivation, and the third is an unwritten `BR`.

**A postcondition is a STATE, not an action.** This is the most expensive wording defect in a use case block because it reads so naturally:

| Written as an action | Written as an observable state |
|---|---|
| *"The system saves the order"* | *"An `orders` record exists with `status = 'pending_payment'` and all order lines"* |
| *"The system sends a confirmation email"* | *"The registered inbox has received the confirmation email, and a delivery-log entry exists"* |
| *"The system deducts inventory"* | *"Each SKU's inventory decreases by the ordered quantity; total inventory plus reservations remains unchanged"* |

The main flow already contains the action; repeating it in the postcondition cell **repeats the flow** instead of specifying the result. Testers need to know **what to observe**, and a sentence beginning with *"The system…"* gives them nowhere to look.

**Failure postconditions are mandatory, not a courtesy field.** They answer what is rolled back, what remains, and what the user sees. If a seven-step use case fails at step 6 without saying what steps 1–5 leave behind, three developers will implement *partial success* in three different ways. See failure mode 8 in R5.

**Every postcondition traces to something real**: a table in [4.2](4.2-data-model.md), a state in [3.5](3.5-state-machines.md), an event, or something the actor can see. If it cannot be traced, nobody has decided where it is stored.

## R5 · Alternatives and exceptions: sweep eight failure modes

| | Alternative flow | Exception flow |
|---|---|---|
| Goal | **Still achieved**—through another path | **Not achieved** |
| End | Rejoins the main flow at a numbered step | Ends in an explicitly stated final state |
| Example | Pay with a voucher instead of a card | Inventory runs out during payment |

Mixing the two is the most common flow defect, and its consequence appears in [6.1](6.1-test-plan.md): error handling is buried in normal behavior, so nobody writes a test case for it.

**An exception has exactly three parts. If any is missing, it is not specified:**

1. **Trigger**—which condition, at which step (`6a`, at step 6).
2. **System response**—what the system does and what the actor sees.
3. **Final state**—what is rolled back, what remains, and whether the use case ends or returns to a numbered step.

> **6a — Inventory becomes unavailable during reservation.** At step 6, the inventory service returns `OUT_OF_STOCK` because another order took the final item. The system displays *"This product has just sold out"* with an option to request a restock notification. **Final state:** no order record exists; reservations for the other lines are released within 60 seconds; the cart retains the available lines. Error code: [4.4](4.4-api-contract.md) `ORDER_ITEM_OUT_OF_STOCK`.

**Eight-failure-mode inventory**—sweep all eight rows for **every write operation**, marking each `yes, flow <number>` or `no, because …`. A blank cell is indistinguishable from a question nobody asked ([0.7](0.7-operations.md#the-thirteen-operation-inventory) applies the same principle to operations):

| # | Failure mode | Discovery question | Commonly missed in |
|---|---|---|---|
| 1 | Invalid input | Which fields can be rejected, and by which criteria? | Use cases with many optional fields |
| 2 | Business-rule violation | Which `BR<n>` can stop this use case mid-flow? | Read use cases that appear to have no rules |
| 3 | Insufficient permission | What happens when another role invokes this exact operation? | Operations with only one role—until a second role appears |
| 4 | Object missing or already deleted | What if someone else has just deleted it? | Every operation accepting an `<id>` |
| 5 | Concurrency conflict | If two people update or reserve it simultaneously, who wins and what does the other see? | Update, approval, inventory deduction, reservation |
| 6 | External-system failure or timeout | What if a supporting actor does not respond within the threshold? | Every use case with a `Supporting actor` |
| 7 | Expired session, quota, or reservation | What if the actor leaves for 30 minutes and returns? | Multi-step use cases and reservations |
| 8 | **Partial success** | Step 4 succeeds and step 5 fails—what does step 4 leave behind? | Use cases writing to ≥ 2 places or calling externally |

Rows 5, 6, and 8 are the most expensive because each **changes the design** when discovered late: concurrency adds a version column; an external timeout adds a *pending* state and retry mechanism; partial success adds a transaction boundary or compensation queue. Discovering one in [2.1](2.1-actors-and-use-cases.md) costs a table row; discovering it in sprint three costs a schema change.

**Every exception propagates to two places, and coverage is countable**: one error code in [4.4](4.4-api-contract.md) and one test case in [6.1](6.1-test-plan.md). An exception that exists only in the specification will be implemented as a generic `500`.

## R6 · Numbers: frequency, priority, and thresholds

| Field | Constraint | Incorrect | Correct |
|---|---|---|---|
| `Frequency` | A **number** + time unit, plus peak hours when relevant | *"Frequently"*, *"daily"* | *"~500 executions/day; peak ~100/hour during campaign launch"* |
| `Priority` | The same scale used in [1.1](1.1-problem-survey.md)—MoSCoW or High/Medium/Low, one scale for the entire set—plus **one sentence of rationale** | *"High"* | *"Must—blocks release; all revenue passes through this use case"* |
| Quality threshold | Does not belong here; use an `NFR<n>` with a threshold, condition, and verification method | *"Must be fast"* inside the flow | *"NFR1: p95 < 400 ms at 50 rps"*, cited in the `Related items` field |

Frequency is not decorative: it feeds load calculations in [4.1](4.1-design.md) and determines which use cases merit optimization. If no real number exists, write `**TBD** — awaiting operations data (owner: …)`; do not use an adjective that reads like a known fact.

## Size thresholds are signals, not aesthetic rules

Exceeding a threshold is not a formatting defect; it almost always signals the wrong **level** or an **incomplete sweep**, and this table is the cheapest way to see it:

| Part | Typical threshold | Exceeding / falling short means |
|---|---|---|
| Use case name | 2–6 words | Longer: the name describes the flow or merges two goals |
| Main flow | 5–15 steps | > 15: multiple operations are merged into one flow ⇒ [0.7](0.7-operations.md). < 3: subfunction ⇒ R1 |
| One step | 1 sentence, < 30 words | Longer: contains a branch or multiple actions |
| Alternative flows | 1–5 | > 5: the use case carries two goals ⇒ split |
| Exception flows | ≥ 3 for every data-writing use case | 0–1: the eight failure modes almost certainly have not been swept |
| Data fields | Every field the actor enters or sees | Exactly matches the table schema: copying [4.2](4.2-data-model.md), not specifying the use case |
| Entire use case block | 1–3 A4 pages | Longer: revisit R1 before cutting words |

A threshold is an attention signal, not a hard limit—a genuine 18-step use case should contain 18 steps and one sentence explaining why it is long.

## Consistency across the document set

Four things must be written **identically** everywhere because each acts as a key joining documents:

| Item | Defined in | Reused identically in |
|---|---|---|
| Actor name | [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) | Actor column in 2.1.2, `Primary/Supporting actor` cells, activity-diagram lanes, and lifelines in [3.2](3.2-sequence-diagrams.md) |
| Use case ID `UC-<n>` | [2.1.2](2.1-actors-and-use-cases.md#212-identify-the-main-use-cases) | All of phases 3, 4, and 6—**never cite a row number** |
| Business-concept name | Glossary in [1.2](1.2-business-rules.md) | One term per concept across the set: *order*, not sometimes *order* and sometimes *transaction* |
| Field names and screen labels | `Data fields` table; labels match [4.5](4.5-ui-design.md) | [4.2](4.2-data-model.md) and [4.4](4.4-api-contract.md) use those exact English names |

This is also where the language rule in [SKILL.md](../SKILL.md#language) applies: write prose in the document language, while field names, enum values, and error codes remain English in `code`.

**Mode A**: goal level **cannot be read from code**. A handler is an operation, not a use case; three routes serving one goal still form one row. A route-based name such as *"POST /orders"* is the clearest sign that use cases were copied from the routing table rather than derived from goals. Exceptions are the opposite: code reveals them well. Every `raise` or `return 4xx` branch is a candidate R5 row, and the existing error-code set is the fastest way to sweep the eight failure modes.

**Mode B**: R4 and R5 produce the best interview questions because respondents need no software knowledge to answer them—*"when is this person not allowed to begin?"*, *"if two people update the same order, who wins?"*, *"if power fails at this step, what will be visible tomorrow morning?"*. See [0.4](0.4-interview.md) for question form and interview rounds.

## Self-check: run against every use case block

[2.1](2.3-use-case-specs.md#self-check-before-publishing) checks the whole document; this table checks **one block**. Run it before declaring a use case complete and when reviewing someone else's work.

| # | Check | Fails when |
|---|---|---|
| 1 | Passes the coffee-break test and the three-ones test | A step or a program sits in the use case table |
| 2 | The main flow has no *"wait for someone"* step extending into another session | A process is specified as one work session |
| 3 | Name is verb + object, with no actor, screen, or endpoint | Goal list mixes in screen and API names |
| 4 | Every empty verb (*manage, process, configure, monitor*) has an **operation matrix** | A valid but empty row ([0.7](0.7-operations.md)) |
| 5 | Every step's subject is a name from [2.1.1](2.1-actors-and-use-cases.md#211-identify-actors) or *System* | [3.2](3.2-sequence-diagrams.md) cannot choose the step's lifeline |
| 6 | No step contains *if / otherwise / repeat until* | An unnumbered branch has neither an error code nor a test case |
| 7 | No step contains a table, endpoint, or component name | The specification expires at the first redesign |
| 8 | Every precondition is checkable by a query or true/false test | *"The system is ready"*—nobody can check it, so nobody does |
| 9 | No business rule sits in the precondition cell | A `BR` is never implemented because it does not appear in [1.2](1.2-business-rules.md) |
| 10 | Every postcondition is an **observable state**, not an action | The main flow is repeated and testers do not know where to look |
| 11 | A **failure postcondition** states what is rolled back and what remains | Three people implement partial success in three ways |
| 12 | Every alternative flow states the numbered step it rejoins | A branch leaves with no return path |
| 13 | Every exception flow contains **trigger · response · final state** | A row names an error without saying where it ends |
| 14 | All **8 failure modes** were swept for every write operation, each marked `yes` or `no, because …` | Concurrency, timeout, and partial success disappear—even though all three change the design |
| 15 | Every exception traces to an error code in [4.4](4.4-api-contract.md) and a test case in [6.1](6.1-test-plan.md) | The exception is implemented as a generic `500` |
| 16 | `Frequency` is numeric; `Priority` has a rationale; quality thresholds live in `NFR<n>` | An adjective enters the contract unchanged |
| 17 | Actor names, use case IDs, concept names, and field names are identical everywhere | Two documents discuss different things while appearing to discuss one |
| 18 | Every part stays within its threshold or includes one sentence explaining why not | A level error is hidden inside a long flow |

## Sources

- **Cockburn, A.**, *Writing Effective Use Cases*—three goal levels, the coffee-break test, the black-box rule, and main/alternative/exception flow structure. R1 and R5 closely follow this source.
- **Wiegers, K. & Beatty, J.**, *Software Requirements* (3rd ed.)—the fields in a use case specification: actors, description, preconditions and postconditions, priority, frequency, flows, and assumptions. R4 and R6 provide rules for completing those fields.
- **ISO/IEC/IEEE 29148:2018** §5.2—requirements must be *unambiguous*, *singular*, and *verifiable*. R3 makes those properties checkable through sentence rules; R6 applies the same principle to quantitative fields.
- **UML 2.5.1** §18—`<<include>>` represents mandatory reused behavior, not a container for subfunctions; this bounds R1.
- **IIBA, BABOK Guide** v3 §10.48—use cases and scenarios as an elicitation technique; foundation for Mode B.
- **Larman, C.**, *Applying UML and Patterns*—actor goals produce use cases; source of R1's one-actor test.
- **phucnt-bazone-vietnam/use-case-writer** (BA Zone, Phuc NT)—practical BA constraints: empty verbs, preconditions vs. assumptions, postconditions as states, failure-mode inventory, and size thresholds. R2, R4, and the threshold table were cross-checked against this skill.
