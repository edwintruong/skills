# 0.3 Diagramming

Diagrams are produced either as **Mermaid** fenced in the Markdown, or with **draw.io** via the `drawio-skill` (`github.com/Agents365-ai/drawio-skill`) exported to SVG and embedded. The two are complementary rather than competing — but which one a document set uses is a decision for the person who owns the set, not one to make silently per diagram.

This file decides **how** a diagram is produced and rendered; whether what it shows is *true* — who initiates, who waits, what crosses, where it becomes permanent — is [0.6](0.6-mechanism.md). A beautifully exported SVG of the wrong mechanism is the most expensive artifact in the set.

## Ask which mode, once

Before drawing the first diagram of a session, ask the user which mode this document set uses — a single question with two answers:

| Mode | What happens | Choose it when |
|---|---|---|
| **Mermaid inline** (default) | Diagrams live as ` ```mermaid ` blocks inside the Markdown. Nothing else to install, diffable in review, rendered by the HTML export. | Diagrams still change; reviewers read them in pull requests; no draw.io CLI available. |
| **draw.io exported** | Diagrams are authored in draw.io, exported to SVG under `diagrams/`, embedded with `![caption](../diagrams/x.svg)`. | Layout matters, official C4/BPMN/UML shape sets are wanted, output goes to stakeholders in a deck. |

Two things make this worth one question rather than a guess. It cannot be reversed cheaply — a set half in Mermaid and half in draw.io has two review workflows and two ways to be stale. And draw.io mode has a hard prerequisite the user may not have: the desktop CLI (see [Availability check](#availability-check)), which no amount of retrying will conjure.

Record the answer in `.software-docs.json` at the root of the documentation folder, so later sessions do not ask again:

```json
{ "docs_folder": "docs", "language": "vi", "diagram_mode": "mermaid", "title": "Loan Platform Docs" }
```

`language` is settled by the same one-off question and governs diagram **labels** — node text, edge text, subgraph titles, legends and captions. Node **identifiers** stay English and terse (`c1`, `officer`, `orderSvc`) whatever the language: they are code, they appear in no rendered output, and a Vietnamese identifier with diacritics is a Mermaid parse error waiting to happen.

Read that file before asking. If it exists, it is the answer. If the user contradicts it in the request, the request wins and the file gets updated.

Within the chosen mode, the table below still governs *individual* diagrams — draw.io mode does not forbid a five-node Mermaid sketch in a design note, and Mermaid mode does not forbid embedding an SVG someone else drew.

## Which tool for which diagram

The trade-off is real and worth stating once: draw.io gives layout control, official shape sets and export quality; Mermaid gives diffable text that renders natively in GitHub and in the HTML export without a build step. Choose per diagram.

| Diagram | Tool | Why |
|---|---|---|
| C4 context / container / component | draw.io | Official C4 shapes, multi-page with click-through drill-down between levels |
| Use case diagram | draw.io | Mermaid has no use case notation; draw.io has proper UML shapes |
| Activity diagram with swimlanes | draw.io | Real fork/join bars and pools, which Mermaid cannot express |
| Sequence diagram | draw.io | Deterministic lifeline and activation geometry rather than hand-placed |
| Class diagram, analysis or design | draw.io | Compartments, visibility markers and stereotypes render properly; Mermaid `classDiagram` while the shape is still changing |
| ERD | draw.io | PK/FK notation and crow's-foot edges; can be generated from SQL DDL |
| Levelled data flow diagram | draw.io | One page per level in one file, so a reviewer can check that a level balances with its parent |
| BPMN process flow | draw.io | Native BPMN events, tasks and gateways |
| Network / deployment topology | draw.io | Official cloud and device icon sets |
| Wireframe | draw.io | Wireframe shape set; still keep it low-fidelity |
| State machine | Mermaid | `stateDiagram-v2` is compact, and these change often during design |
| Small data flow, screen flow, quick inline sketch | Mermaid | Under ten nodes, the round trip through a file and an export is not worth it |
| Anything still being argued about | Mermaid | Edit in the pull request; convert once the shape settles |

The last row is the one that matters most in practice. A diagram that is still changing every day belongs in text; a diagram that has stabilised and will be shown to stakeholders belongs in draw.io.

## Availability check

`drawio-skill` requires the draw.io desktop CLI installed locally (`drawio --version`, version 30 or newer for Mermaid conversion and ELK layout). That means it works in a local agent environment and does **not** work in a browser-based chat session.

Check before promising a `.drawio` file. When the CLI is unavailable, produce the Mermaid version, say plainly that the draw.io render needs the local CLI, and leave the Mermaid in place — it is a valid diagram, not a placeholder. Never emit a link to a `.drawio` or `.png` file that was not actually generated.

## Mermaid as source, draw.io as render

Do not author the same diagram twice. draw.io's CLI converts Mermaid into a native, laid-out, editable `.drawio`, so the productive pattern is:

1. Draft the diagram as Mermaid, inside the Markdown document, where it is reviewable in a pull request.
2. Once agreed, convert it to `.drawio` and export.
3. Keep the Mermaid block in the document as a comment or in a sibling `*.mmd` file, so the next revision starts from text rather than from dragging boxes.

This keeps the thing that is reviewed and the thing that is published in sync, and it means a diagram is never trapped in a binary that only one person can edit. Where a diagram has been hand-tuned in draw.io beyond what the Mermaid expresses, the `.drawio` becomes the source and the Mermaid is deleted rather than left to rot — two sources that disagree are worse than one that is harder to edit.

## File conventions

```
docs/
  diagrams/
    c4-context.drawio          editable source, committed
    c4-context.svg             exported, committed, embedded in Markdown
    erd-orders.drawio
    erd-orders.svg
```

- **Commit both** the `.drawio` and the export. The source is uneditable-in-review but authoritative; the export is what the Markdown embeds and what renders on any platform.
- **Export SVG, not PNG**, for anything embedded in a document — text stays selectable and it scales in the HTML export and in print. PNG only when a target cannot handle SVG.
- Embed with a relative link and a caption underneath, exactly as with a Mermaid block: `![C4 container view](../diagrams/c4-container.svg)`. The caption rules in [0.1](0.1-visual-style.md#diagram-captions) apply unchanged — an exported diagram with no caption is still decoration.
- One diagram per file. Multi-page `.drawio` is the exception, used for a C4 set where the drill-down links between pages are the point.
- Name the file after the document section it serves, not after the tool or the date.

When the document set is published with `scripts/build_site.py`, every embedded image is inlined as a data URI and given a zoomable lightbox automatically — the `Mermaid` or `Image` tag shown on hover is read straight from whether the source was a fenced Mermaid block or an `![]()` reference, so no extra markup is needed for either.

## How big a diagram renders

The HTML export sizes every diagram against the reader's page rather than trusting whatever intrinsic size the renderer produced, because both failure modes are real: a three-node context diagram rendered at its natural 340px looks lost in a 900px column, and a wide sequence diagram squeezed into a 760px text column has 6px labels. The rules, in one place so an author knows what to expect:

| Situation | What the page does |
|---|---|
| Diagram narrower than the frame | Scales up, but never past 1.25× — enough to stop looking lost, not enough to turn a small diagram into a poster |
| Diagram wider than the frame | Scales down to fit, down to 0.55× |
| Wider still | Stops at 0.55× and the diagram box scrolls; full screen (⤢) and the lightbox pan/zoom take over |
| Landscape diagram taller than the viewport | Shrinks until it fits the screen height; a portrait one is left tall, because a long sequence diagram is genuinely a scrolling object |
| Raster image (PNG) | Only ever shrunk, never enlarged — a 2×-DPI export is meant to be displayed smaller |

Diagrams also render in a **wider track than the body text**: prose stops at a readable measure, diagrams and very wide tables use the full content width.

The author-side consequence is the same rule [0.1](0.1-visual-style.md) already gives for a different reason: keep a diagram under ~10 nodes. A diagram that hits the 0.55× floor and starts scrolling is not a rendering problem to tune, it is a diagram that should have been two diagrams.

A ` ```mermaid ` block that fails to parse renders as a visible error box naming the parse failure, not as a gap. Check the box is not there after building — a diagram that silently disappeared is the one bug in a document set nobody notices until a stakeholder asks about the missing picture.

## House style in draw.io

The palette in [0.1](0.1-visual-style.md#mermaid-theming) is not Mermaid-specific — it is the house style, and draw.io output should match it. Capture it once as a named style preset (`drawio-skill` can learn a preset from an existing `.drawio` file) and reuse it, rather than restyling by hand each time.

The rules that carry over verbatim: near-monochrome fills with one accent used for a single meaning per diagram; no shadows or gradients; ten nodes maximum per view; two- or three-word labels. Official vendor icons are worth using for infrastructure and cloud diagrams, where a recognisable AWS or Kubernetes icon genuinely conveys more than a labelled box — but they do not belong in a C4 container diagram, where the point is the boundary, not the vendor.

Wireframes stay low-fidelity even though draw.io makes it easy not to. The moment a wireframe looks finished, review feedback shifts from behaviour to aesthetics — see [4.5](4.5-ui-design.md#svg-layout).

## Generating from existing artifacts

Where a diagram can be derived from something that already exists, derive it — a generated diagram cannot drift from reality the way a hand-drawn one does. `drawio-skill` ships extractors for several of the cases in this document set:

| Source | Produces | Use for |
|---|---|---|
| SQL DDL | ER diagram with PK/FK edges | [4.2](4.2-data-model.md) — regenerate after every migration |
| OpenAPI / Swagger | API diagram grouped by method | [4.4](4.4-api-contract.md) — a visual index of the contract |
| Terraform / Kubernetes / compose | Deployment topology with official icons | [4.1](4.1-design.md) — the *as-deployed* view |
| Codebase import graph | Module structure | [5.1](5.1-codebase-guide.md) — the "where things are" section |
| CI configuration | Pipeline DAG | [5.1](5.1-codebase-guide.md#build-test-and-deploy) |

Two cautions. First, a generated diagram shows what *is*, which is not the same as what the design says *should be* — that gap is often the most interesting thing on the page, so label generated diagrams as generated, with the date and the command. Second, generated output is usually too dense to publish as-is; treat it as a starting point to prune, not a deliverable.

## Review and maintenance

A diagram is part of the document it illustrates, so it changes in the same pull request as the behaviour it describes — the rule in [0.2](0.2-writing-principles.md#when-to-write) applies to diagrams without exception. Where the repository runs CI, rendering changed diagrams and attaching before/after images to the pull request makes diagram review possible at all; without it, reviewers approve binary changes they cannot see.

When a diagram and its caption disagree, the caption is usually right and the diagram is stale — captions get updated during writing, diagrams get updated when someone remembers. Treat the disagreement as a defect in the diagram and fix it in the same sitting.
