**Phase 2 · Specification.** The first file in phase 2 and the contract for everything that follows: the system boundary, the actors outside it, and the closed use case list.

|---|---|---|

| [2.3](2.3-use-case-specs.md) | one section per use case | How each use case runs, how many operations it includes, and what data crosses |
| [2.4](2.4-nfr.md) | 2.4.1 NFR table | How fast, scalable, and secure the system must be and how to measure it |
| [2.5](2.5-feature-spec.md) | outside the formal report chain | One feature end to end, with work divided across teams |

**Four files, not four sections in one file.** The site sidebar is built from filenames ([0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers)), so combining all of phase 2 into `2.1` produces one sidebar row while phase 3 produces four — equal content displayed with unequal shapes. Write in the order above: closing each file is a prerequisite for the next.

**The sections, their order, and their headings are mandatory.** Do not rename, reorder, or merge them — the traceability checks below work only when parts are where expected, and their order is a dependency chain ([0.1](0.1-visual-style.md#section-order)).

| Number | Section | Answers | Form |
|---|---|---|---|
| 2.1.1 | Identify actors | Where the system boundary lies and who stands **outside** it | Boundary statement + one table |
| 2.1.2 | Identify the main use cases | Which use cases exist and which subsystem owns each | One table |

These tables are the contract for everything after them: **nothing may appear in a [2.2](2.2-use-case-diagrams.md) diagram or [2.3](2.3-use-case-specs.md) specification unless it is a row in table 2.1.2, and every table row must appear in both.** This is why the tables precede the diagrams: a specification written before the actor list closes invents an actor, and that actor survives into design because it already appears in a picture.

| Standard | Taken from it |
|---|---|
| ISO/IEC/IEEE 29148:2018 | Requirements necessary, unambiguous, **singular**, feasible, **verifiable**, traceable |
| UML 2.5.1 | *Subject* (the box) and **actor = a role external to the subject** |
| Cockburn, *Writing Effective Use Cases* | **Design scope** and the black-box rule; goal levels |
| Larman, *Applying UML and Patterns* | The three actor kinds — primary, supporting, offstage — and finding use cases from actor goals |

This document governs the use case **set** — whether it is complete and which subsystem owns each use case. Constraints on **one** use case live in [0.8](0.8-use-case-constraints.md) and are checked while writing [2.3](2.3-use-case-specs.md); completeness of operations inside a use case belongs to [0.7](0.7-operations.md).

**Mode A** reads both sections off the code: routes plus their permission checks give actors, handlers grouped by goal give use cases. A use case reconstructed from a route name is a hypothesis until someone confirms the goal behind it.

- **`#` is display order; `Use case ID` is identity.** Everything else cites the ID — a row number used as a reference points to the wrong use case as soon as a row is inserted.
- **Numbering follows the system shape**: one system `UC-01`; several, a letter each matching the file suffix (`UC-A01` admin, `UC-U01` user).
- **The `Subsystem` column in table 2.1.2 defines the axis for the entire documentation set.** It closes here; [2.3](2.3-use-case-specs.md), [3.1](3.1-analysis-classes.md), [3.2](3.2-sequence-diagrams.md), [3.3](3.3-class-diagrams.md), [4.3](4.3-detailed-design.md), and [4.5](4.5-ui-design.md) reuse exactly the same names and order. In those documents, each subsystem becomes a **separate file**, not another heading tier ([0.1](0.1-visual-style.md#section-numbering-and-subsystem-tiers)). For a small system, fill the entire column with `—` and omit the subsystem tier everywhere downstream.
- **This file owns the Open questions table for all of phase 2**, numbered locally as `1..n`. Files 2.2–2.4 contain a one-line `## Open questions` section linking here ([0.1](0.1-visual-style.md#splitting-a-document-into-several-files)).

## 2.1.1 Identify actors

UML 2.5.1 defines an actor as a role played by an entity that interacts with the subject while remaining **external to the subject**. The entire table depends on one word — **external** — so **draw the box first** instead of inferring it afterward. This directly applies the *decisions before the picture* rule ([0.1](0.1-visual-style.md#section-order)): the boundary is the decision; the actor list is its consequence.

### Three steps, in order

**Step 1 — define the box in one sentence at the start of the section.** Copy it from [1.1.1](1.1-problem-survey.md#111-problem-and-system-boundary) when available:

> System being specified: **Sales platform**, treated as a black box. Inside: customer web app, admin console, order service, and recommendation service.

Cockburn calls this **design scope** and distinguishes **black-box** use cases, which say nothing about internal components, from **white-box** use cases that open the box. Section 2.1 is **always** black-box; [4.1](4.1-design.md) opens it.

**Step 2 — three questions, all of which must pass.**

| # | Question | If no, it is |
|---|---|---|
| 1 | Is it **outside** the box just defined? | Inside ⇒ a **container**, documented in [4.1.1](4.1-design.md) |
| 2 | Does it **exchange** something across the boundary, and is it outside this project's control? | No exchange ⇒ stakeholder, not actor |
| 3 | Is it a **role**, not an individual, department, or server? | No ⇒ consolidate into a role |

Question 1 is skipped most often, and it has an objective test: **anything this project builds is never an actor.** If it is in your repository, release, or on-call responsibility, it is a component. An internal service in the actor table looks legitimate — it has a name and API and may belong to another team — but it remains **inside** the box and describes architecture, not the boundary.

**Step 3 — classify in the `Type` column** (Larman): a **Primary** actor achieves a goal through the system; a **Supporting** actor provides a service to the system — payment gateway, SMS service, or another party's ERP. People with an interest but no interaction (accounting, audit, executives) are *offstage stakeholders*: **do not put them in this table**; they are sources of `N<n>`, `BR<n>`, and `NFR<n>`.

| # | Actor name | Type | Description | Source |
|---|---|---|---|---|
| 1 | Customer | Primary | Buys through the storefront; self-registers and places orders; cannot access the admin console | 1.1.2 N1 |
| 2 | Order reviewer | Primary | Handles orders held by the system; has `order_reviewer` permission | 1.1.2 N3 |
| 3 | Payment system | Supporting | Third-party payment gateway; the system calls it and receives results by webhook | Q6 · 1.1.1 *Outside the box* |

- **An actor is a role, not a person or a job title.** The test is the permission set, not the org chart: two titles that see the same screens are one row.
- **`Source` says where the role came from** — a user group in [1.1.2](1.1-problem-survey.md#112-analyze-user-needs), an interview `Q<n>`, the `Outside the box` line in [1.1.1](1.1-problem-survey.md#111-problem-and-system-boundary), or a permission check in code for mode A. A role without a source was recalled rather than derived ([0.5](0.5-derivation.md#the-root-rule-evidence-travels-with-the-element)).
- **External systems owned by another party are actors** and are the most frequently omitted rows; one omission causes an integration to appear for the first time in sprint three. A system that only *receives* data still counts.
- **`Description` says what the role may do and what constrains it**, in one or two sentences, naming the concrete permission in `code` when one exists.
- **Every actor must appear in 2.1.2.** An actor touching no use case is dead scope or a missing use case.

### What is often mistaken for an actor

| Mistaken item | Actually | Correct location |
|---|---|---|
| Product-owned service — *"Backend Service"*, *"AI Service"*, *"Pricing Service"* | Container | Container level in [4.1.1](4.1-design.md) |
| Database, cache, queue, object storage | Data store / infrastructure | [4.2](4.2-data-model.md); `D<n>` stores in [3.4](3.4-data-flow.md) |
| Cron or product-owned scheduled job | Time-based use case **trigger** | `Trigger` field in [2.3](2.3-use-case-specs.md) |
| Browser, mobile app, embedded widget | Channel through which a role reaches the system | Not a separate row; the role is the actor |
| Two job titles with identical permissions | One role | Merge into one row |
| Accounting, audit, executives — interested but not interacting | Offstage stakeholder | Source of `N<n>`, `BR<n>`, and `NFR<n>` |
| *"System administrator"* added because every system supposedly has one | Not yet an actor | Add only when at least one real use case exists |

The first three mistakes share a cause and symptom. Cause: the author describes known **architecture** instead of the chosen **boundary**. Symptom: the actor list resembles the contents of a container diagram.

### Changing the boundary means changing the whole table, not adding a row

The same item may be an actor at one boundary and a component at another — that is a property of scope. What is never valid is **two boundaries in one table**.

A product contains `web-app`, `order-service`, and `recommend-service`, and uses an external payment gateway:

| Chosen boundary | Actors | Not actors |
|---|---|---|
| Entire product — the 2.1 default | Customer · Administrator · Payment gateway | `web-app`, `order-service`, `recommend-service` — **containers** |
| Only `recommend-service`, when its team specifies it separately | `order-service` · Knowledge administrator · Payment gateway | Customer — does **not interact** with this box |

Read vertically for the self-test: **a table containing both `Customer` and `order-service` has mixed two boundaries.** Customer is an actor only for the large box; `order-service` only for the small box. No boundary makes both rows correct. Choosing the small box is valid, but it **removes** end users from the table instead of placing services beside them.

**Cross-check [4.1.1](4.1-design.md) in both directions**: every 2.1.1 row must appear in the context diagram's *Actors / external systems* table, and **no 2.1.1 row may appear in the container table**. A name in both tables stands on both sides of the boundary, so one document is wrong.

## 2.1.2 Identify the main use cases

| # | Use case ID | Use case name | Subsystem | Description | Interacting actors | Source |
|---|---|---|---|---|---|---|
| 1 | UC-01 | Place order | Sales | Customer selects products, confirms an address, and pays to create a valid order | Customer, Payment system | FR1 · pass 1 |
| 2 | UC-02 | Review held order | Operations | Reviewer examines an order held by a risk rule and decides whether to continue or cancel it | Order reviewer | FR4 · BR11 · pass 5 |
| 3 | UC-03 | Release expired reservation | Sales | System returns reserved inventory after a cart remains unpaid for 60 minutes | — (time-based trigger) | BR07 · pass 3 |

- **The `Source` column proves a row was derived rather than recalled**: an `FR<n>`, `BR<n>`, the discovery pass that found it, a `Q<n>`, or mode A `path:line`. The general rule and four valid evidence types are in [0.5](0.5-derivation.md#the-root-rule-evidence-travels-with-the-element). It also exposes what the old table hid: if every source comes from pass 1, the other five passes never ran.
- **Verb + noun, at user-goal level** — *Place order*, not *Cart screen* or *Check inventory*. Cockburn's test: when it ends, can the primary actor go for coffee satisfied? A step toward another goal belongs inside a [2.3](2.3-use-case-specs.md) flow or behind `<<include>>`. The three goal levels, **one actor · one goal · one session** test, and empty-verb table are in [0.8 R1–R2](0.8-use-case-constraints.md#r1-goal-level-one-actor-one-goal-one-session). A *"wait for someone to approve"* step in the middle of the main flow is a **use case boundary**, not a step — this is where a business process is often mistaken for one use case.
- **`Description` is one sentence naming the value delivered**, not a summary of the steps—[2.3](2.3-use-case-specs.md) owns steps, and a description that lists them will contradict them within a month.
- **`Interacting actors` lists the primary actor first.** Every name must exist in 2.1.1, spelled identically.
- **CRUD is not a use case set — but one merged row is not yet a specification.** Turning *Create / Update / Delete product* into four rows promotes four operations of **one goal** into four goals, quadrupling the use case table without stating which rules apply to which operation. Conversely, a bare *"Manage products"* row is **valid and empty**: it does not state how many operations exist, what each receives, or what failures return. That omission appears only in [4.4](4.4-api-contract.md), when the contract contains one endpoint instead of six. Keep **one row per goal**, then require its [2.3](2.3-use-case-specs.md) **operation matrix** ([0.7](0.7-operations.md)). This avoids both failures.
- **Fifteen rows is a lot** — subfunctions have usually crept in, or the set should be split by system. A use case matching a leaf of the [1.1.5](1.1-problem-survey.md#115-function-hierarchy) function hierarchy one-to-one is right-sized.

### Finding the complete set, not stopping at obvious cases

ISO/IEC/IEEE 29148 treats **completeness as a property of the requirement set**, not any one row — so use case discovery is a deliberate sweep with an end condition, not a list of whatever arose in a workshop. Stopping at the obvious six does not remove the other nine; it moves them into sprint three as *"newly discovered work,"* where they cost a redesign instead of one line.

Run all six passes, in order, and add what each turns up:

| # | Pass | Question | Often missed |
|---|---|---|---|
| 1 | Actor × goal | For **every** actor in 1.1, what does this role want to achieve? | Supporting roles — accounting, customer support, audit |
| 2 | External events | Which external events strike the system, and how does it respond? | Partner webhooks, reply emails, reconciliation files |
| 3 | Temporal events | What runs automatically on a schedule, deadline, or cycle? | Reservation expiry, period close, reminders, data cleanup |
| 4 | Entity lifecycle | Through which use cases is each entity created, changed, and ended? | Cancellation, refund, post-approval edits, close, archive |
| 5 | Administration and recovery | Who configures, authorizes, corrects bad data, and reconciles? | Data repair, failed-job rerun, report export |
| 6 | External systems | What does each system actor call into or receive from the system? | The reverse direction — what our system *pushes* outward |

Passes 3, 4 and 5 are where the missing use cases actually are, for one reason: nobody clicks a button to start them, so nobody demonstrates them in a workshop.

Passes 2 and 3 use **event partitioning** (McMenamin & Palmer) as a procedure rather than an open question: list external, temporal, and state events first; write one response per event; make every response both a row here and a top-level process in [3.4](3.4-data-flow.md). The full procedure and the category inventory used for pass 4 are in [0.5 K1 and K2](0.5-derivation.md#eleven-techniques).

Then close the list with two coverage checks, each run in both directions:

- **`FR<n>` ↔ use case.** Every functional requirement in [1.1.4](1.1-problem-survey.md#114-functional-requirements) is realized by at least one use case, and every use case realizes at least one `FR`. An `FR` without a use case means the sweep missed something — or the row was never functional and belongs in [2.4](2.4-nfr.md) as an `NFR`.
- **Leaf functions ↔ use case.** Every leaf in the [1.1.5](1.1-problem-survey.md#115-function-hierarchy) function hierarchy maps to at least one use case. If the tree and table disagree, one is wrong.

**The list is closed only when a full pass adds nothing and both checks return empty.** Record the closure date in the changelog — "we never agreed to build that" is resolved by pointing to it. A considered and rejected use case stays in the table with `Out of scope` in its description, so later readers can distinguish *not needed* from *not noticed*.

## Self-check before publishing

| # | Check | Fails when |
|---|---|---|
| 1 | Section 2.1.1 begins with a **boundary statement** naming what is inside the box | No basis for the three actor questions |
| 2 | **No 2.1.1 row is something this project builds** — compare with the [4.1.1](4.1-design.md) container table | A container written as an actor |
| 3 | Table 2.1.1 does **not** contain both an end user and a product-owned service | Two boundaries mixed in one table |
| 4 | Every actor in 2.1.1 appears in at least one 2.1.2 row | Dead scope or a missing use case |
| 5 | Every name in the 2.1.2 actor column exists identically in 2.1.1 | An actor invented while writing |
| 6 | Every use case cites ≥ 1 `FR<n>` **and every `FR<n>` is realised by ≥ 1 use case** | Scope with no requirement, or a requirement nobody noticed missing |
| 7 | Every leaf of the function hierarchy maps to ≥ 1 use case | Tree and table disagree about scope |
| 8 | All six discovery passes run, closing date in the changelog | The list stopped at what someone happened to mention |
| 9 | No `Source` cell is blank, and every entry is **reader-verifiable** — `FR2`, `BR-CAMP-01`, `1.1.2 N7`, `path:line` | Evidence exists only in the writer's head |
| 10 | Every `Subsystem` cell is filled and names match the [1.1.5](1.1-problem-survey.md#115-function-hierarchy) function hierarchy | Every downstream document invents its own subsystem division |
