## Page skeleton

Every document follows the same top-to-bottom shape. Readers learn the shape once and then know where to look in any document the team writes.

```markdown
# Title

<metadata table — required: Status · Last updated; include other fields only when known>

<one-paragraph plain-language summary>

## Scope
What this document covers, and one line on what it deliberately does not.

## <body sections — type-specific>

## Open questions
| # | Question | Owner | Needed by |

## Changelog
| Date | Change | Author |
```

`Open questions` and `Changelog` are always last, always in that order. Drop `Open questions` only when there genuinely are none. The changelog matters more than it looks: when a document is a contract, "when did this change and who changed it" is the first thing someone asks after an integration breaks. Record the actual author when known; never substitute the assistant's name.

- **Number `Open questions` locally as `1..n` within each document.** Those numbers have meaning only in the current document; nobody cites them across documents, and they are not global identifiers like `FR<n>` or `BR<n>`.
- **Only `Status` and `Last updated` are required metadata.** Add `Owner`, `Author`, `Applies to`, or a document-specific field only when its concrete value is known and relevant. Omit the whole optional row otherwise; never leave it empty or fill it with a placeholder, `Unknown`, or `TBD`.
- **Author ≠ Owner** when both are present: the Author wrote this version; the Owner is accountable for the content remaining correct a year later and is often a team.

## Section numbering and subsystem tiers

**One numbered item in the overall contents is one `.md` file, and the filename carries that number.** `2.3` in the contents ⇒ `2.3-use-case-specifications.md`. This is not aesthetic: `build_site.py` builds the sidebar **from filenames** (`PHASE_FILENAME_RE`, with the leading number as the phase), not headings. A file containing four sections therefore produces **one sidebar row** while an adjacent chapter produces four, making the set look unevenly divided even when the Markdown itself is valid.

| Tier | Form | Example |
|---|---|---|
| Document | File `<section-number>-<name>.md`, with H1 beginning with that number | `3.2-sequence-diagrams.md` → `# 3.2 Sequence diagrams` |
| Section | H2 — the file number **plus one level**, or an **existing identifier** | `## 3.2.2 …` · `## UC-U01 — Place order` |
| Subsection | H3, **unnumbered**, with the fixed name of a repeated part | `### Message table` |
| — | **H4 does not exist** | Split the file |

**Choose one of two H2 forms and use only that form in a document.** Use the next number (`## 3.2.2 Sales subsystem`) when sections are different parts of one document; use an **identifier** (`## UC-01 — Place order`, `## S1 — Cart screen`, `## POST /orders`) when the document contains **n identically shaped blocks** that already have IDs. Other documents cite the ID, so adding a second number only creates two addresses for the same item.

**If another tier is required, split the file instead of adding a heading level.** This replaces the old idea that "numbering stops at three": the ceiling is **H3**, not a digit count. Subsystem → use case → seven use case parts creates three tiers beneath the document, which no valid heading arrangement can contain. Make each subsystem a **file**:

```text
2.3-use-case-specifications.md  # no subsystem split: H2 = UC-01, UC-02 …
2.3.1-sales-use-cases.md        # split: one file per subsystem; number gains a level
2.3.2-inventory-use-cases.md
```

The extra level in the filename is a **consequence** of splitting, not something to avoid: `2.3.1` remains a readable address, while nobody cites `### 2.3.1.1`. The file number follows the tree's real depth. Four levels (`4.5.4.1`) are valid but deserve a second look — the parent document often serves two purposes, and splitting higher in the tree is cleaner.

### What appears in the page contents

The page contents on the right collects **H2 and H3 only** (`collectHeadings` in `site-template.html`). Remember two consequences:

- **H4 is invisible.** An H4 is a section nobody can navigate to, and the rendered page will not match the contents you counted in Markdown.
- **A repeated part with a fixed name must be a heading, not bold text.** *Purpose*, *Operation matrix*, and *Activity flow* are destinations readers **jump to**, not mere emphasis. `**Purpose**` is neither a heading nor a contents entry; `### Purpose` is both. Reserve bold for table labels and RFC 2119 keywords.

**Contents budget: roughly 40 entries per page.** Above that, **split the file** instead of demoting headings to hide entries. Six use cases × seven parts = 42 subsections: technically valid, practically unusable. This threshold tells you when a subsystem needs its own file — around **five repeated blocks** per file.

### Splitting a document into several files

After a split, two shared sections need explicit homes. Both naive choices are wrong: copying them into every file creates noise; removing them loses history.

| Shared part | Destination |
|---|---|
| **Changelog** | Split by file: every row belongs in the file the change **touches**. A change affecting two files gets two rows on the same date, each describing its part |
| **Open questions** | **One file owns the table** — the first file in the group — and every other file has a one-line `## Open questions` section linking to it. Number the table locally as `1..n` in the owning file |
| **Conventions shared by a group** | Put them at **the start of the group they govern** (*Shared conventions for the Sales subsystem*, at the start of `2.3.1`), not in a separate section above; centralizing them forces readers to jump upward and back down |

Every file in the group opens with one line explaining which part of which section it contains and linking to the other parts. A silent split makes readers believe they have read the whole section.

**After splitting, update every link.** If the router says to write `4.2` but its content is folded into `4.1.2`, every link to `4.2-data-model.md` dies — and nobody reports dead links in an internal documentation set. Scan before declaring completion: `build_site.py` prints every unresolved `.md` link and `#fragment`.

## Section order

Numbering says where a section lives; this says in what order sections appear, and it is not a matter of taste. **Anything that determines the shape of a later item must come before it.** Three rules catch defects from the contents alone:

| Rule | Why | Defect caught |
|---|---|---|
| **Decisions before the picture** | A diagram is a *consequence* of decisions, not their source | A container diagram before architecture decisions: readers see the shape before the reason, while the author has made implicit decisions |
| **Inventory before picture, picture before detail** | Paths cannot be drawn between items that have not been listed | A screen-flow diagram before the screen inventory |
| **Derived material last** | Consolidations, traceability tables, and plans are correct only after their inputs are complete | A consolidated class diagram before per-use-case diagrams, which then replaces them |

In practice, **Open questions** and **Changelog** always come last; **Conventions / Scope** always comes first; between them, dependency order replaces writing convenience.

Check by reading the contents once: for each section, ask *"does writing this require anything below it?"* Every "yes" requires a change — either reorder the sections or state that the dependency is an intentional loop and what the second pass revises.

**Cross-document dependency chain** (read downward as writing order):

```
1.1 discovery → 1.2 rules + glossary → 2.1 use cases → 3.1 classes → 3.2 sequences → 3.3 class diagrams → 3.4 DFD
                                         ↓                                          ↓
                              4.1 architecture + ERD + classes + UI → 4.2 data model
                                         ↓
                              4.3 SDD → 4.4 API contract → 4.5 UI design → 6.1 test plan
```

4.4 precedes 4.5 because each screen element's `Data source` cites a field returned by an endpoint. Reversing the order designs a screen around data that no contract returns.

### Subsystems — choose one axis once

A medium-sized product has several subsystems: sales, inventory, administration, and reporting. Choose that division **in [2.1](2.1-actors-and-use-cases.md) and reuse it unchanged** through phases 3 and 4 — the same names, order, and numbering. Reviewing a use case means reading it in 2.1 beside its sequence diagram in 3.2, which works only when the documents share the same shape.

Dividing by subsystem means **splitting files**, not adding a heading tier. Every subsystem gets its own file number while preserving the internal shape:

| Document | No subsystem split | Split by subsystem |
|---|---|---|
| 2.3 Use case specifications | `2.3-use-case-specifications.md` → `## UC-01 — …` | `2.3.1-sales-use-cases.md`, `2.3.2-inventory-use-cases.md`, with the same H2 shape |
| 3.1 · 3.2 · 3.3 Analysis | `3.2-sequences.md` → `## UC-01 — …` | `3.2.1-sales-sequences.md`, `3.2.2-inventory-sequences.md` |
| 4.5 UI | `4.5-ui-design.md` → `## S1 — …` | `4.5.1-sales-ui.md` … |
| 4.4 API contract | `4.4-api-contract.md` → `## POST /orders` | `4.4.1-product-api.md`, `4.4.2-order-api.md` — split by **resource** |

The last row uses the same mechanism on a different axis: 4.4 splits by **resource**, not subsystem, because readers ask *"what can I do with products?"* rather than *"which subsystem?"* Different documents may use different axes, provided each document uses only one. Mixing two axes inside one document is the defect.

- **Split only after reaching the budget.** One file holds about five repeated blocks before its contents exceed roughly 40 entries. Below that threshold, keep one file with all subsystems; the use case table's `Subsystem` column is the single statement of membership.
- **Subsystem-specific conventions belong at the start of that subsystem's file**, not in a shared section above. Inventory readers should not jump into the Sales file to learn their conventions.
- **Changing axes midway is a defect.** If 2.1 divides by subsystem but 3.2 divides by actor, no pair of documents can be read side by side. Keep the chosen axis even when a later document would look shorter on another one.
- **Write subsystem names once** — in the [1.1](1.1-problem-survey.md) function tree — then copy them exactly everywhere; do not create near-synonyms.

## Mermaid theming

Use one theme across all diagrams so a reader recognises the visual language. Put this init block at the top of every Mermaid fence:

```
%%{init: {'theme':'base', 'themeVariables': {
  'primaryColor':'#f4f6f8','primaryTextColor':'#1f2933','primaryBorderColor':'#9aa5b1',
  'lineColor':'#7b8794','secondaryColor':'#eef2f6','tertiaryColor':'#ffffff',
  'fontFamily':'ui-sans-serif, system-ui, sans-serif','fontSize':'14px'
}}}%%
```

The palette is deliberately near-monochrome. Colour is a signal, not decoration — spend it only on meaning, and only in one way per diagram. Two conventions cover almost everything:

- **Ownership** — one accent per team when a diagram crosses BE / FE / AI / Data boundaries.
- **Change** — grey for existing components, one accent for what this document adds or modifies.

Accents, used sparingly: `#2f6f9f` (blue), `#3f8f6f` (green), `#a8742a` (amber), `#8f4f6f` (plum). Apply with `style NodeId fill:#eaf1f7,stroke:#2f6f9f` and add a legend line under the diagram naming what the colour means. A diagram with three colour meanings at once is unreadable — pick one.

Layout: prefer `flowchart TD` for hierarchy and `flowchart LR` for pipelines and request paths. Use `subgraph` to group by deployment boundary or team, and keep subgraph titles to two or three words.

## Diagram captions

The user's requirement is short annotations that are easy to understand, so treat the caption as part of the diagram rather than an optional extra. Directly under each fence, write a short paragraph — not a bulleted restatement of the boxes — that answers:

1. What is the one thing this picture is showing?
2. What is the non-obvious detail a reader would otherwise miss?
3. What does this picture deliberately not show?

**Example:**

> Checkout calls `orders-service` synchronously and gets an order ID back within the request; everything after that — payment capture, inventory reservation, the confirmation email — happens off the `order.created` event and can lag by a few seconds. The diagram shows the happy path only; retry and compensation behaviour is in the API contract.

Two to four sentences. If the caption needs more, the diagram is doing too much.

## Tables

- Header row is a short noun (`Field`, `Type`, `Required`, `Notes`) — never a sentence.
- Same column order every time a table type repeats within a document set.
- Empty cells contain `—`, never blank space, so a missing value is clearly a decision rather than an oversight.
- Types are written in the language of the boundary being described: JSON types (`string`, `integer`, `boolean`, `array<object>`) in API contracts, database types (`uuid`, `varchar(64)`, `timestamptz`) in ERDs. Do not mix the two vocabularies in one table.
- Anything with more than about eight columns should be split into two tables; wide tables are unreadable on a laptop and unprintable.

## Colour and emphasis

In prose, emphasis carries meaning and nothing else:

| Style | Reserved for |
|---|---|
| **Bold** | RFC 2119 keywords, table labels, `TBD` markers |
| `Code` | Identifiers: field names, endpoints, services, files, values |
| *Italic* | A term being defined for the first time |
| > Blockquote | A single callout per section, at most — a warning that would cause an outage if missed |

No coloured text in Markdown, no HTML `<span>` styling, no badge images. If something is important, say why it is important in a sentence.

## File naming and layout

```
docs/
  system/     c4-context.md, c4-container.md, erd.md
  api/        orders-service.api.md, inference.api.md
  features/   2026-08-checkout-split-payment.md
  ui/         checkout-wireframes.md
  guides/     admin-user-guide.md
```

Lowercase, hyphenated, no spaces. Feature specs are prefixed `YYYY-MM-` because they are point-in-time records and sort usefully; system documents are living pages and are not dated in the filename — their metadata table carries the date.

**Documents in the formal report chain have filenames beginning with their section number** and sit flat in `<docs_folder>/`, not in chapter subdirectories: `2.3-use-case-specifications.md`, `2.3.1-sales-use-cases.md`. The sidebar groups by the first digit, so subdirectories only lengthen paths without changing presentation. Documents outside the chain — runbooks, ADRs, and guides — may use directories and are assigned to phases by directory name.

## The overview page

A folder of good documents is still unusable if nobody knows where to start, and the landing page is the only page you can be sure every reader opens. Every documentation set gets exactly one, at `<docs_folder>/README.md`: a repository host renders it when someone opens the folder, and `build_site.py` renders it as the landing page of the exported site instead of the generated phase grid.

It is **not** the repository README of `5.1-codebase-guide.md`. That one gets a developer running the code; this one gets any reader to the right document. A repo with both has one at the root and one in `docs/`, and they link to each other rather than repeating.

Four blocks, in this order, and nothing else:

| # | Block | Heading | Answers | Size |
|---|---|---|---|---|
| 1 | Project in brief | *About this project* | What is being built, for whom, and its current state | one paragraph + document metadata |
| 2 | Document map | *All documents* | Which documents exist, what each answers, and when to open it | one row per document |
| 3 | Reading paths | *Start here* | Where each kind of reader starts and in what order | one row per reader, ≤ 4 documents each |
| 4 | Conventions | *Conventions* | What statuses, ID prefixes, and language rules mean | four to six lines |

```markdown
# <Product> — Documentation

| | |
|---|---|
| **Status** | Draft / In review / Approved / Deprecated |
| **Last updated** | YYYY-MM-DD |

<optionally add System, Users, Stage, or other project metadata only when known>

<2–4 sentences a non-technical reader can finish: what the product does, who
uses it, what problem it removes. Same bar as the summary paragraph of any
document — no jargon, every acronym expanded.>

## All documents

| # | Document | Question answered | Read when | Status |
|---|---|---|---|---|
| 1.1 | [Discovery](1.1-problem-survey.md) | Why this exists, who it serves, and what done means | Entering this domain for the first time | Approved |
| 1.2 | [Business rules](1.2-business-rules.md) | Thresholds, conditions, calculations, and terminology | Before implementing calculation logic | Approved |
| 2.1 | [Use cases](2.1-actors-and-use-cases.md) | Who may do what and where the system boundary lies | Dividing work or resolving authorization questions | In review |
| 4.2 | [Data model](4.2-data-model.md) | What is stored, how it relates, and which fields are required | Writing a migration or encountering an unfamiliar field | Approved |
| 4.4 | [API contract](4.4-api-contract.md) | How two sides communicate and what errors they return | Building frontend and backend in parallel or integrating externally | Approved |
| … | | | | |

## Start here

| You are… | Read in this order |
|---|---|
| New to the team | 1.1 → 4.1 → 5.1 → the runbook for the service you support |
| Stakeholder / customer | 1.1.1–1.1.2 → 2.2 for the feature under discussion |
| Building a feature | feature specification → 4.3 → the contracts it lists |
| Integrating from another system | 4.4 → 4.1 to locate it in the architecture |
| Tester | 2.2 → 6.1 → cases for your assigned area |
| On-call engineer | 5.2 runbook → 4.1 |

## Conventions

- **Status**: `Draft` is unsettled · `In review` is being reviewed · `Approved` is a
  contract and changes through a pull request · `Deprecated` remains for reference and is not used to build.
- **Reference IDs**: `N<n>` need · `FR<n>` requirement · `BR<n>` business rule ·
  `UC-<n>` use case · `TC-<area>-<n>` test case. Every item cites the one to its left.
- **Language**: English prose; field, endpoint, and enum names plus **MUST/SHOULD/MAY**
  remain unchanged.
- **Report errors to**: <person or channel>.
```

Seven rules, and the first two are what separate this page from a directory listing:

- **The `Read when` column is the reason the page exists.** `Question answered` says what is inside a document; `Read when` says whether to open it. A map with only the first column is a prose file listing, and readers skim past it as they skim past `ls`.
- **It routes; it does not explain.** The only prose this page owns is the opening paragraph. Every other fact is a link to the document that owns it — the moment the overview starts restating a business rule or an endpoint, there are two versions of it and the shorter one wins by accident.
- **Status is the one deliberate duplication.** A reader deciding what to open needs to know what to trust before opening it, so status is repeated here from each document's metadata table and updated in the same pull request. Mark deprecated documents in the map rather than deleting the row — a reader who finds a dead link with no explanation assumes the whole set is neglected.
- **Order the map by phase number, never by importance**, so the map, the writing order and the site sidebar all read in the same sequence. Importance belongs in the reading paths, which is where a reader asks the question.
- **Keep every reading path to four documents or fewer**, and order the rows by how often that reader appears. A path long enough to feel like homework does not get followed.
- **Link with the plain relative filename** — `4.4-api-contract.md`, `ops/runbook-orders.md`. The site build rewrites those into in-page links, so the same link works in the repo and in the exported page; an absolute path or a `docs/`-prefixed one breaks in both.
- **Update it in the same session that adds, renames or retires a document.** A document missing from the map does not exist as far as the reader is concerned. This is the last edit of a writing session, not a follow-up task.

The overview page follows the same metadata rule as every other document: it carries its own `Status` and `Last updated`, then includes project fields such as `System`, `Users`, or `Stage` only when their values are known. The document map still repeats each linked document's status because readers need to know what they can trust before opening it.

Write it once the second document lands — with one document there is nothing to route — and keep the four blocks even when the set is small. An overview page for three documents is three rows and still worth having, because it is where the project paragraph lives.
